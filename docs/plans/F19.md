# F19 · Agent clients against fixtures

## Goal

Behavior (copied from docs/features.json):

> Typed clients read order, transitions, courier timeline (dispatch GraphQL) and payment, refundable amount (ledger REST); recorded fixtures replay without live services.

Verification (copied from docs/features.json):

```bash
cd agent && python -m pytest -q tests/test_clients.py
```

F19 is the agent's first code. It has three parts, decided with the user on 2026-10-26:

1. **Dispatch gains an order event log.** Today dispatch updates `order.status` in place and keeps no history, so "transitions" and "courier timeline" have no data behind them. F19 adds an `order_event` table, written in the same transaction as every order change, and a read-only GraphQL query `orderTimeline`.
2. **Dispatch gains a read-only service token** for the agent (option B). The agent is not a user: it presents `X-Service-Token`, which authorizes exactly two queries, `getOrder` and `orderTimeline`, on any order, and nothing else. No new role, no user row, no change to `createAccount`.
3. **The agent gets typed async clients** for dispatch (GraphQL) and the ledger (REST), and a replay transport that serves recorded fixtures with no network.

The fixtures are recorded from the real services by their own tests (a dispatch e2e spec and a ledger HTTP IT). The same tests, run without the record switch, check that the live responses still have the committed fixtures' shape. So a fixture cannot silently drift from the service it claims to come from.

Contract first (root `AGENTS.md`): the dispatch operations the agent sends are written in `contracts/` before either side.

## Design decisions (fixed)

1. **Order event log.** One immutable row per applied order change, in table `order_event`, written in the same transaction as the change. Three kinds:

   | Kind | Written by | `fromStatus` | `toStatus` | `actor` | `driverId` | `providerEventId` |
   | --- | --- | --- | --- | --- | --- | --- |
   | `CREATED` | `createOrder` | null | `Pending` | `Client` | null | null |
   | `STATUS_CHANGED` | `editOrder` | old status | new status | `Owner` or `AssignedDriver` | the driver's user id when `AssignedDriver`, else null | null |
   | `STATUS_CHANGED` | fulfillment callback (`WebhookIngestService.apply`) | old status | new status | `FulfillmentProvider` | null | the callback's `eventId` |
   | `DRIVER_ASSIGNED` | `takeOrder` (winning claim only) | null | null | `AssignedDriver` | the driver's user id | null |

   - `actor` values are the existing `TransitionActor` literals. `CREATED` always uses `Client`: it names the ordering customer's part, whatever role the account has.
   - Only applied changes are recorded. A noop, an illegal or forbidden transition, a lost `takeOrder` race, a duplicate or ignored callback writes nothing, because each of those either writes nothing today or rolls back.
   - Payment status changes (`paymentStatus`, F16) are not order events. They are not part of the fulfillment timeline, and the agent reads payment state from the ledger.
   - No backfill. Orders created before the migration have an empty timeline; the agent treats that as "no history" (F20/F21 decide what that means).
2. **Order of events.** Events of one order are read by `id` ascending. Every write site holds the order row lock (the conditional `UPDATE`, or the insert in `createOrder`) until it commits, and inserts its event after taking that lock, so for one order `id` order is commit order. `occurredAt` defaults to `clock_timestamp()`, not `now()`: `now()` is the transaction's start, and a callback transaction can start before an earlier change commits, which would make `occurredAt` go backwards.
3. **Every write site checks it changed exactly one row** before recording. `editOrder` and `takeOrder` already check `affected`. `WebhookIngestService.apply` does not: its `manager.update(Order, {id, status}, …)` can match nothing if the order moved concurrently, and would then record an event that did not happen. F19 adds the check there: `affected !== 1` throws `ConflictError('The order changed while this callback was applied')` inside the transaction. The transaction rolls back, the `processed_event` row too, the controller answers 500, and the provider redelivers. That is the existing contract for "not durably decided".
4. **`orderTimeline` query**, read-only: `orderTimeline(input: {orderId: Int!}): OrderTimelineOutput!` with `{ok, code, error, events: [OrderEvent!]}` in the `CoreOutput` envelope, the same as `getOrder`. Same visibility as `getOrder`: a user sees the timeline of an order they may see (`canSeeOrder`); otherwise `FORBIDDEN`; an unknown order is `NOT_FOUND`.
5. **Service token (option B, decided with the user).**
   - Config `AGENT_SERVICE_TOKEN`, optional, at least 32 characters (Joi). When it is unset, service access is off and every service-token request is refused.
   - The agent sends header `X-Service-Token: <token>`, and no `Authorization` header.
   - Only handlers marked `@ServiceReadable()` accept it: `getOrder` and `orderTimeline`. Nothing else, so no mutation and no list query.
   - If a request carries `X-Service-Token`, the guard decides on the token alone, even if `Authorization` is also present: readable handler and matching token → allowed as the service caller; anything else → refused. A request cannot fall back from a bad service token to a user JWT.
   - The comparison is constant time: SHA-256 of both values, then `timingSafeEqual`.
   - A service caller may read any order. That includes fields the agent does not select (for example `customer { email }`): the token is a secret with full read access to orders. The agent's operations select no email.
   - HTTP only. The WebSocket context does not read the header, so subscriptions never see a service caller.
6. **Caller type.** `getOrder` and `orderTimeline` take a `Caller` (`{kind: 'user', user}` or `{kind: 'service'}`) instead of a `User`, from a new `@CurrentCaller()` decorator. `OrderService.canRead(caller, order)` is `true` for the service and `canSeeOrder` for a user. Other handlers keep `@AuthUser()`.
7. **Contract first.** `contracts/dispatch-agent-operations.graphql` holds the two operations the agent sends, `AgentOrder` and `AgentOrderTimeline`, with their exact selection sets. Three checks hold it in place:
   - the dispatch e2e test validates the document against dispatch's live schema and sends it as is;
   - the agent test compares its embedded operation strings with the file;
   - nothing else defines these operations.
8. **Recorded fixtures** live in `contracts/fixtures/agent/`, one JSON file per HTTP exchange. They are shared between services, so `contracts/` is the place (root `AGENTS.md`: "shared fixtures").
   - Producers: `dispatch/test/agent-fixtures.e2e-spec.ts` (6 files) and `ledger/src/test/java/com/paymentsledger/payment/AgentFixturesHttpIT.java` (5 files).
   - With `RECORD_AGENT_FIXTURES=1` a producer writes its files. Without it, it compares the live response with the committed file by **shape** (decision 9) and fails on any difference or a missing file. Ids and timestamps differ between runs, so values are not compared, except those the test asserts itself.
   - No request header is recorded. A fixture never contains a credential (agent test A2).
9. **Fixture format and shape.**

   ```json
   {
     "name": "ledger-refundable-full",
     "source": "ledger/src/test/java/com/paymentsledger/payment/AgentFixturesHttpIT.java",
     "request": {"method": "GET", "path": "/v1/payments/pay_…/refundable", "operationName": null, "variables": null},
     "response": {"status": 200, "body": {}}
   }
   ```

   - `name` equals the file name without `.json`. `source` is the producer's path from the repository root. GraphQL requests use `method: "POST"`, `path: "/graphql"`, the `operationName` and the `variables` object; REST requests have both `null`. `path` is the request's real path, ids included.
   - Files are UTF-8, pretty-printed (dispatch: `JSON.stringify(value, null, 2)`; ledger: Jackson's default pretty printer), with a final newline. Body keys keep the server's order.
   - The shape of a JSON value: an object maps each key, sorted, to the shape of its value; an array is the list of its items' shapes, so its length counts; `null`, booleans, strings and numbers are the type names `null`, `boolean`, `string`, `integer` (a whole number) and `float`.
   - Verify mode compares `request.method`, `request.operationName`, the shape of `request.variables`, `response.status` and the shape of `response.body`. `request.path` is not compared, since it holds run-specific ids.
10. **Agent clients**, Python 3.11, async (`httpx.AsyncClient`), so F21 can gather evidence in parallel.
    - Typed responses are Pydantic v2 models, frozen, camelCase aliases, unknown fields ignored (the ledger's `PaymentSummary` has `additionalProperties: true`).
    - Money fields are `StrictInt` and at least 0: a JSON float such as `100.0` is a malformed response, never coerced (root hard rule: integer cents).
    - Typed errors, one hierarchy (Changes, `errors.py`). The clients never retry; retry and escalation are F21's.
    - Arguments are validated before any request: an invalid payment id or order id raises `ValueError` and sends nothing.
    - Credentials never appear in an exception message, `repr` or log.
    - The agent's ledger credential and its provisioning (F14 review note: it must belong to the payment's application) are F22's. F19's tests use placeholder tokens.
11. **Replay without live services.** `FixtureReplay` turns the recordings into an `httpx.MockTransport`. A request matches a recording on method, path, `operationName` and `variables` (compared as canonical JSON). An unmatched request raises `UnrecordedRequest`, so a test can never reach a network. The verification command needs no dispatch, ledger, database or Docker.
12. **Agent tooling.** `uv` creates `agent/.venv` with Python 3.11; dependencies are pinned exactly in `agent/pyproject.toml`: `httpx==0.28.1`, `pydantic==2.12.5`, `pytest==9.0.2`. No build backend: tests import the package through pytest's `pythonpath = ["."]`. The verification command calls `python`, which on the developer's Mac exists only inside the activated venv (Steps).

#### `agent/fairsettle_agent/clients/errors.py` (new)

```python
class ClientError(Exception):
    """Base of every client failure. Messages never contain credentials."""
    service: str          # "dispatch" or "ledger"

class Unavailable(ClientError):        # connect error, timeout, any other httpx.TransportError, or HTTP 502/503/504
class Unauthorized(ClientError):       # ledger 401/403; dispatch extensions.code FORBIDDEN on the guard
class NotFound(ClientError):           # ledger 404 NOT_FOUND; dispatch getOrder/orderTimeline code NOT_FOUND
class Forbidden(ClientError):          # dispatch code FORBIDDEN inside the CoreOutput envelope
class ServiceError(ClientError):       # any other non-2xx, or a dispatch envelope with ok false and another code
class MalformedResponse(ClientError):  # not JSON, wrong shape, or a model validation failure
class UnrecordedRequest(ClientError):  # FixtureReplay found no recording for a request
```

- Every class takes `(service: str, message: str, *, status: int | None = None, code: str | None = None, request_id: str | None = None, retryable: bool = False)` and stores each as an attribute. `str(error)` is `f"{service}: {message}"`.
- `Unavailable` sets `retryable=True`. Ledger errors copy `retryable`, `code` and `requestId` from the `Error` body when it parses, so a `429 RATE_LIMITED` is a `ServiceError` with `retryable=True`.
- `MalformedResponse` raised from a Pydantic error chains it (`raise … from exc`), and its message names the failing fields, never the body.

#### `agent/fairsettle_agent/clients/replay.py` (new)

```python
FIXTURES_DIR: Path  # repository-root contracts/fixtures/agent

@dataclass(frozen=True)
class Recording:
    name: str
    method: str
    path: str
    operation_name: str | None
    variables: dict | None
    status: int
    body: object

class FixtureReplay:
    def __init__(self, recordings: Iterable[Recording]) -> None
    @classmethod
    def load(cls, *names: str, directory: Path = FIXTURES_DIR) -> "FixtureReplay"
    @property
    def requests(self) -> list[httpx.Request]
    def transport(self) -> httpx.MockTransport
    def client(self, base_url: str = "http://fixture.invalid") -> httpx.AsyncClient
```

- `load` reads `<name>.json` per name; a missing file is `FileNotFoundError`; a file whose `name` differs from its file name, or that lacks a decision-9 key, is `ValueError`.
- Two recordings with the same match key (method, path, operation name, canonical variables) are `ValueError` in `__init__`.
- The transport's handler appends every request to `requests`. Then it computes the request's match key: method, URL path, and for `POST /graphql` the body's `operationName` and `variables`, canonicalised with `json.dumps(…, sort_keys=True, separators=(",", ":"))`. A match returns `httpx.Response(status, json=body)`. No match raises `UnrecordedRequest("fixture", "no recording for <method> <path> <operationName>")`; httpx propagates it out of the client call unchanged, because it is not an `httpx.TransportError`.
- `client` returns `httpx.AsyncClient(base_url=base_url, transport=self.transport())`. The `.invalid` host can never resolve, as a second guard against a real request.

## Risks

- **Migration on existing databases.** The table is new and nothing is backfilled, so it cannot fail on old data. Outside production it runs on boot (`migrationsRun`); the compose image runs `migration:run` before `node dist/main` (`dispatch/Dockerfile`), so the root stack applies it on its next build.
- **Event writes extend three transactions.** `editOrder` and `takeOrder` move from a bare `UPDATE` into a transaction. The `UPDATE`'s row lock is now held until the event insert commits, which is one statement later. The existing concurrency tests (`take-order-concurrency.e2e-spec.ts`, `fulfillment.e2e-spec.ts`) must pass unchanged.
- **The service token is a full-read secret.** Anyone holding it reads every order, including fields the agent does not select. It is optional and off by default; it must never be committed or logged (root hard rules). D12 and D13 guard the scope.
- **Fixture drift.** A fixture is only as current as its last recording. The verify mode of both producers fails when a live shape changes, so drift shows up in the dispatch e2e or ledger IT runs, not in the agent tests. Re-record in the same change that alters a response.
- **Fixture churn.** Re-recording changes ids and timestamps in every file. Only re-record when a shape changes or a test asks for new data.
- **Python on the developer's Mac.** `python` exists only inside the activated venv; the gate runs the verification command with bash and the inherited `PATH` (Steps 4 and 7).
- **Network for `uv`.** PyPI downloads were unreliable from this Mac before (F11–F13); retry `uv sync`.
- **Ledger IT needs Docker** (Testcontainers), like every ledger IT.

## Deviations

Filled in during review: what changed from this plan, why, and in which commit.

- **`OrderEventKind` keys equal their values (plan correction before the work commit).** The first version declared `{Created = 'CREATED', StatusChanged = 'STATUS_CHANGED', DriverAssigned = 'DRIVER_ASSIGNED'}`. Codex found, before starting, that `@nestjs/graphql` emits enum **keys** on the wire, so the response would carry `Created`, `StatusChanged` and `DriverAssigned`. The agent's models accept only `CREATED`, `STATUS_CHANGED` and `DRIVER_ASSIGNED`, so A6 and A7 would fail. The enum now uses `CREATED`, `STATUS_CHANGED` and `DRIVER_ASSIGNED` as both key and value, every reference in Changes was renamed, and the new test D4b checks the wire spellings of both timeline enums against the live schema. `OrderEventActor` and the existing `OrderStatus` and `OrderPaymentStatus` already have keys equal to their values, so they are unaffected.
