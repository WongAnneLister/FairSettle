# F08 · Refund by capture id

## Goal

Behavior (copied from docs/features.json):

> Full and partial refunds are issued against the stored capture id, respect the ledger's refund reservation limit, and are idempotent on retry.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='PayPalRefundTest' test
```

`PayPalRefundTest` is a unit test: the adapter against `PayPalTestTransport`, plus the pure rules, with no Docker. The end-to-end refund paths also get an integration test, `PayPalRefundIT`, which runs under `./mvnw verify` and must pass before the work commit.

### The flow in one paragraph

`POST /v1/refunds` reserves the amount against the payment's refund control. This is existing code: it holds the payment and control locks and rejects anything over `captured − refunded − reserved` with `REFUND_LIMIT_EXCEEDED`. The reservation's `CreateRefundCommand` targets `payment.latest_charge_id`, which for PayPal is now the stored capture id. The worker (or `RefundExecutor.execute`) sends `POST /v2/payments/captures/{capture_id}/refund` with `PayPal-Request-Id` = the operation key (ADR D6), `custom_id` = the ledger refund id (ADR D12) and `Prefer: return=representation` (ADR D11). The response becomes a `RefundFact` and is merged by the existing `RefundWriteback` / `RefundFactMerger`, which settles the reservation exactly once. A `COMPLETED` refund with a `seller_payable_breakdown` is posted through the same settlement path F06 uses for captures (sales returns). A lost response is never resent (ADR D7). Recovery finds the refund through GET order by `custom_id`.

## Design decisions (fixed)

1. **The stored capture id is `payment.latest_charge_id`.**
   - F06 left it null for PayPal, because `PaymentStateMerger` takes it only from a payment intent.
   - New pure rule `PaymentEvidenceRules.latestChargeId(PaymentFacts facts, boolean stale)`:
     - with an intent: `intent.latestChargeId()` (Stripe, unchanged);
     - otherwise, for non-stale facts whose session is a PayPal order: the id of the single captured `succeeded` charge;
     - otherwise null.
   - `PaymentStateMerger` uses this rule. The SQL already does `coalesce(:latestChargeId, latest_charge_id)`.
   - The reservation then needs no change: `requireRefundable` already requires `latest_charge_id`, and `CreateRefundCommand.chargeId` = `latest_charge_id` = the capture id.
2. **`CreateRefundCommand` gains `currency` and `localRefundId`.** PayPal needs the currency for the decimal value and the ledger refund id for `custom_id`. `RefundIntentService.prepare` fills both. The record keeps a six-argument constructor (nulls) for existing callers, and Stripe ignores both fields. Commands stored earlier decode with nulls; the PayPal adapter refuses such a command with `IllegalArgumentException`. No PayPal refund existed before F08.
3. **PayPal refund statuses map raw** (ADR §7). `RefundFactRules.STATUSES` gains `COMPLETED`→`SUCCEEDED`, `PENDING`→`PENDING`, `FAILED`→`FAILED` and `CANCELLED`→`CANCELED`. `CANCELLED` is matched exactly, with two L. The raw value is stored as the refund's `provider_status` (existing `FactUpdate`).
4. **No automatic resend, ever (ADR D7).** `RefundExecutor.recover`, when the PayPal search port is present and there is no anchor, never calls `executeClaim` except for a `PREPARED` operation. It searches GET order `purchase_units[0].payments.refunds[]` by `custom_id` = the ledger refund id (ADR D12):
   - exactly one match: adopt it through `RefundWriteback.finish(..., query=true)`;
   - more than one: `conflictingAnchors` (freeze, CONFLICT, escalate);
   - none, or the GET failed: `finish` with a payload-less result. The refund stays `UNKNOWN`, the hold is kept, L1 backoff applies, and the existing age limit escalates it.

   With an anchor (a known PayPal refund id), recovery uses `queryRefund` as today.
5. **Over-refund freezes the control (ADR §7, refund.md §3).** A create rejected with `REFUND_AMOUNT_EXCEEDED` or `CAPTURE_FULLY_REFUNDED` still releases the hold and fails the refund (existing `rejectionReleasesHold` → `failRejected`). Additionally the control moves to `EXTERNAL_CONFLICT` (`freezeControlStamped`): PayPal knows a refund the ledger does not. Further reservations get `EVIDENCE_CONFLICT`. Stripe never returns these upper-case codes, so Stripe is unchanged.
6. **400 and any other 422 keep the hold.** The adapter classifies them `CONTRACT_MISMATCH`. The existing write-back then marks the refund `UNKNOWN` and keeps the hold. The custom-id search and the age limit then bring it to a person. ADR §7 says "resolution CONFLICT" for these rows; F08 leaves them `UNKNOWN` and escalates by age instead, so the existing write-back keeps one meaning per classification. The ADR row is updated (Changes, last entry). 403 → `CAPABILITY_UNAVAILABLE`, which has the same effect.
7. **Refund posting** reuses `CaptureSettlementService` unchanged.
   - `RefundFact` gains an optional trailing component `BalanceTransactionFact settlement`. It is non-null only for a `COMPLETED` PayPal refund with a `seller_payable_breakdown`, and then `RefundFact.balanceTransactionId` = the refund id.
   - The settlement fact:
     - `btId` = refund id, `type` `refund`;
     - `amountMinor` = −gross, `feeMinor` = −paypal_fee (missing → 0), `netMinor` = −net;
     - currency as given, `PAYMENTS`, source = refund id / `refund`, `status` `available`;
     - `createdAt` = refund `create_time`, `availableOn` null;
     - `feeDetails` = `[FeeDetail(−fee, currency, "paypal_fee", null)]` if fee > 0, else empty;
     - `rawDigest` = digest of `"paypal-refund|" + id + "|" + gross + "|" + fee + "|" + net`.
   - `BTJournalMapper`'s REFUND mapping then posts: SALES_RETURNS debit gross, PSP_FUNDS credit net, PSP_FEE_EXPENSE credit the returned fee.
   - `RefundExecutor` records the settlement after the write-back committed, exactly like `PaymentExecutor.postSettlements`. Failures leave it for the next query.
   - `CaptureSettlementConfiguration` already wires the `RefundEvidencePort` bean (`RefundFinancialEvidence`).
8. **The PayPal refund adapter is a separate class.** `PayPalRefundAdapter implements RefundPort, RefundSearchPort` (new port). It is built in `PayPalCheckoutConfiguration` with the same scope. `RefundExecutor` reports provider name `PAYPAL` when PayPal is enabled.
9. **Refund `chargeId` comes from PayPal's `up` link** (`…/v2/payments/captures/{id}`) on create and query. On create, a present `up` link must equal the command's capture id; when absent, the command's id is used. On query, the link is required. In the order search, every refund's `chargeId` is the order's single capture id.

### Refund call → classification (adapter)

`POST /v2/payments/captures/{captureId}/refund`. Headers `PayPal-Request-Id: <key>` and `Prefer: return=representation`. Body exactly `{"amount":{"currency_code":"<currency>","value":"<decimal>"},"custom_id":"<local refund id>"}`. The reason and note are not sent.

| `PayPalExchange` | Classification | Notes |
| --- | --- | --- |
| `Responded` 200/201, valid refund matching the command | SUCCESS + `RefundFact` | 201 sample 08, 200 replay sample 09 |
| `Responded` 200/201, invalid (rules below) | CONTRACT_MISMATCH `paypal_contract_mismatch` | |
| 422 `REFUND_AMOUNT_EXCEEDED` or `CAPTURE_FULLY_REFUNDED` | DEFINITIVE_REJECT, code = issue | sample 10 |
| 422 any other issue, or none | CONTRACT_MISMATCH, code = issue or null | decision 6 |
| 400 | CONTRACT_MISMATCH, code = `errorCode(body)` | decision 6 |
| 401, 409, 5xx | RETRYABLE_TRANSIENT | |
| 403 | CAPABILITY_UNAVAILABLE | |
| 404 | NOT_FOUND | |
| 429 | RATE_LIMITED | |
| any other status | CONTRACT_MISMATCH | |
| `NoResponse` | TIMEOUT_UNKNOWN, `idempotencyKeyUsed` = key | |
| `NotSent` | RETRYABLE_TRANSIENT, `idempotencyKeyUsed` null | |

**A valid refund body has:**

- `id` matching `[A-Z0-9]{1,36}`;
- `status` in {`COMPLETED`, `PENDING`, `FAILED`, `CANCELLED`};
- an `amount` convertible by `PayPalOrderMapping.minor`, positive. On create it must equal the command's amount and currency.
- On create, a `custom_id` equal to `localRefundId` when present.
- An `up` link per decision 9.
- For `COMPLETED`, if `seller_payable_breakdown` is present, a consistent breakdown:
  - all currencies equal;
  - gross = the refund amount;
  - gross − fee = net;
  - `create_time` present.

**Field mapping:**

- `failureReason` = `status_details.reason` if it matches `[A-Z0-9_]{1,64}`, else null.
- `failureBalanceTransactionId` null.
- `createdAt` = `create_time` (null if missing or unparsable, except as above).

**Evidence** follows F05–F07: `apiVersion` = `paypal-payments-v2`; `rawDigest` = digest of `"paypal-refund|" + id + "|" + status` for a fact, else the F05 error digest.

`queryRefund(scope, id)`: `GET /v2/payments/refunds/{id}`. It uses the same mapping, without the command checks, and requires the `up` link. Non-2xx statuses follow F05's query table.

`queryOrderRefunds(scope, orderId)`: `GET /v2/checkout/orders/{orderId}`.

- `purchase_units` must have exactly one unit.
- Each element of `purchase_units[0].payments.refunds[]` (missing → empty) maps to `OrderRefundFact(custom_id or null, RefundFact)` with `chargeId` = the single capture id.
- Refunds present but no capture, more than one capture, or any invalid refund → CONTRACT_MISMATCH.

  - In the anchor branch, keep `result` in a local and call `postSettlement(claim, result)` after `refunds.finish(...)`.
  - Directly after the `PREPARED` branch, and before the window logic: `if (search != null) { recoverBySearch(claim); return; }`. The window logic stays for Stripe and Fake.
- New:

```java
/** ADR §7 / D12: find the refund by custom_id; never resend. */
private void recoverBySearch(Claim claim)

/** Posts a refund settlement after its write-back committed; failures leave it for the next query. */
private void postSettlement(Claim claim, ProviderCallResult<RefundFact> result)
```

`recoverBySearch`:

1. `payment = operations.payment((UUID) claim.payment().get("payment_id"))`; `orderId = str(payment, "checkout_session_id")`; `refundId = claim.operation().get("refund_id").toString()`.
2. If `orderId == null`: `operations.escalate(claim, "REFUND_WITHOUT_ORDER")` and return.
3. Call `search.queryOrderRefunds(RefundRepository.scope(claim.payment()), orderId)`, wrapped like `call` (exceptions → TIMEOUT_UNKNOWN).
4. `matches` = the elements whose `customId` equals `refundId`.
5. Not SUCCESS, or no payload → `refunds.finish(claim, new ProviderCallResult<>(result.classification(), null, result.evidence()), true)`.
6. `matches.size() > 1` → `refunds.conflictingAnchors(claim)`.
7. `matches.size() == 1` → `refunds.finish(claim, new ProviderCallResult<>(SUCCESS, match.refund(), result.evidence()), true)`, then `postSettlement` with that result.
8. Zero matches → `refunds.finish(claim, new ProviderCallResult<>(TRANSIENT_EMPTY, null, result.evidence()), true)`.

`postSettlement`:

1. Return if `settlements == null`, if `result.payload()` is null, or if `result.payload().settlement()` is null.
2. Call `settlements.record(RefundRepository.scope(claim.payment()), result.payload().settlement(), result.evidence())` inside `try`, ignoring `RuntimeException`. No logging.

## Out of scope

- **Refund webhooks.** `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.REFUND.*`: F09/F10.
- **Liability splits** and their postings: F14/F17.
- **Refund cancel.** It is not offered.
- **External refunds discovered only through the order search** (elements with another or no `custom_id`). They are ignored by F08's recovery; external refund ingestion follows the existing webhook/query paths later.
- **Changing the reservation limit rules**, `RefundReservationRules` or `RefundIntentService` beyond the command fields.
- **Files that do not change:**
  - `financialingestion` (all files), `CaptureSettlementService`, `CaptureSettlementConfiguration`;
  - migrations, the Stripe and Fake adapters, `PayPalCheckoutAdapter`;
  - `contracts/` and `openapi.yaml` (`POST /v1/refunds` is unchanged), `dispatch/`, `agent/`, and the off-limits modules.

## Risks

- **`seller_payable_breakdown` and the `up` link in the real sandbox.** Sample 08 is a minimal response without amount; F08 requires the representation (D11). If the real response omits the amount, every refund is CONTRACT_MISMATCH: the hold is kept and a person investigates. F12 checks the real shape; if it differs, stop and replan rather than loosen the checks.
- **`custom_id` on refunds inside GET order** (ADR D12) is documented, not observed. If it is missing, recovery finds no match, and the refund escalates at the age limit with its hold kept. That is safe, but slower.
- **Payments captured before F08** have `latest_charge_id` null. The next query fills it, through the `coalesce`. The only such rows are local test data.
- **`CreateRefundCommand` / `RefundFact` shape.** The added components have old-arity constructors. Stored Stripe commands decode with nulls. Run the whole unit suite and `./mvnw verify` (Stripe and Fake refund ITs) to catch leftovers.
- **Refund posting needs the account's ingestion policy and the SALES_RETURNS account**, as F06's capture posting does. Without them the BT stays `PENDING_EVIDENCE`, and L2 keeps waking the refund until it posts.
- **Docker.** `PayPalRefundIT` runs under `./mvnw verify` on the VPS. Sync `ledger/` and `docs/adr/paypal-samples/` (tests 5 and 36 read sample 10), and strip CRLF from `mvnw`.
