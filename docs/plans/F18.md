# F18 · Refund proposal API and review

## Goal

Behavior (copied from docs/features.json):

> POST refund proposal (idempotent on complaint id) enters the existing review queue; approval executes the refund with its liability split in one transaction; rejection changes nothing.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='RefundProposalApiTest' test
```

F18 implements the five F14 contract operations F17 did not:

| # | Operation | Who |
| --- | --- | --- |
| 2 | `GET /v1/payments/{paymentId}/refundable` | agent (application) |
| 3 | `POST /v1/refund-proposals` | agent |
| 4 | `GET /v1/refund-proposals/{proposalId}` | agent |
| 7 | `GET /ops/refund-proposals` | ops viewer and above |
| 8 | `POST /ops/refund-proposals/{proposalId}/decision` | ops reviewer only |

`contracts/ledger-openapi.yaml` is the specification: field names, status codes, error codes and the validation table in op 3's description. Where this plan and the contract disagree, the contract wins; stop and report.

The agent never moves money. It proposes; a person approves. Approval creates the refund through the existing reservation, so the worker sends it to PayPal like any refund. F22 and F23 build on this.

## Design decisions (fixed)

1. **New package `com.paymentsledger.proposal`**, with `proposal.domain` (pure rules) and `proposal.repository` (all SQL). The liability split, refund reservation and audit are reused, not copied.
2. **Proposals are their own review queue.** The contract's `/ops/refund-proposals` endpoints are the queue; the ops adjustment queue (`ops_adjustment`) is not used. The feature text's "existing review queue" is the ops review surface: same ops identities, roles, audit log and approval semantics (conditional update, idempotent replay).
3. **Ops authorization is role-based.** The contract's OpsBearer scopes map onto roles, because `OpsContext` carries a role, not scopes:
   - `ops:refund-proposal:read` → `OpsAuthorization.read(c, false)` (`OPS_VIEWER`, `OPS_OPERATOR`, `OPS_REVIEWER`, `OPS_ADMIN`; not `PARTNER_VIEWER`);
   - `ops:refund-proposal:review` → `OpsAuthorization.write(c, "DECIDE_REFUND_PROPOSAL")`, which allows `OPS_REVIEWER` only, exactly like `APPROVE_ADJUSTMENT`.
4. **Application scopes.** `refund-proposals:write` (op 3) and `refund-proposals:read` (op 4) are new. `application_credential.granted_scopes` has a CHECK that allows only the four existing scopes; V20 replaces it with one allowing six. Op 2 uses the existing `payments:read`.
5. **Proposal storage: one row per proposal**, `platform.refund_proposal` (Changes, V20).
   - The submitted content is immutable.
   - The review result is written once.
   - Idempotency for both POSTs is stored on the row itself, not in `api_idempotency_record`:
     - the creation key and fingerprint;
     - the decision key and fingerprint.
6. **Creation (op 3)**, in one transaction:
   1. Scope `refund-proposals:write` (else `403`). `PaymentRequests.idempotencyKey(key)` (missing → `400 IDEMPOTENCY_KEY_REQUIRED`; malformed → `400 VALIDATION_ERROR`).
   2. Parse the body (decision 8). Failures give `400 VALIDATION_ERROR` or `422 LIABILITY_SPLIT_INVALID`.
   3. Advisory lock `lockKey(tenant, "REFUND_PROPOSAL", key)`, then advisory lock `lockKey(tenant, "REFUND_PROPOSAL_COMPLAINT", complaintId)`, always in this order.
   4. A row with this application and key exists: same fingerprint → replay (`200`, `Idempotent-Replay: true`, the stored proposal); different fingerprint → `409 IDEMPOTENCY_CONFLICT`.
   5. A row with this application and complaint exists → `409 PROPOSAL_EXISTS`, details `[{field: "complaintId", issue: "<prop_… id>"}]`.
   6. Read the payment (no lock) in the caller's organization, environment, application and provider account. Absent, or its currency not in `allowedCurrencies` → `404 NOT_FOUND`.
   7. Request currency differs from the payment's → `400 VALIDATION_ERROR` with details `[{field: "currency", issue: "must equal the payment currency"}]`.
   8. `RefundReservationRules.requireRefundable(tenant, payment, currency)` (conflict → `409 EVIDENCE_CONFLICT`; nothing captured or no charge → `409 REFUND_BLOCKED`).
   9. Read the refund control (no lock). If it has no row yet: captured = the payment's captured amount, refunded 0, reserved 0, `NORMAL`. State not `NORMAL` → `409 REFUND_BLOCKED`. `amountMinor` > `max(0, captured − refunded − reserved)` → `422 REFUND_LIMIT_EXCEEDED`.
   10. Insert the row with `status = PENDING_REVIEW`. Return `201`, `Location: /v1/refund-proposals/<prop_ id>`.

   Nothing is reserved. Creation writes no refund, control or liability row.
7. **Approval and rejection (op 8)**, in one transaction:
   1. `OpsAuthorization.write(c, "DECIDE_REFUND_PROPOSAL")` (not `OPS_REVIEWER` → `403`; no identity → `401`). `PaymentRequests.idempotencyKey(key)`.
   2. Parse the body (decision 8).
   3. Lock the proposal row: `SELECT … FOR UPDATE` in the ops organization and environment. Absent → `404 NOT_FOUND`.
   4. **The key belongs to another proposal** (added by review fix RF-3): another proposal in this organization and environment already stores this decision key → `409 IDEMPOTENCY_CONFLICT`, whatever this proposal's status.

      **Already decided:**
      - same decision key with a different decision fingerprint → `409 IDEMPOTENCY_CONFLICT`;
      - otherwise the same `action` as stored → replay: `200`, `Idempotent-Replay: true`, the current proposal, nothing written except the audit row;
      - otherwise → `409 PROPOSAL_NOT_PENDING`.
   5. **`REJECT`:** set `REJECTED`, reviewer, `reviewed_at = now()`, `rejection_reason`, decision key and fingerprint. Nothing else changes.
   6. **`APPROVE`:**
      1. Recheck without locks (decision 6 step 9) against the current control: not `NORMAL` → `409 REFUND_BLOCKED`; amount above what is available → `422 REFUND_LIMIT_EXCEEDED`.
      2. Build the proposal's application context: `new TenantContext(org, env, app, providerAccount, Set.of(currency), false, Set.of("refunds:write"))`.
      3. `refunds.prepare(context, "proposal-refund:" + proposalUuid, new RefundRequests.Create(paymentId, amountMinor, currency, "REQUESTED_BY_CUSTOMER", "Refund proposal " + prop_id, "proposal:" + proposalUuid), provider)`. It locks and rechecks again (authoritative), and reserves.
      4. `liability.record(intent.refundId(), proposalUuid, split)`.
      5. Set `APPROVED`, reviewer, `reviewed_at`, `refund_id`, decision key and fingerprint.
   7. Audit inside the transaction: `audit.recordInTransaction(c, "DECIDE_REFUND_PROPOSAL", prop_id, body, result, before, after)`. `result` is `APPROVED`, `REJECTED` or `REPLAYED`; `before` and `after` are `{status}` objects.
   8. Return the proposal resource (decision 9), `200`.

   Any exception rolls the whole transaction back: the proposal stays `PENDING_REVIEW`, and no refund, reservation, allocation or success audit remains. The controller records failures with `audit.record` (decision 12). Lock order: proposal (rank 15), then the reservation's advisory lock, payment (20), control (30) and share allocations (50), then `refund_liability` (55).
8. **Request parsing** (`ProposalRequests`, strict like `RefundRequests`).
   - **Create body.** The object must hold exactly the contract's fields: the 11 required fields; `agentRun.traceId` is the only optional field.
     - `400 VALIDATION_ERROR` for:
       - a non-object body, or a missing or unknown field (also inside `agentRun` and inside a liability item);
       - `complaintId` not matching `^[A-Za-z0-9._:-]{1,128}$`;
       - `orderRef` not 1–64 characters;
       - `paymentId` not a valid `pay_` id;
       - `decision`, `reasonCode` or a `party` not in its enum;
       - `amountMinor` not an integral number ≥ 1 (`1.5` included);
       - `currency` not `[A-Z]{3}`;
       - `liability` not an array of exactly 3 objects;
       - a `basisPoints` value that is not an integer in 0..10000;
       - `explanation` not 1–2000 characters;
       - `evidenceRefs` not an array of 1–50 strings of 1–128 characters;
       - `threadId` or `traceId` not 1–128 characters.

       Text fields reject ISO control characters, except that `explanation` may contain `\n`.
     - **Shape valid but the split is not**: a party repeated or missing, or shares not summing to 10000 → `422 LIABILITY_SPLIT_INVALID`, via `LiabilitySplit.of`.
   - **Decision body.**
     - Allowed: `{"action":"APPROVE"}` or `{"action":"REJECT","reason":"…"}`, with `reason` 1–500 characters and no control characters.
     - `400 VALIDATION_ERROR` for: anything else, including `APPROVE` with a `reason`, `REJECT` without one, and unknown fields.
   - **Fingerprints** are SHA-256 hex of a Jackson-serialized list, like `RefundRequests.Create.fingerprint`:
     - create: `["REFUND_PROPOSAL_V1", complaintId, orderRef, paymentUuid, decision, amountMinor, currency, reasonCode, restaurantBp, driverBp, platformBp, explanation, evidenceRefs, threadId, traceId]`. Shares are taken by party, so the order of the liability items does not matter;
     - decision: `["PROPOSAL_DECISION_V1", action, reason]`.
9. **The proposal resource** (`ProposalResources`), an `ObjectNode` in exactly this field order:

   | Field | Value |
   | --- | --- |
   | `complaintId`, `orderRef` | stored text |
   | `paymentId` | `pay_…` |
   | `decision` | stored enum |
   | `amountMinor` | number |
   | `currency` | stored text |
   | `reasonCode` | stored enum |
   | `liability` | three `{party, basisPoints}` in the order `RESTAURANT`, `DRIVER`, `PLATFORM` |
   | `explanation` | stored text |
   | `evidenceRefs` | array in submitted order |
   | `agentRun` | `{threadId}`, plus `traceId` when stored |
   | `id` | `prop_…` |
   | `status` | stored status |
   | `createdAt` | ISO-8601 instant |
   | `reviewedAt` | instant or `null` |
   | `reviewer` | `{subject, role}` or `null` |
   | `rejectionReason` | text or `null` |
   | `refundId` | `ref_…` or `null` |
   | `allocation` | for `APPROVED`, the F17 `LiabilityAllocation` resource from `liability.read(…)`, called with the proposal's application context and scope `refunds:read`, with `journalId` written explicitly as `null` when pending; otherwise `null` |

   Every `null` is written with `putNull`. Tests assert that the key is present and holds JSON null.
10. **Refundable amount (op 2).**
    - Scope `payments:read`. The payment must be scoped as in decision 6 step 6, else `404`.
    - Control values as in decision 6 step 9.
    - `refundableMinor` is `max(0, captured − refunded − reserved)` when `NORMAL`, else 0.
    - Body fields in order: `paymentId`, `currency`, `capturedMinor`, `refundedMinor`, `reservedMinor`, `refundableMinor`, `controlState`.
11. **Ops list (op 7).**
    - Query parameters:
      - `status`: default `PENDING_REVIEW`; must be one of the three statuses, else `400 VALIDATION_ERROR`;
      - `limit`: default 50, 1..200, else `400`;
      - `cursor`: optional.
    - Rows: the ops organization and environment, the given status, ordered by `id` ascending. Proposal ids come from `PaymentIds.newId()`, which is time-ordered, so the oldest come first.
    - Fetch `limit + 1` rows.
    - The cursor is base64url (no padding) of `refund-proposals|<org>|<env>|<status>|<last id>`. A cursor that does not decode or does not match → `400 VALIDATION_ERROR`.
    - Body: `{items, nextCursor}`, with `nextCursor` written as `null` on the last page.
12. **HTTP layer.**
    - **Application routes** in `RefundProposalController`:
      - `POST /v1/refund-proposals`;
      - `GET /v1/refund-proposals/{id}` (id parsed with `PaymentIds.parse("prop", …)`);
      - `GET /v1/payments/{id}/refundable`.
    - **Ops routes** in `OpsRefundProposalController`:
      - `GET /ops/refund-proposals`;
      - `POST /ops/refund-proposals/{id}/decision` (id via `OpsAuthorization.resourceId(id, "prop")`). On a `RuntimeException` it calls `audit.record(c, "DECIDE_REFUND_PROPOSAL", target, body, 403 ? "DENIED" : "REJECTED")`, sets the `ops.audited` request attribute (also on success), and rethrows. Same as `OpsController.command`.
    - Both controllers are `@Profile("api")`.
13. **The provider name** for `prepare` comes from `RefundExecutor.providerName()`, which becomes `public`. `RefundProposalConfiguration` reads it lazily (`ObjectProvider<RefundExecutor>`), because the executor exists only where a refund port does.
14. **Link to F17.** An `APPROVED` proposal must have exactly one `refund_liability` row with its `refund_id` and `proposal_id`. A deferred constraint trigger checks this at commit. F17's plan expected F18 to add a foreign key `refund_liability.proposal_id → refund_proposal(id)`. That is **not** added: F17's merged tests record allocations with made-up proposal ids, and the deferred trigger enforces the same link from the proposal side.
15. **Local fixtures for the demo.** `LocalFixtureInitializer`:
    - grants the local application credential the two new scopes;
    - adds an `OPS_REVIEWER` identity (`local-reviewer`) with a credential that uses the same local ops secret. Without it, a local run cannot approve.

```java
public final class ProposalRules {
    public enum Replay { REPLAY, CONFLICT, NOT_PENDING }
    public record Refundable(long capturedMinor, long refundedMinor, long reservedMinor, String controlState) {
        public long refundableMinor();      // NORMAL ? max(0, c − r − h) : 0
    }
    public static void requireProposable(Refundable refundable, long amountMinor);
    public static Replay decided(String storedAction, String storedKey, String storedFingerprint,

}
```

## Risks

- **Two rechecks.** Approval prechecks without locks to return the contract's codes, then `prepare` rechecks under lock. If the control changes in between, `prepare` may answer `409 EVIDENCE_CONFLICT` (`EXTERNAL_CONFLICT` control) instead of `REFUND_BLOCKED`. The proposal still stays pending. Recorded, not handled.
- **Refund idempotency key.** `proposal-refund:<…>` lives in the application's `CREATE_REFUND` key space. The first version of this plan said the application could not know the proposal's UUID. - **Payment conflict.** A payment whose resolution is `CONFLICT` makes creation and approval fail with `409 EVIDENCE_CONFLICT` (`requireRefundable`). The contract's tables do not list this code for these operations. It is the ledger's existing behaviour and is kept.
- **Fixture secret reuse.** The local reviewer shares the local ops secret (decision 15). This is acceptable only in the `local` profile, which `LocalFixtureInitializer` already requires.
- **Migration counts.** Eight tests move by one again. That is mechanical and authorized above.

  - `"proposal-refund:" + p.refundKey()` as the idempotency key;
  - `"proposal:" + p.refundKey()` as the `clientRefundKey`.
