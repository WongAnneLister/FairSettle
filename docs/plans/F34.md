# F34 · Settled payment recovery finishes

## Goal

Behavior (copied from docs/features.json):

> After a payment is settled with certainty, its CREATE_CHECKOUT recovery task finishes, and a provider read that brings no evidence no longer downgrades it to UNKNOWN, so a settled payment is never polled forever or escalated by the unresolved-age limit (KI-6).

Verification (copied from docs/features.json, `kind: command`):

```bash
cd ledger && ./mvnw -q -Dtest='OperationLeaseRulesTest,PaymentStateMachinePayPalTest,PaymentEvidenceRulesTest' -Dit.test='PayPalCaptureIT,OperationRecoveryIT' verify
```

This fixes `docs/known-issues.md` KI-6, which was found in the F33 live check. Two defects combine:

1. `OperationLeaseRules.paymentTaskDone` has no rule that ends a `CREATE_CHECKOUT` task whose payment succeeded with certainty. The create task of every paid checkout stays `WAITING` and re-queries the provider about every two minutes, forever.
2. `PaymentEvidenceRules.decide` turns any incomplete read into `resolution = UNKNOWN`, even when the read brought no evidence at all and the payment was already settled (`SUCCEEDED` or `CANCELED`, `KNOWN`). If an hour passes without a successful read, the operation is escalated with `UNRESOLVED_AGE_LIMIT` and the payment stays `UNKNOWN` for good.

### Decisions (user, 2026-11-01)

1. **Fix both defects** in this feature (A: the create task finishes; B: a read with no evidence keeps a settled payment's resolution).
2. **Verified by a command** (unit tests plus `PayPalCaptureIT` and `OperationRecoveryIT`), no live run.
3. **The F24 payment `7KR80011U08627743` is out of scope.** It stays `ESCALATED`/`UNKNOWN` in the local live database; clearing it would need a separate ops tool. KI-6 keeps a note.

Planner decisions (no user choice needed):

- Fix B is deliberately narrow. Partial or inconsistent evidence still downgrades, and payments that are not settled keep today's behaviour.
- The two existing assertions that pin the bug change on purpose (see Tests). One of them is in F06's verification test class; F06's verification command is unchanged and still passes.
- A new ADR decision D13 records the rule.

## Changes

### `ledger/src/main/java/com/paymentsledger/payment/domain/OperationLeaseRules.java` (modified)

`paymentTaskDone` becomes:

```java
    /**
     * A task finishes once acknowledged, canceled with certainty, its cancel resolved, or its create or capture resolved
     * a payment that succeeded with certainty (F06, F34).
     */
    public static boolean paymentTaskDone(
            String operationStatus, String operationType, String paymentStatus, String paymentResolution) {
        return "ACKNOWLEDGED".equals(operationStatus)
                || "CANCELED".equals(paymentStatus) && "KNOWN".equals(paymentResolution)
                || "CANCEL_PAYMENT".equals(operationType) && "RESOLVED".equals(operationStatus)
                || ("CAPTURE_ORDER".equals(operationType) || "CREATE_CHECKOUT".equals(operationType))
                        && "RESOLVED".equals(operationStatus)
                        && "SUCCEEDED".equals(paymentStatus)
                        && "KNOWN".equals(paymentResolution);
    }
```

Unposted money is still found: L2 wakes tasks of payments whose `financial_status` is `PENDING_EVIDENCE` even when they are `DONE`.

### `ledger/src/main/java/com/paymentsledger/payment/domain/PaymentEvidenceRules.java` (modified)

Add, after `capturable`:

```java
    /** A read that brought no evidence at all: no session, intent, charge or settlement, and no conflict (F34). */
    public static boolean noEvidence(PaymentFacts facts) {
        return facts.session() == null
                && facts.intent() == null
                && facts.charges().isEmpty()
                && facts.settlements().isEmpty()
                && !facts.conflict();
    }

    /** ADR D13: a read without evidence cannot make a payment that is settled with certainty uncertain again. */
    public static boolean keepsSettledResolution(PaymentSnapshot payment, PaymentFacts facts) {
        return noEvidence(facts)
                && payment.resolution() == ResolutionStatus.KNOWN
                && (payment.status() == PaymentStatus.SUCCEEDED || payment.status() == PaymentStatus.CANCELED);
    }
```

In `decide`, the resolution expression becomes:

```java
        ResolutionStatus resolution = conflict
                ? ResolutionStatus.CONFLICT
                : stale
                        ? payment.resolution()
                        : facts.complete()
                                ? ResolutionStatus.KNOWN
                                : keepsSettledResolution(payment, facts) ? payment.resolution() : ResolutionStatus.UNKNOWN;
```

Nothing else in `decide` changes. `payment` is the snapshot before this observation, which is what "already settled" means. Run `./mvnw spotless:apply` and keep its formatting.

### `docs/adr/paypal-state-mapping.md` (modified)

After D12, add:

> - **D13 A settled payment stays settled (F34).** A provider read that brings no evidence at all (a timeout or no response) leaves a payment that is `SUCCEEDED` or `CANCELED` with `resolution_status=KNOWN` unchanged, instead of making it `UNKNOWN`. ## Risks

- **Other tests may rely on a settled payment turning `UNKNOWN` after a failed read.** The step 6 full `./mvnw verify` covers this. If any other test fails, stop and report it with the test name and assertion. Do not change it.
- **`merge` now returns true for a failed read on a settled payment.** This completes the operation `RESOLVED` and, with Fix A, the task `DONE`. The side effects were checked (What was checked). If a test shows a capture being prepared or settlements posted from empty facts, stop and report.
- **A Stripe checkout's create task now finishes when the payment succeeds with certainty.** Posting that is still pending is woken by L2 (`PENDING_EVIDENCE`), as for PayPal captures since F06.
- **Tasks already `WAITING` in an existing database** heal on their next successful query. Escalated ones do not (KI-6 Resolution).
