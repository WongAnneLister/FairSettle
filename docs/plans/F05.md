# F05 · Create PayPal order

## Goal

Behavior (copied from docs/features.json):

> POST /v1/payments with provider=paypal creates an Orders v2 order with a PayPal-Request-Id derived from the ledger operation; a retry with the same Idempotency-Key returns the same order and never creates a second one.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='PayPalCreateOrderTest' test
```

`PayPalCreateOrderTest` is a unit test (no Docker). The end-to-end idempotency behavior also gets an integration test, `PayPalCreateOrderIT`, which runs under `./mvnw verify` and must pass before the feature is committed (step 4).

### How "provider=paypal" is read

The ledger does not take a provider in the request body: `PaymentRequests` rejects unknown fields, and an application charges through the single `provider_account` it is bound to (`TenantContext.allowedProviderAccountId()`, `PaymentIntentRules.requireBinding`). "provider=paypal" therefore means: **the application's bound provider account has `provider='PAYPAL'`, and the deployment runs the PayPal adapter.** The request and response of `POST /v1/payments` do not change, so `contracts/` and `ledger/docs/contracts/openapi.yaml` are not touched. The PayPal order id appears where the Stripe Checkout session id appears today (`provider.checkoutSessionId` in the response, `payment.checkout_session_id` in the database).

## Design decisions (fixed)

1. **PayPal implements the existing `CheckoutPort`.** No new port, no new operation type: order creation is `CREATE_CHECKOUT` (ADR D5). `PaymentExecutor`, `ProviderResults`, recovery and idempotency are reused unchanged.
2. **One provider per deployment.** `platform.paypal.enabled=true` together with `platform.stripe.enabled=true` or `platform.provider.fake.enabled=true` fails startup. `PaymentExecutor` reports provider name `PAYPAL` when PayPal is enabled. `RefundExecutor` is not changed: refunds are unavailable under PayPal until F08.
3. **Deployment binding generalized.** The record `StripeDeployment` is renamed to `ProviderDeployment` (same four fields). The binding checks that apply to `STRIPE` today apply to `PAYPAL` too. For PayPal, `accountId` is the sandbox REST app's **client id**, and the provider account row's `provider_account_ref` must equal it. The client id is public (it ships in PayPal's browser SDK); the secret is never stored.
4. **`PayPal-Request-Id` = `command.operationIdempotencyKey()`** (`pay_create_<operation uuid>`, 47 characters). Sent on every create attempt, including recovery resends; never regenerated.
5. **Order body** (exact; no other fields):

   ```json
   {
     "intent": "CAPTURE",
     "purchase_units": [{
       "reference_id": "<payment_id>",
       "custom_id": "<payment_id>",
       "amount": {"currency_code": "<currency>", "value": "<decimal>"}
     }],
     "payment_source": {"paypal": {"experience_context": {
       "return_url": "<successUrl>",
       "cancel_url": "<cancelUrl>",
       "user_action": "PAY_NOW",
       "shipping_preference": "NO_SHIPPING"
     }}}
   }
   ```

   `payment_id` comes from `command.sessionMetadata().get("payment_id")`. Merchant metadata is **not** sent to PayPal (Orders v2 has no metadata map); it stays in the ledger.
6. **Headers:** `PayPal-Request-Id: <key>`, `Prefer: return=representation` (ADR D11). `Content-Type`, `Accept` and `Authorization` are set by `PayPalAuthClient`.
7. **Order → `CheckoutSessionFact`:** `sessionId` = order `id`; `status` from the table below; `hostedUrl` = the `href` of link `rel=payer-action`, else `rel=approve`; `paymentIntentId` = null; `paymentStatus` = the raw order status (ADR D3); `metadata` = `{"payment_id": purchase_units[0].custom_id}`; `expiresAt` = `command.expiresAt()` on create, and `create_time + PaymentIntentRules.CHECKOUT_LIFETIME_SECONDS` (truncated to seconds) on query. PayPal orders carry no expiry; the ledger's checkout expiry is local.

   | Order status | `CheckoutSessionStatus` |
   | --- | --- |
   | `CREATED`, `PAYER_ACTION_REQUIRED` | OPEN |
   | `APPROVED`, `COMPLETED` | COMPLETE |
   | `VOIDED` | EXPIRED |
   | `SAVED`, anything else | CONTRACT_MISMATCH, no payload |

8. **`provider_status` holds the raw PayPal order status (ADR D3).** `PaymentEvidenceRules.sessionStatus(fact)` returns `fact.paymentStatus()` when it is one of the six PayPal order statuses, and otherwise the existing lowercase session status. Stripe's `paymentStatus` values (`unpaid`, `paid`, `no_payment_required`) are lowercase and never match, so Stripe behavior is unchanged. This also makes ADR D2 hold for F06: an APPROVED order merges as PROCESSING with `provider_status='APPROVED'`.
9. **Resend window:** `RecoveryPolicy.verifiedWindow("PAYPAL")` = 5 hours (ADR D7). The existing `retry_until` horizon still applies, so the effective create window is the shorter one.
10. **`expireSession` is not supported:** Orders v2 has no void for `intent=CAPTURE` orders. It returns `CAPABILITY_UNAVAILABLE` without a call. Payment cancel under PayPal is outside M1.
11. **Hosted URL must be a sandbox URL:** it must start with `https://www.sandbox.paypal.com/`. Otherwise the result is `CONTRACT_MISMATCH`.

### Call outcome → classification (create and query)

| `PayPalExchange` | Classification | Evidence |
| --- | --- | --- |
| `Responded` 200/201, valid order | SUCCESS + fact | `httpStatus`, `providerRequestId` = debug id |
| `Responded` 200/201, invalid order (not JSON, missing `id`, unknown status, open without sandbox link, missing `custom_id`; on query also missing `create_time`) | CONTRACT_MISMATCH | `providerErrorCode = "paypal_contract_mismatch"` |
| 400, 422 | DEFINITIVE_REJECT | `providerErrorCode` = first `details[].issue`, else `name`, else null |
| 401 (already retried once by F04) | RETRYABLE_TRANSIENT | |
| 403 | CAPABILITY_UNAVAILABLE | |
| 404 | NOT_FOUND | |
| 409 | RETRYABLE_TRANSIENT | |
| 429 | RATE_LIMITED | |
| 5xx | RETRYABLE_TRANSIENT | |
| any other status (1xx, 3xx, other 2xx, other 4xx) | CONTRACT_MISMATCH | |
| `NoResponse` | TIMEOUT_UNKNOWN | `httpStatus` and `respondedAt` null |
| `NotSent` | RETRYABLE_TRANSIENT | `idempotencyKeyUsed` null (nothing was sent), `providerErrorCode` = the `NotSent` reason |

Every result carries `ProviderEvidence(providerRequestId=debugId or null, idempotencyKeyUsed=key on create when sent / null on query, requestedAt, respondedAt, httpStatus, providerErrorCode, rawDigest, apiVersion="paypal-orders-v2")`. `rawDigest` = lowercase hex SHA-256 of `"paypal-order|" + id + "|" + status` for a fact, or `"paypal-error|" + httpStatus + "|" + errorCode` otherwise. It never covers payer data, links or the raw body. Error codes are kept only if they match `[A-Z0-9_]{1,64}`, otherwise null.

### `provider/adapter/paypal/PayPalOrderMapping.java` (new)

```java
final class PayPalOrderMapping {
    static final String API_VERSION = "paypal-orders-v2";
    static final String SANDBOX_CHECKOUT_PREFIX = "https://www.sandbox.paypal.com/";
    static final Set<String> ORDER_STATUSES =
            Set.of("CREATED", "SAVED", "APPROVED", "VOIDED", "COMPLETED", "PAYER_ACTION_REQUIRED");

    /** Exact decimal string for PayPal; 0 or 2 fraction digits (java.util.Currency); otherwise IllegalArgumentException. */
    static String value(long amountMinor, String currency)
    /** The JSON body of decision 5, serialized with Jackson; field order as shown. */
    static String createBody(CreateCheckoutSessionCommand command, String paymentId)
    /** Maps a 200/201 order body; empty Optional means CONTRACT_MISMATCH. */
    static Optional<CheckoutSessionFact> fact(JsonNode order, Instant expiresAt)
    /** create_time + CHECKOUT_LIFETIME_SECONDS, truncated to seconds; empty if create_time is missing or unparsable. */
    static Optional<Instant> queryExpiry(JsonNode order)
    /** Decision table above. */
    static ProviderCallClassification classify(int status)
    /** First details[].issue, else name, else null; only if it matches [A-Z0-9_]{1,64}. */
    static String errorCode(String body)
    static String digest(String text)   // lowercase hex SHA-256 of UTF-8
}
```

`fact(...)` returns empty when: `id` is missing or blank; `status` is missing, not a string, or not in the session-status table (including `SAVED`). Check for null before any `Set.of(...).contains`, which throws on null; `purchase_units[0].custom_id` is missing or blank; or the status maps to OPEN and no `payer-action`/`approve` link starts with `SANDBOX_CHECKOUT_PREFIX`. When both links exist, `payer-action` wins.

### `provider/adapter/paypal/PayPalCheckoutAdapter.java` (new)

```java
public final class PayPalCheckoutAdapter implements CheckoutPort {
    public PayPalCheckoutAdapter(PayPalAuthClient client, ProviderScope scope, Clock clock)
    @Override public ProviderCallResult<CheckoutSessionFact> createSession(CreateCheckoutSessionCommand command)
    @Override public ProviderCallResult<CheckoutSessionFact> querySession(ProviderScope scope, String sessionId)
    @Override public ProviderCallResult<CheckoutSessionFact> expireSession(ProviderScope scope, String sessionId)
}
```

- Constructor: `scope.livemode()` → `IllegalArgumentException("Live scope is unsupported")`; null arguments → NPE via `Objects.requireNonNull`.
- `createSession`:
  1. `command.scope()` must equal the bound scope, else `IllegalArgumentException("Provider scope differs from credential binding")`.
  2. `payment_id` metadata must be a UUID string, else `IllegalArgumentException("payment_id metadata is required")`.
  3. `PayPalOrderMapping.value` must succeed.
  4. Then `client.exchange(PayPalHttpRequest.post("/v2/checkout/orders", Map.of("PayPal-Request-Id", key, "Prefer", "return=representation"), createBody(...)))`.
  5. Map the result per the classification table, and the fact with `expiresAt = command.expiresAt()`.
  6. `requestedAt` = clock before the call; `respondedAt` = clock after a `Responded`, else null.
- `querySession`:
  1. Scope check as above.
  2. `sessionId` must match `[A-Z0-9]{1,36}`, else `IllegalArgumentException`, no call.
  3. Then `exchange(get("/v2/checkout/orders/" + sessionId, Map.of()))`, with expiry from `queryExpiry` (missing → CONTRACT_MISMATCH).
  4. `idempotencyKeyUsed` is null.
- `expireSession`: scope check, then `CAPABILITY_UNAVAILABLE` with `providerErrorCode = "paypal_order_void_unsupported"`, `requestedAt = clock.instant()`, no call.
- No logging. No raw body, payer data or links in any returned value except the hosted URL inside the fact.

## Out of scope

- Capture, approval handling, `CAPTURE_ORDER` migration: F06. Capture timeout: F07. Refunds and `RefundExecutor`: F08. Webhooks: F09/F10.
- `ProviderResultRules.sessionAnchor` only accepts operation external ids starting with `cs_` (Stripe). A PayPal create timeout has no external id, so F05 is unaffected; F07 must handle it. Do not change it here.
- Local fixtures for a PAYPAL provider account (`LocalFixtureInitializer`) and compose configuration: F12/F13.
- Payment cancel under PayPal (`expireSession` returns unsupported).
- No changes to `contracts/`, `dispatch/`, `agent/`, the Stripe or Fake adapters, `PayPalAuthClient`, `PayPalAdapterConfiguration`, or the off-limits ledger modules.

## Risks

- **`custom_id` echo.** The adapter requires `purchase_units[0].custom_id` in the create response. PayPal's spec includes it in the representation, but the F02 sample used a minimal response. If the real sandbox omits it, every create is CONTRACT_MISMATCH. F12 confirms it against the sandbox; until then the unit fixtures follow the spec. If it turns out to be missing, stop and replan; do not drop the check.
- **Create window.** 5 h is documented, not measured. The existing `retry_until` horizon shortens it further. Test 23 pins that nothing is resent after the window.
- **Constraint name in V17.** Postgres naming is deterministic for inline checks. If it fails, stop (see the V17 section).
- **Rename blast radius.** `StripeDeployment` → `ProviderDeployment` touches 6 main files and 1 test. It is mechanical; run the whole unit suite and `./mvnw verify` to catch leftovers.
- **`sessionStatus` change and Stripe.** The PayPal set is uppercase and disjoint from Stripe's lowercase payment statuses. Test 18 pins both, and the existing Stripe ITs run in step 4.
- **Docker.** `PayPalCreateOrderIT` needs Docker. If Docker is not running, stop at step 4 and say so; do not skip the IT.
