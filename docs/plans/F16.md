# F16 · Payment result drives order state

## Goal

Behavior (copied from docs/features.json):

> Ledger merchant notifications mark the order paid or failed through the existing order state machine; duplicates and out-of-order notifications are ignored.

Verification (copied from docs/features.json):

```bash
cd dispatch && npm run test:e2e -- --testPathPattern=payment-notification
```

The ledger already delivers signed, at-least-once merchant notifications (PR09): `payment.succeeded`, `payment.canceled`, `payment.state_changed`. F16 adds the dispatch side.

- **A receiver,** `POST /webhooks/ledger`. It:
  - verifies the HMAC over the **raw bytes**;
  - deduplicates by `eventId` in the same transaction as the effect;
  - correlates the order through `orderKey` (`dispatch-order-<id>`, F15);
  - moves a new order payment status through `order-state-machine.ts`.
- **One F15 review issue fixed:** a ledger replay whose `nextAction` is `NONE` (the payment is already paid or canceled) no longer dead-letters the outbox event.

The verification sends signed notifications to dispatch directly in e2e. Real delivery from the ledger is F24 (see Out of scope).

## Existing code to follow

- `ledger/docs/contracts/merchant-notifications.md` (Chinese; the source of truth for the wire format) and `ledger/src/main/java/com/paymentsledger/notification/NotificationSignature.java`:
  - **Signature:** `v1=` + lowercase hex of `HMAC-SHA256(secret, "<timestamp>.<eventId>.<businessKey>." + rawBody)`. The secret must be at least 32 bytes; the timestamp is accepted within ±300 s.
  - **Headers:** `X-Payments-Event-Id`, `X-Payments-Business-Key`, `X-Payments-Timestamp`, `X-Payments-Signature`.
  - **Body:** at most 16 KiB. Its fields are:
    - `schemaVersion` (1), `eventId` (UUID), `eventType`;
    - `organizationId`, `environmentId`, `applicationId`, `providerAccountId`;
    - `paymentId` and `orderId`, both ledger **UUIDs**;
    - `orderKey`, `resourceVersion`, `currency`, `amountMinor`, `capturedAmountMinor`, `paymentStatus`, `origin`, `occurredAt`, `businessKey`.
  - **Responses:** 2xx means done; 408, 429 and 5xx are retried; anything else is DEAD.
  - `payment.succeeded` is emitted once, only for a full NATIVE capture. `businessKey` repeats across `payment.state_changed` events.

## Design decisions (fixed)

1. **Order payment status, separate from fulfillment status.** New enum `OrderPaymentStatus`, registered for GraphQL as `OrderPaymentStatus`:

   | Value | Meaning |
   | --- | --- |
   | `NotRequired` | Checkout was disabled when the order was created; also every pre-F16 order (migration default) |
   | `AwaitingPayment` | Checkout enabled; the ledger payment is owed or created, no result yet |
   | `Paid` | `payment.succeeded` applied |
   | `Failed` | `payment.canceled` applied |

   - **Column** `Order.paymentStatus`: `enum`, not null, default `NotRequired`, exposed as a GraphQL field.
   - **`createOrder`** sets `AwaitingPayment` when `LEDGER_CHECKOUT=enabled`, else `NotRequired`.
   - **Fulfillment status** (`OrderStatus`) is not touched by payments. Holding cooking or dispatch until `Paid` is a later feature.
2. **Payment transitions live in the state machine.** In `order-state-machine.ts`, add:

   ```ts
   export type LedgerPaymentEvent = 'payment.succeeded' | 'payment.canceled' | 'payment.state_changed';
   export const PAYMENT_TRANSITIONS: Readonly<Record<OrderPaymentStatus, Readonly<Partial<Record<LedgerPaymentEvent, OrderPaymentStatus>>>>> = {
     [OrderPaymentStatus.NotRequired]: {},
     [OrderPaymentStatus.AwaitingPayment]: {'payment.succeeded': OrderPaymentStatus.Paid, 'payment.canceled': OrderPaymentStatus.Failed},
     [OrderPaymentStatus.Paid]: {},
     [OrderPaymentStatus.Failed]: {},
   };
   export type PaymentVerdict =
     | {kind: 'allowed'; next: OrderPaymentStatus}
     | {kind: 'noop'}
     | {kind: 'ignored'; reason: string};
   export function evaluatePaymentEvent(current: OrderPaymentStatus, event: LedgerPaymentEvent): PaymentVerdict
   ```

   The rules are checked in this order; the first that matches wins:
   1. `payment.state_changed` → `ignored` with reason `informational event`.
   2. The event's target already equals `current` → `noop`. That is `succeeded` on `Paid`, or `canceled` on `Failed`.
   3. An edge exists → `allowed`.
   4. Otherwise → `ignored`, with reason `` `${event} cannot apply to a ${current} order` ``. That covers `canceled` after `Paid`, `succeeded` after `Failed`, and anything on `NotRequired`.

   Out-of-order and conflicting events never move an order backwards or across.
3. **Raw body.** `NestFactory.create(AppModule, {rawBody: true})` in `main.ts`, and `moduleRef.createNestApplication({rawBody: true})` in `test/utils/e2e.ts`. The controller reads `req.rawBody` (`RawBodyRequest<Request>`).
   - The signature is computed over those bytes. The body is never re-serialized.
   - The existing fulfillment webhook is unchanged.
4. **Receiver** `POST /webhooks/ledger`, in a new `LedgerNotificationsController` in `src/ledger/`. The steps run in this order:

   | Step | Failure | Response |
   | --- | --- | --- |
   | `LEDGER_CHECKOUT` is `enabled` | disabled | `404` |
   | `rawBody` present and ≤ 16384 bytes | missing / larger | `400` / `413` |
   | Four headers present and single-valued; signature format `^v1=[0-9a-f]{64}$`; timestamp an integer within ±300 s of now; HMAC matches (constant-time, `timingSafeEqual`) | any | `401` `{error: 'invalid signature'}`, nothing stored |
   | The body parses as JSON with the fields of decision 5; `eventId` and `businessKey` in the body equal the headers | any | `400` |
   | Ingest (decision 6) | DB error | `500`: the ledger retries |
   | Ingest result | duplicate (same digest) | `200` `{received: true, duplicate: true}` |
   | Ingest result | same `eventId`, different digest | `409` `{error: 'event id reused with different content'}` |
   | Ingest result | recorded (applied or ignored) | `200` `{received: true, duplicate: false, applied, reason}` |

   The response codes follow the ledger's retry rules: a `401` or `409` becomes DEAD on the ledger side and is investigated; it is never retried forever.
5. **Accepted body** (`LedgerNotification`, validated by a pure function):
   - required: `schemaVersion === 1`, `eventId` (UUID, lowercase), `eventType` in decision 2's three values;
   - required: `orderKey` matching `^dispatch-order-([1-9][0-9]*)$`;
   - required: `currency`, `amountMinor` and `capturedAmountMinor` (non-negative integers), `paymentStatus` (string), `businessKey` (string), `occurredAt` (string);
   - the other fields are kept but not interpreted.

   A body that fails validation gets `400` (decision 4) and stores nothing.
6. **Ingest**, one transaction, in `LedgerNotificationService.ingest(notification, rawBody)`:
   1. **Inbox.** Insert into the new `ledger_notification` inbox: `eventId` (unique), `eventType`, `businessKey`, `digest` = sha256 hex of the raw body, `orderId` (nullable), `outcome`. On `23505`, read the stored digest: equal → duplicate; different → conflict. Insert-then-act, as `webhook-ingest.service.ts` does.
   2. **Order.** Look the order up by the id parsed from `orderKey`, with `FOR UPDATE`. None → outcome `ignored: unknown order`.
   3. **Consistency.** Ignored, each with its own outcome:
      - `currency !== 'USD'` → `ignored: currency mismatch`;
      - `amountMinor !== order.totalCents` → `ignored: amount mismatch`;
      - for `payment.succeeded`, `paymentStatus !== 'SUCCEEDED'` or `capturedAmountMinor !== amountMinor` → `ignored: not a full capture`.
   4. **State machine.** `evaluatePaymentEvent(order.paymentStatus, eventType)`:
      - `allowed` → `UPDATE "order" SET "paymentStatus" = :next WHERE id = :id AND "paymentStatus" = :current`, with outcome `applied: <next>`;
      - `noop` → `ignored: already <status>`;
      - `ignored` → `ignored: <reason>`.
   5. **Write-back.** Store the outcome and `orderId` on the inbox row, then commit.

   The inbox row is written for every validated, signed event, including ignored ones, so a redelivery is a duplicate.
7. **Correlation by `orderKey`, not `paymentId`.** The notification's `paymentId` is the ledger's internal UUID. F15 stored the API id (`pay_<ULID>`). The two are not compared. `orderKey` is unique per ledger application and is derived from the dispatch order id, so it identifies the order exactly.
8. **Config.** New `LEDGER_NOTIFICATION_SECRET`: required when `LEDGER_CHECKOUT=enabled`, `Joi.string().min(32)`. It is never logged.
9. **Inbox entity** `LedgerNotification` (`CoreEntity`): `eventId` varchar(64) unique, `eventType` varchar(64), `businessKey` varchar(256), `digest` char(64), `orderId` int nullable (not a foreign key, as with the outbox's `aggregateId`), `outcome` varchar(128). Registered in `src/database/entities.ts`.
10. **F15 issue 1 fix.**
    - `interpretLedgerResponse` gains `{kind: 'settled', paymentId}` for `201`/`200` whose `nextAction.type === 'NONE'`: the payment is already paid or canceled, and needs no link.
    - `deliverPayment` handles `settled` like `accepted`: guarded `ledgerPaymentId` write, event `Sent`, `providerRef = paymentId`. It leaves `checkoutUrl` unchanged (null if never set). Its result arrives as a notification.
    - `WAIT_FOR_CONFIRMATION` stays `pending` (unchanged).
    - `FakeLedger` gains the step `{respond: 'settled'}`: it stores the payment and answers `201` with `nextAction: {type: 'NONE'}`, and a key replay then answers `200` with the same body.
11. **Contract.** New `contracts/ledger-merchant-notifications.md` (English): the cross-service notification contract for dispatch, as decisions 4–7 consume it, with a link to the ledger's Chinese source document. New `contracts/fixtures/ledger-payment-succeeded.json`: one valid `payment.succeeded` body for `orderKey dispatch-order-1`, amount 1875. The e2e helper loads it and overrides fields per test. `contracts/README.md` gets one line for each new file.
12. **No change** to:
    - the ledger (code, notifications, config), `ledger-openapi.yaml`, `docs/features.json` verification;
    - fulfillment webhooks and `OrderStatus` transitions;
    - the root `docker-compose.yml`.

## Out of scope

- **Real ledger → dispatch delivery.** That is F24. It needs:
  - a `platform.merchant_notification_target` row with an HTTPS public URL (the ledger refuses plain HTTP and private addresses outside its test fixture), for example an ngrok tunnel to dispatch;
  - `MERCHANT_NOTIFICATION_ALLOWED_HOSTS`, `MERCHANT_NOTIFICATION_KEY_<REF>` equal to dispatch's `LEDGER_NOTIFICATION_SECRET`, `PAYMENT_MESSAGING_ENABLED=true` on the worker, and the Kafka topic.

  F16 changes nothing in the ledger.
- Gating cooking or fulfillment on `Paid`; cancelling the order on `Failed`; refund notifications.
- F15 review issues 2–4 (claim lease vs timeout, the unfalsifiable fake count, the extra payment on mismatch). They remain recorded in `docs/progress.md`.

## Risks

- **Raw body.** If `req.rawBody` is undefined for `application/json`, the `rawBody: true` option did not reach the app (main.ts or the e2e harness). Test 22 catches this. Do not fall back to `JSON.stringify(req.body)`.
- **The env leaking between spec files.** As in F15: set, import, restore. Run the whole suite.
- **Enum migration naming.** The TypeORM default for `Order.paymentStatus` is `order_paymentstatus_enum`. The `--dryrun` check proves the hand-written SQL matches the entity.
- **Clock skew in tests.** Sign with the current time from `Math.floor(Date.now() / 1000)`. Test 17's stale case uses −301 s, not a value close to the limit.
- **Host ports for dispatch e2e on the developer's Mac.** As in F15: throwaway `f13-e2e-postgres` (127.0.0.1:55432) and `f13-e2e-redis` (127.0.0.1:56380), and a temporary `dispatch/.env.test`. Remove them afterwards. Do not stop other projects' containers.
