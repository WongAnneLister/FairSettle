# F37 · Driver offers and owner restaurants load

## Goal

Behavior (to be added to docs/features.json by the user):

> Drivers see every ready, unassigned order that is paid or needs no payment, can open it without the customer's details, and can claim only those; unpaid orders are not offered. The owner dashboard and restaurant pages load the owner's restaurants with their menus, order lists carry their customer and driver, and every storefront query runs without a GraphQL error.

Verification (`kind: command`):

```bash
cd dispatch && npm test -- --testPathPattern=driver-offer && npm run test:e2e -- --testPathPattern='driver-offers|storefront-queries' && cd frontend && npm test
```

### Decisions

1. **Paid only (user, 2026-11-04).** A driver is offered an order only when it is `Cooked`, has no driver, and its `paymentStatus` is `Paid` or `NotRequired`. `AwaitingPayment` and `Failed` orders are not offered.
2. **One rule, one place.** `src/orders/driver-offer.ts` holds the rule (`isOfferedToDrivers`) and what a driver sees before claiming (`driverPreview`). The new list, `getOrder`, the `cookedOrders` subscription and the claim all use it.
3. **What an unclaimed order shows a driver.** Restaurant (name, address), items, total, status, payment status, created time. Not shown: `customer` (id and email), `checkoutUrl`, `ledgerPaymentId`. An order has no delivery address of its own; the customer's email is the only customer data, and the driver gets it after claiming (`getOrders` / `getOrder` as the assigned driver, unchanged).
4. **New query `availableOrders`, not a change to `getOrders`.** `getOrders` means "my orders" for every role (driver: `driverId = me`), and `/driver/active` and the driver dashboard's history depend on that. A separate query keeps that meaning and lets the list return previews only.
5. **`getOrder` admits a driver to an offered order, as a preview.** `canRead` / `canSeeOrder` stay as they are, so `orderTimeline` and `editOrder` are unchanged; only `getOrder` gets the extra branch. A read cannot race a claim: the claim is still decided by the conditional UPDATE (ADR 0001, 0005).
6. **`takeOrder` refuses unpaid orders (user, 2026-11-04).** The payment precondition goes into the UPDATE's WHERE clause, the same shape ADR 0001 requires. Without it, the list hides unpaid orders but any driver can still claim one by id (the F36 live check did exactly that with order 12).
7. **The `cookedOrders` push follows the same rule.** It is filtered to offered orders and resolved as a preview. Today it announces unpaid orders ("New order ready to claim") that the list would not show, and any driver can ask the payload for `customer { email }`.
8. **Same class of bug, found by the audit (item 3 and more).** See "What was checked".

### `dispatch/src/orders/driver-offer.ts` (new)

```ts
import {Order, OrderPaymentStatus, OrderStatus} from './entities/order.entity';

/** Payment states in which a ready order is offered to drivers (F37). */
export const OFFERED_PAYMENT_STATUSES: readonly OrderPaymentStatus[] = [
  OrderPaymentStatus.Paid,
  OrderPaymentStatus.NotRequired,
];

export function isOfferedToDrivers(order: Pick<Order, 'status' | 'driverId' | 'paymentStatus'>): boolean;

export function driverPreview(order: Order): Order;
```

- `isOfferedToDrivers`: `order.status === OrderStatus.Cooked && order.driverId == null && OFFERED_PAYMENT_STATUSES.includes(order.paymentStatus)`. `== null` on purpose: `driverId` is `null` from the database and may be `undefined` on a published payload.
- `driverPreview`: returns a new object `{...order, customer: null, customerId: null, checkoutUrl: null, ledgerPaymentId: null}`. Does not mutate the argument. Doc comment: what a driver sees of an order before claiming it; the customer is revealed by the claim.

### `dispatch/src/orders/orders.service.ts` (modified)

1. Import `AvailableOrdersInput, AvailableOrdersOutput` and `OFFERED_PAYMENT_STATUSES, driverPreview, isOfferedToDrivers`.
2. **`getOrders`**: after `.leftJoinAndSelect('order.restaurant', 'restaurant')` add `.leftJoinAndSelect('order.customer', 'customer')` and `.leftJoinAndSelect('order.driver', 'driver')`. Extend the comment: the query builder ignores `eager: true`, so every relation the storefront reads is joined here; without these two, `customer` and `driver` came back null for every role. Nothing else changes (role filters, paging, order).
3. **New method**, placed after `getOrders`:

   ```ts
   async availableOrders(driver: User, {page}: AvailableOrdersInput): Promise<AvailableOrdersOutput>
   ```

   - Query builder on `order`: `leftJoinAndSelect` `order.restaurant` → `restaurant`, `order.items` → `item`, `item.dish` → `dish`. Do **not** join `customer` or `driver`.
   - `.where('order.status = :cooked', {cooked: OrderStatus.Cooked})`, `.andWhere('order.driverId IS NULL')`, `.andWhere('order.paymentStatus IN (:...offered)', {offered: [...OFFERED_PAYMENT_STATUSES]})`. The three conditions are the SQL form of `isOfferedToDrivers`; say so in a comment.
   - `.orderBy('order.createdAt', 'ASC').addOrderBy('order.id', 'ASC')` (oldest first: the order that has waited longest is offered first), `.take(ORDERS_PAGE_SIZE).skip((page - 1) * ORDERS_PAGE_SIZE)`.
   - `getManyAndCount()`; return `{ok: true, orders: orders.map(driverPreview), totalResults, totalPages: Math.ceil(totalResults / ORDERS_PAGE_SIZE)}`.
   - Catch: `return failure(error, this.logger, {op: 'availableOrders', driverId: driver.id, page});`.
4. **`getOrder`**: replace

   ```ts
   if (!this.canRead(caller, order)) {
     throw new ForbiddenError("You can't see that.");
   }
   ```

   with

   ```ts
   if (!this.canRead(caller, order)) {
     // A driver may look at an order on offer before claiming it, without the
     // customer's details (F37). The claim itself is still decided by takeOrder's
     // conditional UPDATE, so this read cannot let two drivers win.
     if (caller.kind === 'user' && caller.user.role === UserRole.Delivery && isOfferedToDrivers(order)) {
       return {ok: true, order: driverPreview(order)};
     }
     throw new ForbiddenError("You can't see that.");
   }
   ```

   `canRead`, `canSeeOrder`, `orderTimeline`, `editOrder` unchanged.
5. **`takeOrder`**: add to the conditional UPDATE, after the status condition:

   ```ts
   .andWhere('"paymentStatus" IN (:...offered)', {offered: [...OFFERED_PAYMENT_STATUSES]})
   ```

   Extend the comment above the statement: the payment precondition is part of the same WHERE clause (F37), so an unpaid order cannot be claimed and the winner is still decided by rows affected.
6. **`explainFailedClaim`**: keep the not-found and already-has-a-driver branches. Replace the final `throw` with:

   ```ts
   if (order.status !== OrderStatus.Cooked) {
     throw new ConflictError(`Order is ${order.status}, not ${OrderStatus.Cooked}`);
   }
   throw new ConflictError('Order is not paid yet');
   ```

   CONFLICT, not FORBIDDEN: the payment may still complete, the driver may refresh and try again (same reasoning as the existing comment).

## Risks

- **Unpaid orders disappear for drivers on the live stack.** With `LEDGER_CHECKOUT=enabled`, an order must be paid in the PayPal sandbox before a driver can see or claim it. That is the user's decision and matches the refund demo (a refund needs a captured payment), but the demo script must pay first. Cooked orders already stuck in `AwaitingPayment` are no longer offered.
- **Query builder conditions on relation ids.** `order.driverId IS NULL` and `order.paymentStatus IN (...)` must be written in the property-path form the existing `getOrders` uses (`order.driverId = :userId` works today). E1 fails if TypeORM does not translate them; do not switch to raw SQL without saying so under Deviations.
- **Joining `customer`/`driver` in `getOrders`.** `User.password` is `select: false`, which `leftJoinAndSelect` respects, so no hash is loaded. Many-to-one joins add no rows, so `take`/`skip` pages are unchanged; E13 and S2 cover the result.
- **Redis payloads.** `cookedOrders` payloads cross Redis as JSON; `driverId` arrives as `null` and `paymentStatus` as a string, which `isOfferedToDrivers` handles (`== null`). `subscriptions-across-replicas` (NotRequired orders) keeps proving cross-replica delivery.
- **Reading frontend files from a dispatch e2e test.** `storefront-queries` depends on `dispatch/frontend/src/lib/graphql/queries.ts` keeping documents without `${}` interpolation (true today in all three files). If a fragment is ever interpolated, S1 fails loudly rather than silently skipping a query.
