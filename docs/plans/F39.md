# F39 · Food-safety complaints refund the order total

## Goal

Behavior (copied from docs/features.json):

A complaint can be filed as food_safety (a foreign object such as an insect, or contamination). The agent may propose up to the order total for it, only for a delivered order, and by default charges the restaurant 10000 bp. The ledger accepts and stores the FOOD_SAFETY reason code; every other reason code and cap is unchanged.

Verification (copied from docs/features.json):

`cd agent && PYTHONUTF8=1 uv run --frozen python -m pytest -q tests/test_food_safety.py tests/test_policy.py tests/test_evals.py::test_prompt_and_policy_carry_the_prd_defaults ../scripts/tests/test_ledger_contract.py && cd ../ledger && ./mvnw -q -Dtest='RefundProposalApiTest' test`

Only the PRD-defaults test is taken from `test_evals.py`: its other tests open an asyncio event loop, which the tests' network guard refuses on Windows, so they fail there with or without this feature. `PYTHONUTF8=1` lets `test_policy_is_pure` read source files on a Windows GBK locale.

Why: today a dead insect in the food can only be filed as `quality`, whose cap is 20 % of the order (`PolicyConfig.quality_cap_basis_points = 2000`). That cap is right for cold or poor food and wrong for a food-safety incident. Raising the `quality` cap would let every quality complaint refund the whole order, so food safety gets its own reason code instead.

Compensation above the amount paid is out of scope: a PayPal refund cannot exceed the capture, and paying more would need the payout module.

## Changes

### `ledger/src/main/resources/db/migration/V21__food_safety_reason.sql` (new)

Replace the column check created by V20 (Postgres names it `refund_proposal_reason_code_check`):

```sql
ALTER TABLE platform.refund_proposal DROP CONSTRAINT refund_proposal_reason_code_check;
ALTER TABLE platform.refund_proposal ADD CONSTRAINT refund_proposal_reason_code_check
    CHECK (reason_code IN ('LATE_DELIVERY','MISSING_ITEM','WRONG_ITEM','QUALITY','FOOD_SAFETY','DELIVERY_FAILED','OTHER'));
```

If the constraint name differs, the migration fails at startup and the ledger tests fail; that is the intended signal (do not make it conditional).

## Out of scope

- Compensation above the paid amount, payouts, vouchers.
- The `quality` cap and every other cap and default split.
- Eval scenarios and `docs/eval-results.md` (they need a live model run).
- Dispatch and the storefront.

## Risks

- The model may still file an insect under `quality`. The prompt now defines food safety; the complaint page lets the customer choose `food_safety`, and the complaint type is shown to the model.
- A full refund is a larger amount for the reviewer to approve; review by a person stays mandatory.
- The constraint name: see the migration note.
