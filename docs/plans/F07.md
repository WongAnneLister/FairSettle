# F07 · Capture timeout goes to UNKNOWN

## Goal

Behavior (copied from docs/features.json):

> A capture call that times out leaves the payment UNKNOWN; recovery queries PayPal and settles the state without issuing a second capture.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='PayPalCaptureUnknownTest' test
```

`PayPalCaptureUnknownTest` is a unit test of the pure recovery rules (no Docker). The end-to-end recovery paths also get an integration test, `PayPalCaptureUnknownIT`, which runs under `./mvnw verify` and must pass before the work commit.

### What F06 already does, and what F07 adds

F06 already handles the first half of the behavior and the adoption case:

- A capture timeout leaves the operation `UNKNOWN`. The payment stays `PROCESSING`, `provider_status='APPROVED'` and becomes `resolution_status='UNKNOWN'` (F06 test 43).
- Recovery of a non-`PREPARED` capture runs a GET order, merges it and never sends. A GET showing a `COMPLETED` capture adopts it, resolves the operation and posts the settlement.

F07 implements the remaining rows of ADR §5's timeout path:

1. **Step 3:** after a recovery GET shows `APPROVED` with no capture, resend the capture with the original `PayPal-Request-Id`. This happens only while the operation's `retry_until` (first send + 5 h, ADR D7) has not passed, and only directly after that GET, under the same lease.
2. **Step 4:** the same GET after `retry_until` → ESCALATED (`CAPTURE_WINDOW_EXPIRED`). No resend, no new id, not failed.
3. **Step 5 and P1:**
   - `VOIDED` with no capture → `CANCELED` (already true through the merge); the operation is now `RESOLVED`.
   - `COMPLETED` whose only capture is `DECLINED`/`FAILED` → `CANCELED`, from a query only.
   - `VOIDED` with any capture → CONFLICT.
4. **Step 6:** a GET that fails stays `UNKNOWN` with L1 backoff. At the unresolved-age limit → ESCALATED (`UNRESOLVED_AGE_LIMIT`).
5. **`ORDER_ALREADY_CAPTURED`:** the capture result is followed directly by a GET order (ADR §5 row), so an existing capture is adopted in the same attempt.

"Without issuing a second capture" means: a second capture **object** is never created. A resend under step 3 uses the same request id, so PayPal returns the original capture if the first request was accepted (sample 06). A new request id is never used (op X1). Every test below pins that all capture calls carry the same `PayPal-Request-Id`.

## Design decisions (fixed)

1. **One pure rule decides what a capture recovery does after its GET.** The rule is `CaptureRecoveryRules.next`, and its order is fixed (table below). The write-back applies it under the lease. A resend is the only outcome that does not complete the operation in that transaction.
2. **The resend reuses F06's send path.** `PaymentExecutor.capture(...)` is called with a claim whose payment map is re-read after the recovery merge (the merge bumped the payment version; a stale map would make the follow-up GET stale). `skipCapture` still checks `owns()` and `capturable` right before sending. The command, and with it the `PayPal-Request-Id`, comes from the operation row, which is immutable (V4 trigger). It cannot change.
3. **The window is the operation's `retry_until`.** The lease grant sets it once to `first_send_at + RecoveryPolicy.verifiedWindow("PAYPAL")` = 5 h and it never moves (`OperationLeaseRules.grant`, V5 trigger). The resend is allowed iff `retry_until != null && now < retry_until`.
4. **The window check comes before the age check.** A GET that shows `APPROVED` makes the payment `KNOWN` again, so the age limit cannot apply in that case anyway.
5. **`ORDER_ALREADY_CAPTURED` is queried immediately.** `CaptureOutcomeRules.queriesAfter` also returns true for `TIMEOUT_UNKNOWN` with code `ORDER_ALREADY_CAPTURED`. `decide` is unchanged: row 1 resolves the operation when the GET shows the capture, otherwise row 8 leaves it `UNKNOWN`.
6. **P1 for a declined capture.**
   - `ProviderQueryService.queryOrder` treats an order `COMPLETED` whose captures are all `failed` as complete evidence.
   - `PaymentEvidenceRules.decide` cancels on such evidence exactly as it cancels on an expired session: query only, not stale, no conflict, nothing captured.
   - A webhook never cancels (payment R4); the existing `query` guard keeps that true.
7. **`VOIDED` with any capture is a conflict** (ADR §3), set in `queryOrder`.
8. **A canceled payment resolves the capture operation.** The task is already done for `CANCELED`/`KNOWN` (`paymentTaskDone`); the operation status becomes `RESOLVED` instead of staying `UNKNOWN`.
9. **No change** to the capture adapter, the classification tables, F06's first-send path, the GET-payment path (`refresh` never resends; F06 test 43 stays as is), settlements, migrations or the ADR.

### `CaptureRecoveryRules.next`: first matching row wins

Inputs:

- `payment`: `PaymentProgress` after the merge.
- `approvedWithoutCapture`: the merge was applicable and `PaymentEvidenceRules.preparesCapture(facts, true)`.
- `retryUntil`, `now`.
- `ageLimitReached`: `ProviderResultRules.ageLimitReached(payment.resolution(), payment.unresolvedSince(), policy.unresolvedAge(), now)`.

| # | Condition | `Next` | Write-back |
| --- | --- | --- | --- |
| 1 | payment `SUCCEEDED`, `capturedMinor > 0`, `KNOWN` | `RESOLVE` | `completeOperation(RESOLVED, payment resolution, order id, provider status)` |
| 2 | payment `CANCELED`, `KNOWN` | `RESOLVE` | as row 1 |
| 3 | `approvedWithoutCapture` and `capturable(payment)` and `retryUntil != null` and `now < retryUntil` | `RESEND` | nothing; the lease is kept for the resend |
| 4 | `approvedWithoutCapture` and `capturable(payment)` | `ESCALATE_WINDOW` | `escalateOwned(claim, "CAPTURE_WINDOW_EXPIRED")` |
| 5 | `ageLimitReached` | `ESCALATE_AGE` | `alertAgeOwned(claim)`, then `escalateOwned(claim, "UNRESOLVED_AGE_LIMIT")` |
| 6 | otherwise | `WAIT` | `completeOperation(original status RESOLVED ? RESOLVED : UNKNOWN, …)`, as F06 |

## Changes

Java paths are under `ledger/src/main/java/com/paymentsledger/` unless noted. No migration.

### `payment/domain/CaptureRecoveryRules.java` (new)

```java
/** Pure rules for recovering a capture whose outcome is uncertain (ADR §5 timeout path). */
public final class CaptureRecoveryRules {
    public enum Next {
        RESOLVE,
        RESEND,
        ESCALATE_WINDOW,
        ESCALATE_AGE,
        WAIT
    }

    private CaptureRecoveryRules() {}

    public static Next next(
            PaymentProgress payment,
            boolean approvedWithoutCapture,
            Instant retryUntil,
            Instant now,
            boolean ageLimitReached)
}
```

Implements the table above exactly; uses `PaymentEvidenceRules.capturable`. Class Javadoc lists the never-rules: no new request id, no resend without a fresh GET in the same attempt, no resend outside the window, never marks the payment failed.

### `payment/domain/CaptureOutcomeRules.java` (modified)

`queriesAfter` also returns true when `classification == TIMEOUT_UNKNOWN && "ORDER_ALREADY_CAPTURED".equals(errorCode)`. Update its Javadoc. `decide` does not change.

### `payment/domain/PaymentEvidenceRules.java` (modified)

- Add:

```java
/** ADR P1: a PayPal order completed with only declined or failed captures can no longer be captured. */
public static boolean captureDeclined(PaymentFacts facts) {
    return facts.session() != null
            && "COMPLETED".equals(facts.session().paymentStatus())
            && !facts.charges().isEmpty()
            && facts.charges().stream().allMatch(c -> !c.captured() && c.status().equals("failed"));
}
```

- In `decide`, the cancel condition's last term `facts.session().status() == CheckoutSessionStatus.EXPIRED` becomes `(facts.session().status() == CheckoutSessionStatus.EXPIRED || captureDeclined(facts))`. Nothing else in that condition changes. Stripe session payment statuses are lowercase and never `COMPLETED`, so Stripe behavior is unchanged.

### `payment/ProviderQueryService.java` (modified, `queryOrder` only)

- `conflict` gains one more term: `"VOIDED".equals(session.paymentStatus()) && !order.captures().isEmpty()`.
- `declined` = `!verified.isEmpty() && verified.stream().allMatch(c -> !c.captured() && c.status().equals("failed"))`.
- `complete` = `!conflict && (!"COMPLETED".equals(session.paymentStatus()) || captured || declined)`.

### `payment/ProviderResults.java` (modified)

- New nested record: `record RecoveredCapture(boolean applicable, CaptureRecoveryRules.Next next) {}`.
- `finishCaptureRecovery(Claim, Queried)` returns `RecoveredCapture` instead of `boolean`. Its steps:
  1. Lock, record observations, `owns()`. If not owned, return `new RecoveredCapture(false, Next.WAIT)`.
  2. `applicable = merge(...)`; `stampQuery`; `progress = results.progress(...)`.
  3. `approvedWithoutCapture = applicable && PaymentEvidenceRules.preparesCapture(queried.facts(), true)`.
  4. `age = ProviderResultRules.ageLimitReached(progress.resolution(), progress.unresolvedSince(), policy.get().unresolvedAge(), clock.instant())`.
  5. `next = CaptureRecoveryRules.next(progress, approvedWithoutCapture, instant(claim.operation(), "retry_until"), clock.instant(), age)`.
  6. Apply the write-back column of the table. `orderId` is `progress.checkoutSessionId()`.
  7. Return `new RecoveredCapture(applicable, next)`.

  Use `PaymentRepository.instant` (static import) for `retry_until`.

### `payment/PaymentRepository.java` (modified)

`finishCaptureRecovery` returns `ProviderResults.RecoveredCapture`.

### `payment/PaymentExecutor.java` (modified)

`recoverCapture` becomes:

```java
/** ADR §5: a PREPARED capture is sent; any other is queried first and resent only per CaptureRecoveryRules. */
void recoverCapture(Claim claim) {
    if ("PREPARED".equals(claim.operation().get("status"))) {
        executeClaim(claim);
        return;
    }
    var queried = query(claim.payment());
    var recovered = repository.finishCaptureRecovery(claim, queried);
    if (recovered.applicable()) postSettlements(claim.payment(), queried);
    if (recovered.next() == CaptureRecoveryRules.Next.RESEND)
        capture(new Claim(
                claim.operationId(),
                claim.paymentId(),
                claim.token(),
                claim.version(),
                claim.type(),
                claim.operation(),
                repository.payment(claim.paymentId())));
}
```

`capture` itself does not change.

## Out of scope

- **Order creation timeouts.** These are F05's. `ProviderResultRules.sessionAnchor` still accepts only `cs_` operation external ids. A PayPal create whose only trace is an unusable observation is resent within the create window, as F05 tests pin. Do not change it here.
- **Capture `PENDING` for longer than the unresolved-age limit.** Today it escalates with `UNRESOLVED_AGE_LIMIT`. A longer wait for PayPal reviews is a later decision (F12 observes the real behavior).
- **Webhooks.** `PAYMENT.CAPTURE.*` and `CHECKOUT.ORDER.APPROVED` are F09/F10. Refunds are F08.
- **Capturing again after a definitive reject and a new approval.** Still one `CAPTURE_ORDER` per payment.
- **Files that do not change:**
  - the PayPal adapter and `PayPalOrderMapping`;
  - `CaptureSettlementService`, the repositories and migrations;
  - `OperationRecoveryCoordinator` (its `CAPTURE_ORDER` branch already delegates to `recoverCapture`);
  - `PaymentExecutor.refresh` / `capture`, `OperationLeaseRules`;
  - the ADR, `contracts/`, `dispatch/`, `agent/`, and the off-limits ledger modules.

## Risks

- **The window rests on documentation.** 5 h is PayPal's documented 6 h minus 1 h, not measured (ADR §10). Test 23 pins that nothing is resent after `retry_until`.
- **A resend after an accepted first request.** It relies on PayPal returning the original capture for the same request id (sample 06, observed). If PayPal instead answered `ORDER_ALREADY_CAPTURED`, test 22 shows the GET right after it adopts the capture.
- **Concurrent capture requests with one request id.** PayPal documents that simultaneous requests may fail (ADR §5 row, not observed). The resend runs under the operation's lease, so only one sender exists per operation.
- **Payment version after the merge.** The resend re-reads the payment row (decision 2). Otherwise the follow-up GET would be judged stale and the capture would only be adopted one recovery round later. Test 21 pins the same-attempt result.
- **IT determinism.** Both the create task and the capture task are due after a timeout. `onlyCaptureTaskRecovers()` isolates the capture task; the create task's own recovery is covered by F05/F06 tests.
- **Docker.** `PayPalCaptureUnknownIT` needs `./mvnw verify`. Run it on the VPS as for F06. Sync both `ledger/` and `docs/adr/paypal-samples/` (tests 22 and F06's tests read samples), and strip CRLF from `mvnw` there. Do not skip the IT.
