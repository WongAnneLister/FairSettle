# F13 · One compose for all services

## Goal

Behavior (copied from docs/features.json):

> Root docker-compose.yml starts separate Postgres and Redis for ledger and dispatch (no port clash), Kafka, ledger api and worker, dispatch; every service reports healthy.

Verification (copied from docs/features.json):

```bash
docker compose up -d --wait && curl -fsS localhost:8080/actuator/health && curl -fsS localhost:8081/actuator/health && curl -fsS -o /dev/null localhost:4000/graphql?query=%7B__typename%7D
```

F13 is the local stack that F15 (dispatch checkout through the ledger) and later features build on. It adds:

- a repository-root `docker-compose.yml` with eight services;
- a Dockerfile for dispatch, which has none today;
- a narrow change in dispatch so that the verification's plain `GET` health probe is not rejected by Apollo's CSRF prevention (decision 6).

The ledger gets no code change; its Dockerfile gets two BuildKit cache mounts (decision 12).

### Why dispatch needs a code change

The verification's last `curl` sends `GET /graphql?query={__typename}` with no headers. Dispatch uses Apollo Server 5.5.1 through `@nestjs/apollo` 13.4.5:

- `ApolloServer` enables CSRF prevention when `csrfPrevention` is undefined;
- `@nestjs/apollo` does not override it;
- `preventCsrf` rejects any request that has no `Content-Type` (or a "simple" one) and no non-empty `x-apollo-operation-name` / `apollo-require-preflight` header.

The probe therefore gets HTTP 400, and `curl -f` fails. The verification command must not change (AGENTS.md). Disabling CSRF prevention for the whole API was rejected. The user chose a probe-only exemption on 2026-10-24.

## Design decisions (fixed)

1. **Eight services, project name `fairsettle`:**

   | Service | Image / build | Role |
   | --- | --- | --- |
   | `ledger-postgres` | `postgres:16` | ledger database |
   | `ledger-redis` | `redis:7-alpine` | ledger rate-limit store |
   | `kafka` | `apache/kafka:3.9.0` | broker (KRaft, single node) |
   | `ledger-api` | build `./ledger`, image `fairsettle-ledger:local` | `--spring.profiles.active=api` |
   | `ledger-worker` | build `./ledger`, image `fairsettle-ledger:local` | `--spring.profiles.active=worker` |
   | `dispatch-postgres` | `postgres:16-alpine` | dispatch database |
   | `dispatch-redis` | `redis:7-alpine` | dispatch GraphQL subscriptions |
   | `dispatch` | build `./dispatch`, image `fairsettle-dispatch:local` | dispatch API |

   No `container_name` anywhere, so nothing clashes with the containers of `ledger/compose.yaml` (`pl-*`) or `dispatch/docker-compose.yml`. Those two files stay as they are.
2. **Only the three verified ports are published:** `ledger-api` `8080:8080`, `ledger-worker` `8081:8081`, `dispatch` `4000:4000`.
   - No database, Redis or Kafka port is published. Services reach each other by service name on the compose network.
   - This is what "no port clash" means here: ledger and dispatch never compete for a host port, and neither do other projects' containers.
   - For direct access, use `docker compose exec ledger-postgres psql -U postgres -d payments_ledger`.
3. **No variable interpolation.** `docker-compose.yml` contains no `${`; every value is literal.
   - Reason: Compose reads the repository-root `.env` for interpolation. That file holds sandbox credentials and local overrides (`DB_PORT=5434`, `WORKER_PORT=8091`). Literal values keep both out of the stack.
   - No `env_file:` either.
4. **No provider and no secrets in the stack.**
   - The ledger runs with no provider enabled: no `PAYPAL_*`, `STRIPE_*`, fixtures or webhook settings. That is enough for health.
   - Enabling PayPal in the stack belongs to F15 or later, and needs its own secret handling.
   - Local passwords are the documented local defaults (`postgres`, `payments_app_pw`, `payments_migrator_pw`, `adminer`/`secret123`). Dispatch's `SECRET_KEY` is `local-compose-only` and `FULFILLMENT_SIGNING_SECRET` is `mock-secret`, as in `env.dev.example`.
5. **Dispatch image.** New `dispatch/Dockerfile`, multi-stage:
   - **Build stage:** `node:22-bookworm` (full image: python3/make/g++ are there if a native module like `bcrypt` 6.0.0 must compile). `HUSKY=0 npm ci`, `npm run build`, `npm prune --omit=dev`.
   - **Runtime stage:** `node:22-bookworm-slim`. Copy `package.json`, `node_modules` and `dist` from the build stage. Run as the image's `node` user. `EXPOSE 4000`.
   - **Command:** `sh -c "node node_modules/typeorm/cli.js migration:run -d dist/database/data-source.js && node dist/main"`.
   - **Environment:** `NODE_ENV=production`, so the app reads only real env vars (`ignoreEnvFile`) and does not run migrations itself; the command's explicit `migration:run` is dispatch's documented production step.

   Node 22 matches dispatch CI (`.github/workflows/ci.yml`). New `dispatch/.dockerignore` excludes `node_modules`, `dist`, `pg_data`, `frontend`, `docs`, `test`, `coverage`, `.git`, `.github`, `.husky`, `.env*`, `*.log`.
6. **CSRF exemption for the health probe only.** New Express middleware `healthProbeCsrfExemption`, applied in `AppModule.configure` with `forRoutes({path: 'graphql', method: RequestMethod.GET})`. Nest applies route middleware before Apollo's handler; this is the pattern Nest documents for graphql-upload.
   - It sets `req.headers['apollo-require-preflight'] = 'health-probe'` only when **all** hold:
     - `req.method === 'GET'`;
     - `req.query` has exactly one key, `query`;
     - its value is the string `{__typename}` exactly: no whitespace variants, no arrays;
     - the request has no `apollo-require-preflight` header yet.
   - Otherwise it changes nothing. Then it calls `next()`.
   - `{__typename}` returns only the root type name and reads no data, so exempting it opens nothing. Every other GET and every POST keeps Apollo's CSRF check. `csrfPrevention` stays at its default.
7. **Startup order and health.**
   - **Healthchecks.** Every service has one:
     - Postgres: `pg_isready`.
     - Redis: `redis-cli ping`.
     - Kafka: the broker-api-versions check from `ledger/compose.yaml`.
     - Ledger: `wget -qO- http://127.0.0.1:<port>/actuator/health | grep -q '"status":"UP"'`; busybox `wget` is in the temurin alpine runtime.
     - Dispatch: `node -e "fetch('http://127.0.0.1:4000/graphql?query=%7B__typename%7D').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"`. This is the same probe as the verification, so it also exercises decision 6.
   - **`depends_on`, all `condition: service_healthy`:**
     - `ledger-api` → `ledger-postgres`, `ledger-redis`;
     - `ledger-worker` → `ledger-api`, so Flyway has finished, and `kafka`;
     - `dispatch` → `dispatch-postgres`, `dispatch-redis`.
   - **Start periods:** ledger 60 s, dispatch 60 s, Kafka 20 s.
8. **Kafka is internal only.** Listeners `PLAINTEXT://:9092,CONTROLLER://:9093`; advertised `PLAINTEXT://kafka:9092`; no host listener.
   - The ledger worker gets `SPRING_KAFKA_BOOTSTRAP_SERVERS=kafka:9092`. `PAYMENT_MESSAGING_ENABLED` stays unset (false), so nothing is published yet.
   - Kafka runs and reports healthy, as the behavior requires.
9. **Volumes:** `fairsettle-ledger-postgres`, `fairsettle-dispatch-postgres`, `fairsettle-kafka`, each with an explicit `name:`. `docker compose down` keeps them; `down -v` removes only these.
   - `ledger-postgres` also mounts `./ledger/scripts/db/init-roles.sql:/docker-entrypoint-initdb.d/10-init-roles.sql:ro`.
10. **Ledger environment** (both roles):
    - `DB_HOST=ledger-postgres`, `DB_PORT=5432`, `DB_NAME=payments_ledger`;
    - `DB_APP_USER=payments_app`, `DB_APP_PASSWORD=payments_app_pw`, `DB_MIGRATION_USER=payments_migrator`, `DB_MIGRATION_PASSWORD=payments_migrator_pw`;
    - `REDIS_HOST=ledger-redis`, `REDIS_PORT=6379`;
    - `API_PORT=8080` (api), `WORKER_PORT=8081` (worker).

    **Dispatch environment:**
    - `NODE_ENV=production`;
    - `DB_HOST=dispatch-postgres`, `DB_PORT=5432`, `DB_USER=adminer`, `DB_PASSWORD=secret123`, `DB_NAME=food_delivery`;
    - `SECRET_KEY=local-compose-only`;
    - `REDIS_HOST=dispatch-redis`, `REDIS_PORT=6379`;
    - `FULFILLMENT_SIGNING_SECRET=mock-secret`.
11. **No change** to:
    - the ledger: code, compose, and the Dockerfile apart from decision 12;
    - `dispatch/docker-compose.yml`, dispatch's GraphQL options other than the middleware, dispatch's other modules, and dispatch dependencies other than moving `dotenv` (see `dispatch/package.json`);
    - `agent/`, `contracts/`, `scripts/features.py`, the verification command.

12. **Maven cache mounts in `ledger/Dockerfile`** (amendment of 2026-10-24, approved by the user).
    - **Why.** The first full `docker compose build` failed after 2505 s in `RUN ./mvnw -B -q dependency:go-offline`: `Read timed out` on `org.jetbrains.kotlinx:kotlinx-coroutines-core-jvm:jar:1.8.1` from Maven Central. A failed `RUN` step is not cached, so every retry downloaded every dependency again, and one timeout anywhere lost the whole attempt.
    - **What.** Both Maven `RUN` lines get `--mount=type=cache,target=/root/.m2`. The build stage runs as root, so `~/.m2` is `/root/.m2`. Artifacts downloaded by a failed attempt stay in the BuildKit cache, and the next attempt only fetches what is missing.
    - **Effect.** The image content and the runtime stage are unchanged. Docker Desktop's built-in BuildKit Dockerfile frontend supports `RUN --mount`. Do not add a `# syntax=` line: it would pull a frontend image from Docker Hub during every build.
    - **Not changed.** No Maven timeout or retry flags, no mirror, no proxy.

### `dispatch/package.json` and `dispatch/package-lock.json` (modified)

Move `"dotenv": "^18.0.0"` from `devDependencies` to `dependencies`. Nothing else changes in `package.json`.

- **Why.** `src/database/data-source.ts` imports `dotenv` at runtime; it is the only file in `src/` that does. It is compiled into `dist/` and is the entry of the image's `migration:run`. With `dotenv` as a dev dependency, `npm prune --omit=dev` removes it, and the container fails with `Cannot find module 'dotenv'` (found by Codex, 2026-10-24). `@nestjs/config` and `typeorm` carry their own nested `dotenv` copies, which do not satisfy this import.
- **Rejected:** keeping dev dependencies in the runtime image, because it would ship jest and ts-node.
- **Lockfile.** Do not regenerate it with npm. Codex tried `npm install --package-lock-only` with npm 11.19.0 on macOS. Besides the intended change, it dropped the `"libc"` field from the four Linux-only optional packages `node_modules/@css-inline/css-inline-linux-{arm64,x64}-{gnu,musl}`: those packages are not installed on macOS, so npm rebuilt their entries from registry metadata that has no `libc`. Without `libc`, npm on Linux cannot tell the glibc and musl binaries apart. Instead, edit the parsed JSON with a one-off script (do not commit the script):
  - in `packages[""]`, move `"dotenv": "^18.0.0"` from `devDependencies` to `dependencies`, keeping both objects' keys in alphabetical order;
  - in `packages["node_modules/dotenv"]`, delete the `"dev"` key. Nothing else in that entry changes.

  Write the file back with 2-space indentation and a trailing newline, as npm does. `git diff dispatch/package-lock.json` must show exactly these three changed lines and nothing else. Then `cd dispatch && npm ci` must succeed: it fails if the lockfile and `package.json` disagree.

## Risks

- **Host ports already taken.** The verification needs 8080, 8081 and 4000 free on the host. On the developer's Mac, `redis-admin` publishes 8081. Stop it for the run: `docker stop redis-admin` is the user's call, and so is restarting it afterwards. Do not change the published ports; the verification command fixes them.
- **Network during image builds.** Several downloads go through Docker Hub, Maven Central and npm, all of which timed out intermittently on the developer's Mac (F11, F12):
  - the ledger build downloads Maven dependencies inside Docker;
  - dispatch downloads npm packages;
  - the base images are `eclipse-temurin:21-*`, `node:22-*` and `apache/kafka`.

  Build first with `docker compose build`, so `verify` only starts containers. On a timeout, retry the same command. Do not add mirrors or proxies to the files.
- **`bcrypt` native build.** If no prebuilt binary matches, `npm ci` compiles it. That is why the build stage uses the full `node:22-bookworm` image. If it still fails, stop and report the npm log; do not replace `bcrypt`.
- **Middleware order.** If test 17 gets 400, the middleware runs after Apollo. Stop and report; do not set `csrfPrevention: false`.
- **Apollo/Express query parsing.** Test 14 pins array values. If Express 5's parser presents the probe differently (for example `req.query` is a getter), match on `req.query` as Express gives it, and keep tests 10–16 unchanged.
- **Flyway on first boot.** Only `ledger-api` starts first; the worker waits for it to be healthy, so the two roles never migrate concurrently.
- **Root `.env`.** Compose reads it, but with no interpolation (test 9) its values never reach the stack. Never add `env_file: .env`.
- **First `up` duration.** The verify timeout is 3600 s (F11). After `docker compose build`, startup takes about 1–2 minutes.
