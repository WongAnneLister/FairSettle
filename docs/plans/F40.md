# F40 · Food-safety complaints are decided on the customer's report

## Goal

Behavior (copied from docs/features.json):

A food_safety complaint on a delivered order is decided on the customer's own report. The prompt tells the model that no photo, inspection or chat reaches it, so their absence is no reason to escalate, and that the report supports the complaint unless the order, timeline or payment contradicts it. `python -m evals.food_safety --runs 3` runs one food-safety fixture against the real model and passes only if every run proposes a full refund of the order total charged 10000 bp to the restaurant. The ten PRD scenarios and docs/eval-results.md are unchanged.

Verification (copied from docs/features.json):

`cd agent && PYTHONUTF8=1 uv run --frozen python -m pytest -q tests/test_food_safety_eval.py tests/test_food_safety.py tests/test_evals.py::test_prompt_and_policy_carry_the_prd_defaults && uv run --frozen python -m evals.food_safety --runs 3`

The second half calls the real model, like F27's verification: `DEEPSEEK_API_KEY` must be set in the shell that runs `verify`. `FAIRSETTLE_MODEL` defaults to `deepseek/deepseek-v4-pro`, the model the live stack runs.

Why: F39 let a complaint be filed as `food_safety` and set its cap and default (order total, restaurant 10000), but the prompt gives that default only "when the evidence supports the complaint". In the 2026-11-12 rehearsal on the live stack, two food-safety complaints were escalated by the model itself (no policy violation), both with the same reason: the evidence has the order and the timeline but no photo or inspection, so the claim "cannot be validated". The agent can never receive a photo (the complaint page has no upload and the evidence sources are dispatch and the ledger), so as written every food-safety complaint escalates and F39's default is never reached. A person reviews every proposal before money moves, and the repeat-complaint rule (third complaint in 7 days escalates) still applies, so accepting the customer's report here does not let money move without review.

Quality complaints have the same shape and are out of scope (see below).

## Changes

### `agent/evals/food_safety.py` (new)

```python
import os
os.environ.setdefault("LITELLM_LOCAL_MODEL_COST_MAP", "True")

import argparse
import asyncio
from collections.abc import Mapping
from dataclasses import replace
import sys

import litellm

from fairsettle_agent.complaint import ComplaintInput
from fairsettle_agent.decide import Completion
from fairsettle_agent.model import ModelConfig
from fairsettle_agent.policy import PolicyConfig
from .run import EVAL_MODEL, RunResult, _expected, _party, counted_violations, is_correct, run_case
from .scenarios import Expected, SCENARIOS, Scenario

COMPLAINT_TEXT = ("There was a dead mosquito in my pizza. We found it halfway through the meal, "
                  "so we could not eat the rest.")

FOOD_SAFETY: Scenario = replace(
    SCENARIOS[2],
    id="fs01",
    title="Food safety on the customer's report",
    complaint=ComplaintInput(complaint_id="eval-fs01", order_id=3, complaint_type="food_safety", text=COMPLAINT_TEXT),
    expected=Expected(frozenset({"propose"}), "full_refund", "food_safety", 1500, "restaurant"),
)


def line(result: RunResult) -> str: ...
def main(argv: list[str] | None = None, env: Mapping[str, str] = os.environ,
         complete: Completion = litellm.acompletion) -> int: ...


if __name__ == "__main__":
    sys.exit(main())
```

- `FOOD_SAFETY` reuses scenario 3's order, timeline, payment, refundable amount, `received_at`, `prd` (3) and empty history; only `id`, `title`, `complaint` and `expected` change. `SCENARIOS` itself is not modified.
- `line(result)` returns `f"run {result.run}: {outcome}"` where `outcome` is `"{result.outcome} {decision} {reason_code} {amount_cents} {party}"` when `result.decision` is not `None` (a refund that broke a rule shows its policy outcome, e.g. `escalate full_refund ...`) (party from `_party`, `None` printed as `none`), otherwise `"{result.outcome} ({result.stage}: {result.reason})"`; when `counted_violations(result)` is not empty, append `f" violations {','.join(...)}"`. It never includes the explanation, evidence refs or complaint text.
- `main`:
  - `argparse` with `--runs` (int, default 3); `--runs` < 1 → `parser.error("--runs must be at least 1")`.
  - No `DEEPSEEK_API_KEY` in `env` → print `DEEPSEEK_API_KEY is required` to stderr, return 2, never call `complete`.
  - `ModelConfig(model=env.get("FAIRSETTLE_MODEL", EVAL_MODEL), api_key=...)`; `ValueError` → message to stderr, return 2.
  - `asyncio.run` of `run_case(FOOD_SAFETY, run, model, PolicyConfig(), complete)` for `run` in `1..runs`, sequentially.
  - Print `f"expected: {_expected(FOOD_SAFETY.expected)}"`, then `line(result)` for each run, then `f"correct: {n}/{runs}"` where `n` counts `is_correct(FOOD_SAFETY.expected, result)`.
  - Return 0 when every run is correct, else 1. Writes no file.

## Out of scope

- `agent/evals/scenarios.py`, `agent/evals/run.py`, `docs/eval-results.md` and the README evaluation line: the ten PRD scenarios stay as they are. F40 does not rerun F27.
- `quality` complaints: they rest on the customer's report in the same way and may escalate for the same reason; a later feature can decide that.
- Policy code, caps, default splits, the ledger, dispatch, the complaint page.
- Photo upload or any new evidence source.

## Risks

- The model may still escalate some food-safety runs. The verification requires 3 of 3; if it fails, the feature stays active and the prompt line is revisited in a new plan, never by weakening the check.
- The new line could shift other scenarios. The PRD default lines are unchanged and `test_prompt_and_policy_carry_the_prd_defaults` stays in the verification; a full F27 rerun is advisable before publishing the evaluation line again, but is not part of this feature.
- Accepting the report makes a false food-safety claim easier to propose. Mitigations already in place: review by a person before any refund, the third-complaint-in-7-days escalation, the delivered-order rule and the order-total cap.
- The live check costs three model calls per run (plus investigate turns) and needs network access to DeepSeek.
