# F38 · Owner adds dishes from the storefront

## Goal

Behavior (to be added to docs/features.json by the user):

> An owner can add a dish from the storefront's Add dish form, with an optional photo URL that is saved and shown on the menu. The price field starts empty and accepts only a dollar amount with at most two decimals; any other entry is refused with a message instead of being saved as a different price. Every storefront mutation document, with the variables its page sends, is valid against the dispatch schema.

Verification (`kind: command`):

```bash
cd dispatch && npm test -- --testPathPattern=dish-input && npm run test:e2e -- --testPathPattern=storefront-mutations && cd frontend && npm test
```

The e2e part needs the dispatch test infrastructure (`docker compose up -d` in `dispatch/`, `.env.test` from `env.test.example`), as F37 does.

### Defect (reproduced on the live stack, 2026-11-05)

- `frontend/src/app/owner/restaurants/[id]/menu/page.tsx:48-50` keeps a `photo` state, prefilled with an Unsplash URL, and `:117` always sends it in `createDish`'s `input`.
- `CreateDishInput` (`src/restaurants/dtos/create-dish.dto.ts`) is `PickType(Dish, ['name', 'priceCents', 'description', 'options'])` plus `restaurantId`. `Dish.photo` exists (`src/restaurants/entities/dish.entity.ts`, nullable column, nullable GraphQL field) but is not picked.
- GraphQL variable coercion therefore fails before the resolver runs: HTTP 400, `Variable "$input" got invalid value { ... }; Field "photo" is not defined by type "CreateDishInput".` Every Add dish attempt fails. During F37's live check the dish was created through GraphQL by hand.
- **Price field.** `priceDollars` starts as `'12.00'` (`:46`). Typing after it gives `12.0014.50`, and `dollarsToCents` (`frontend/src/lib/currency.ts`) uses `parseFloat`, which stops at the second dot: `parseFloat('12.0014.50')` is `12.0014`, so the dish is saved at **1200 cents with no error**. Unparseable text becomes 0 cents. The option extra prices (`'0.00'`, `'3.00'`, `'1.00'` defaults) go through the same function.
- **Name and description length.** `Dish.name` is `@Length(5)` and `Dish.description` `@Length(5, 256)`. The production `ValidationPipe` (`src/main.ts`) rejects shorter values with a GraphQL "Bad Request Exception", which the page shows as "Submission failed". A dish called `Taco` cannot be added, and the form does not say why.

### Decisions

1. **Accept `photo` (user, 2026-11-05).** `CreateDishInput` and `EditDishInput` pick `photo` as well. The column already exists, so there is no migration. `EditDishInput` gets it too: both inputs list the same fields today, and an owner who can set a photo should be able to change it. `editDish` already spreads its input into the saved row (`restaurants.service.ts:287-292`), so no service change is needed.
2. **`@IsOptional()` on `Dish.photo`.** `PickType` copies class-validator metadata, and `Dish.photo` has `@IsString()` without `@IsOptional()`. Without the change, the production `ValidationPipe` would refuse every dish **without** a photo ("photo must be a string"). The e2e app (`test/utils/e2e.ts`) installs no `ValidationPipe`, so only the unit spec V1–V5 catches this. The column is nullable, so the validator now matches it.
3. **One pure helper builds the `createDish` input.** `frontend/src/lib/dish-form.ts` `createDishInput(form)` validates the form and returns the exact variables. The page calls it, Vitest tests it, and the dispatch e2e **imports the same file** to coerce its output against the live schema. The defect was the page's variables, not the document, so a document-only check would have passed. Importing a dependency-free frontend `.ts` file from a dispatch Jest test works under ts-jest (checked on 2026-11-05 with `frontend/src/lib/currency.ts`). `dish-form.ts` may import only `./currency`, with no `@/` aliases and no React.
4. **Strict money parsing.** New `parseDollars(text)` in `currency.ts` accepts `^\d+(\.\d{1,2})?$` after trimming and computes cents with integer arithmetic (no `parseFloat`). `dollarsToCents` is deleted: the menu page was its only caller, and it turns wrong input into a different price without an error.
5. **The price starts empty; the photo starts empty.** The price shows the placeholder `For example: 14.50`. The prefilled Unsplash photo URL goes too: it gave every new dish the same salad picture. An empty photo is left out of the input, so the dish has no photo and the cards show none, as they do today for dishes without one. The extra-price inputs keep their defaults, but select their text on focus so typing replaces it, and strict parsing refuses `3.001.00`.
6. **Base price must be more than $0.00.** A zero-price dish makes a zero-total order. Extras may be `0.00`.
7. **Mutation documents are checked without side effects.** The new `test/storefront-mutations.e2e-spec.ts` takes the schema from the running app (`GraphQLSchemaHost`). For each document and each variables shape its page sends, it runs `validate(schema, parse(document))` and `getVariableValues(schema, variableDefinitions, variables)`. These are graphql-js's own validation and variable-coercion steps, the ones that produced the 400, and nothing executes. Separate tests then run `createDish` and `editDish` for real, to prove the photo is saved.
8. **`CreateRestaurantOutput.restaurantId` becomes nullable (audit finding).** See "What was checked".

### `dispatch/frontend/src/lib/dish-form.ts` (new)

Imports only `{ parseDollars } from './currency'`. It must not import React, `@/` paths or anything else, because the dispatch e2e imports it (decision 3). Say so in a file comment.

```ts
export interface DishChoiceForm {
  name: string;
  extraDollars: string;
}

export interface DishOptionForm {
  name: string;
  choices: DishChoiceForm[];
}

export interface DishForm {
  restaurantId: number;
  name: string;
  priceDollars: string;
  description: string;
  photo: string;
  options: DishOptionForm[];
}

/** The `input` variable of CREATE_DISH_MUTATION; keys match CreateDishInput (F38). */
export interface CreateDishVariables {
  restaurantId: number;
  name: string;
  priceCents: number;
  description: string;
  photo?: string;
  options?: { name: string; choices: { name: string; extraCents: number }[] }[];
}

export type DishFormResult =
  | { ok: true; input: CreateDishVariables }
  | { ok: false; error: string };

export function createDishInput(form: DishForm): DishFormResult;
```

`createDishInput` checks in this order and returns the first failure:

1. `name = form.name.trim()`. If `name.length < 5`: `{ ok: false, error: 'The dish name needs at least 5 characters' }`.
2. `priceCents = parseDollars(form.priceDollars)`. If `null`: `'Enter the price in dollars, for example 14.50'`. If `0`: `'The price must be more than $0.00'`.
3. `description = form.description.trim()`. If `length < 5 || length > 256`: `'The description needs 5 to 256 characters'`.
4. For each option, then each choice: `extraCents = parseDollars(choice.extraDollars)`. If `null`: `` `Enter the extra price for "${choice.name.trim()}" in dollars, for example 1.50` ``. Option and choice names are trimmed.
5. `photo = form.photo.trim()`.

On success it returns `{ ok: true, input }`. `input` is built in this key order and **has no key whose value is `undefined`**: `restaurantId`, `name`, `priceCents`, `description`, then `photo` only if non-empty, then `options` only if `form.options.length > 0` (each `{ name, choices: [{ name, extraCents }] }`). The limits 5 and 256 mirror `@Length` on `Dish` (`dish.entity.ts`). Say so in a comment.

1. Delete `dollarsToCents`.
2. Add:

   ```ts
   /**
    * Parses a dollar amount typed by a person into integer cents (F38).
    * Accepts digits with an optional point and one or two decimals, after trimming:
    * "14", "14.5", "14.50". Anything else (empty, "12.0012.00", "14.505", "-1",
    * "1,000", "$14", "1e3", ".5") is null, never a different amount.
    * Integer arithmetic only, no parseFloat.
    */
   export function parseDollars(text: string): number | null;
   ```

   `const match = /^(\d+)(?:\.(\d{1,2}))?$/.exec(text.trim()); if (!match) return null; const cents = Number(match[1]) * 100 + Number((match[2] ?? '').padEnd(2, '0')); return Number.isSafeInteger(cents) ? cents : null;`

## Risks

- **Importing frontend files into a dispatch Jest run.** `dish-form.ts`, `currency.ts`, `order-actions.ts` and `types.ts` must stay free of React, `@/` aliases and browser globals. If one of them gains such an import, the e2e fails to compile, loudly; it does not skip silently. The file comment in `dish-form.ts` says so. Checked on 2026-11-05: ts-jest under `dispatch/tsconfig.json` compiles `frontend/src/lib/currency.ts` from outside its `include`.
- **Hand-written M2 rows can drift from their pages.** Only `CREATE_DISH_MUTATION` and the failed-delivery `EDIT_ORDER_MUTATION` take their variables from the page's own helper. The other rows mirror the call sites listed in "What was checked", which a reviewer must compare when a page changes. This is the same limit F37's S2 rows have.
- **`getVariableValues` and `validate` are graphql-js internals of the HTTP path.** Apollo Server runs exactly these before executing (the live 400 came from variable coercion), so a row that passes M2 is not refused at the GraphQL layer. Class-validator still runs after that in production, which is why V1–V5 exist.
- **Nullable `restaurantId`.** Schema clients that generated non-null types would see a looser type. The only client is the storefront, which reads `restaurantId` only when `ok` is true (`owner/restaurants/page.tsx`).
- **Existing dishes.** Untouched: there is no migration, `photo` stays as stored, and dishes created by hand during F37's live check keep their photo.
