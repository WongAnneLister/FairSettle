## Changes

### `docs/adr/paypal-state-mapping.md` (new)

English. Status line: `Status: Accepted · Date: 2026-10-22 · Feature: F03`. Links line to the five ledger docs listed above and to `paypal-samples/SUMMARY.md` (relative paths from `docs/adr/`, e.g. `../../ledger/docs/state-machines/payment.md`).

Sections, in this order, with this content:

#### 1. Context

Three short paragraphs:

- PayPal Orders v2 with `intent=CAPTURE` is a two-step flow: the buyer approves on PayPal, then the merchant must call capture. Stripe Checkout (the existing adapter) captures automatically, so the ledger has no capture step today. Money cannot move before the ledger calls capture.
- The ledger keeps four orthogonal dimensions per payment (`payment_status`, `provider_status`, `resolution_status`, `financial_status`) and has no FAILED payment status. This ADR maps PayPal onto them without adding statuses.
- Facts verified in the sandbox (F02 run 20261022170335): same `PayPal-Request-Id` on create, capture and refund returns the original object (samples 02, 06, 09); capture before approval is 422 `ORDER_NOT_APPROVED` (03); capture with a new request id after success is 422 `ORDER_ALREADY_CAPTURED` (07); over-refund is 422 `REFUND_AMOUNT_EXCEEDED` (10). PayPal documents that create and capture request ids are stored for 6 hours; the refund endpoint documents no retention. The 6-hour figure is documented, not measured.

#### 2. Decisions (numbered rules D1–D12)

Write each as one or two sentences:

- **D1 No new payment or refund statuses.** PayPal maps onto the existing `PaymentStatus` and `refund_status` values. No migration changes the `payment_status` or `refund_status` CHECK.
- **D2 Approved-not-captured** is defined as `payment_status=PROCESSING` and `provider_status='APPROVED'` and `captured_amount_minor=0`. It is the state F06 asserts. PROCESSING is correct because the buyer has finished and the remaining step is ours (payment.md §2: "submitted and provider processing").
- **D3 `provider_status` holds the raw PayPal order status** (`CREATED`, `PAYER_ACTION_REQUIRED`, `APPROVED`, `COMPLETED`, ...), never a capture or refund status. Capture status is kept raw on the payment attempt; refund status raw on the refund's `provider_status`.
- **D4 A PayPal capture is the payment attempt.** Capture id plays the role of the charge id: it is the refund anchor (F08) and the normalized fact key is `CAPTURE:<capture id>`, so a webhook and a query of the same capture count once.
- **D5 Only the ledger starts a capture**, and only after authoritative evidence of approval: a GET order showing `APPROVED`, or a verified `CHECKOUT.ORDER.APPROVED` webhook. The buyer's return to `return_url` is level-5 evidence (payment.md R3): it only triggers a GET order. The capture is a new operation type `CAPTURE_ORDER`, one per payment (existing unique `(payment_id, operation_type)`), prepared in the same transaction that records approval. Order creation reuses `CREATE_CHECKOUT`. Adding `CAPTURE_ORDER` to the `operation_type` CHECK belongs to F06.
- **D6 PayPal-Request-Id = the operation's persisted `operation_key`.** Never a new id for the same operation (X1). Create, capture and each refund have different keys (provider-operation.md §3).
- **D7 Retention used for automatic resend: 5 hours** from the operation's first send for create and capture (documented 6 h minus 1 h margin). Refunds: no automatic resend at all, because PayPal documents no retention for the refund endpoint.
- **D8 Capture timeout: query, never resend blindly** (full path in §5). This is the core rule of this ADR.
- **D9 Financial evidence.** For PayPal there is no balance-transaction import (that module is off limits). The `seller_receivable_breakdown` (gross, `paypal_fee`, net) on a capture with status `COMPLETED` is the financial evidence for posting. A capture in any other status posts nothing. Amounts are converted from PayPal's decimal strings to integer minor units exactly (no floating point); a value with more decimals than the currency allows is `CONTRACT_MISMATCH`.
- **D10 Webhooks are level-3 evidence** (payment.md §6): they may move state forward along allowed transitions, never backwards, and a terminal state never changes because of one. A webhook that contradicts a recorded fact makes the object CONFLICT, it does not pick a side.
- **D11 Requests use `Prefer: return=representation`** on create, capture and refund, so the response carries full status and amounts (the refund sample 08 was minimal and lacked the amount).
- **D12 Refund correlation.** Every refund request sets `custom_id` = the ledger refund id (UUID). Refund recovery finds refunds through GET order `purchase_units[].payments.refunds[]` by `custom_id`.

#### 5. Capture call outcomes and the timeout path

| Outcome | classification | operation | payment | Next step | Ref |

| 5xx | RETRYABLE_TRANSIENT | UNKNOWN | resolution UNKNOWN | as timeout | |
| No response / read timeout | TIMEOUT_UNKNOWN | UNKNOWN | PROCESSING, provider_status stays `APPROVED`, resolution UNKNOWN | the path below | O4, T3 analog |

Then the timeout path as a numbered list and an ASCII decision tree in the style of provider-operation.md §7. The order id is always known at capture time (it is the operation's `external_object_id`), so recovery always starts with a query:

1. GET `/v2/checkout/orders/{id}` (level-2 evidence).
2. Order `COMPLETED` with one capture → adopt it per §4; operation RESOLVED (O5). No capture is sent.
3. Order `APPROVED` with no capture → resend capture **only** with the original `PayPal-Request-Id`, **only** while less than 5 hours have passed since the operation's first send (D7), **only** right after this GET in the same recovery attempt (O7). PayPal returns the original capture if the first request was accepted.
4. Order `APPROVED` with no capture and the 5 hours have passed → ESCALATED (O8). No resend, no new request id, not marked failed.
5. Order `VOIDED` and no capture → payment CANCELED (T9), operation RESOLVED.
6. GET times out, 5xx, 429 or 404 → stay UNKNOWN, L1 backoff (provider-operation.md §8); after the age limit, ESCALATED.
7. Rejected forever: a new request id (X1), resend outside the window (X3), resend without a fresh GET, "waited long enough" (X5), marking the payment failed (X2).

#### 6. Order creation outcomes

Short table for `POST /v2/checkout/orders` (operation `CREATE_CHECKOUT`): 200/201 → SUCCESS, AWAITING_CUSTOMER (T2); same request id → same order (sample 02); 400/422 → DEFINITIVE_REJECT, payment may be CANCELED only if no order id was ever recorded (T10, `ProviderResultRules.rejectLeftRemoteTrace`); timeout/5xx → UNKNOWN (T3). Timeout recovery: PayPal has no order search, so the only recovery is a resend with the original request id within 5 hours (O7); after that ESCALATED (O8). Note that an unapproved duplicate order moves no money, but the rule stays the same.

#### 8. Webhook events and ordering

Table, columns: Event | Resource | Effect | Ref. Exactly these rows:

| Event | Resource | Effect |
| --- | --- | --- |
| `CHECKOUT.ORDER.APPROVED` | order | Same as GET showing `APPROVED` (§3): approved-not-captured, prepare `CAPTURE_ORDER` once |
| `CHECKOUT.PAYMENT-APPROVAL.REVERSED` | order | No direct state change; schedules a GET order and the result is applied per §3 |
| `PAYMENT.CAPTURE.COMPLETED` | capture | Per §4 `COMPLETED`; anchored to the payment through `supplementary_data.related_ids.order_id` |
| `PAYMENT.CAPTURE.PENDING` | capture | Per §4 `PENDING` |
| `PAYMENT.CAPTURE.DECLINED` | capture | Records the attempt; payment stays PROCESSING; CANCELED only after a GET (§4) |
| `PAYMENT.CAPTURE.REFUNDED` | refund | Per §7 `COMPLETED`, matched by refund id, else by `custom_id` |
| `PAYMENT.REFUND.PENDING` | refund | Per §7 `PENDING` |
| `PAYMENT.REFUND.FAILED` | refund | Per §7 `FAILED` |
| `PAYMENT.CAPTURE.REVERSED` | capture | Stored in the inbox and left unprocessed (WAITING); reversal belongs to the dispute module, which is out of scope |
| any other event, incl. `CHECKOUT.ORDER.COMPLETED` (marketplaces only) | | Stored, not processed |

Ordering rules, numbered:

1. Verification first (F09): an event that fails or times out on verification is never stored as verified and never changes state.
2. Transport dedup by event id in the existing `webhook_inbox` (unique per provider account and event id).
3. Semantic dedup: a capture seen by query and by webhook is one fact (`CAPTURE:<capture id>`, D4); a refund by its PayPal refund id.
4. Staleness: the resource's `update_time` is the event time used by `PaymentEvidenceRules.isStale`; an event older than the last webhook, or not newer than the last successful query, does not change state.
5. Terminal never regresses: payment SUCCEEDED and refund SUCCEEDED/FAILED/CANCELED do not change on any later event (R1, refund.md §7). A contradicting event (different amount, currency, order, or terminal→other terminal) → CONFLICT.
6. An event whose order or capture is not yet known locally (e.g. `PAYMENT.CAPTURE.COMPLETED` before the capture response was written) goes to the existing `dependency_wait` and is retried; it is not dropped.
7. A webhook can skip intermediate states (T8): `PAYMENT.CAPTURE.COMPLETED` while the payment is still AWAITING_CUSTOMER moves it to SUCCEEDED.
8. A webhook alone never cancels a payment or releases a refund hold that a query has not confirmed — except `PAYMENT.REFUND.FAILED`, which is an explicit failure (F6).

#### 9. Rejected alternatives

Table with these rows and reasons:

- Add a new `APPROVED` payment_status: needs a migration on a CHECK used by Stripe code paths and every status switch; PROCESSING + provider_status carries the same fact (D2).
- Capture directly on the buyer's return without a GET: the return is not evidence (R3); a GET costs one call and the capture would be rejected anyway if not approved.
- On capture timeout, resend capture immediately: within 6 h this is usually safe, but a resend without a GET hides `ORDER_ALREADY_CAPTURED` cases and outside the window can be treated as a new request (X3).
- Resend refunds with the original request id after a timeout: refund retention is undocumented; a second refund is a real loss.
- Treat `ORDER_ALREADY_CAPTURED` as a rejection: it proves a capture exists; treating it as failure would cancel a paid payment.
- Use the capture webhook as the only capture signal: webhooks are late, duplicated and out of order; the capture response and GET order are authoritative.

#### 10. Consequences

Positive and negative, a few bullets each: no schema change for statuses; one new operation type in F06; payments can sit in approved-not-captured if the worker is down (L2 scan finds PROCESSING with an open `CAPTURE_ORDER`); refunds with lost responses need a person more often than Stripe ones; financial posting for PayPal does not wait for a balance-transaction import.

#### 11. Verification ownership

Table mapping rules to the features that implement and test them: D5/D2 → F06 (`PaymentStateMachinePayPalTest`); §5 timeout path → F07 (`PayPalCaptureUnknownTest`); §7 → F08; §8 rules 1–2 → F09; §8 rules 3–8 → F10; D6/§6 → F05; 401 refresh → F04; real sandbox run of the whole map → F12.

## Deviations

Filled in during review: what changed from this plan, why, and in which commit.

- Written by Claude Code instead of Codex, at the author's request.
- The plan called `DECLINED`/`FAILED`/`VOIDED`-after-approval cancellation "T9-equivalent". payment.md has no PROCESSING → CANCELED transition, so the ADR names it P1 (PayPal only) with its guard, and records that `PaymentEvidenceRules.decide` already allows it on complete unpaid query evidence. Same decision, made explicit.
- Transition references in the ADR are prefixed with their document (`payment T7`, `refund F3`, `op O4`), because payment.md's R1–R7 and ADR-0003's R1–R8 would otherwise collide.
- The `EXTERNAL_CONFLICT` move on `REFUND_AMOUNT_EXCEEDED` is noted in the ADR as an extension of refund.md §3 (inferred, not ingested, external refund).
