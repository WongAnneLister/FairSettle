## Existing code to follow

There is nothing to copy. These files define what "the whole suite" is; read them, do not change them:

- `ledger/pom.xml`:
  - surefire runs everything except `**/*IT.java`;
  - failsafe runs `**/*IT.java` and is bound to `integration-test` and `verify`;
  - Spotless is **not** bound to `verify` (decision 6).
- `ledger/src/test/java/**/*Fixture.java`: abstract bases with one `@Test` each, run through their `*IT` subclasses. They are not orphaned tests. Every class with a test method ends in `Test` or `IT` (checked while planning).
- The Testcontainers ITs start their own PostgreSQL, Redis and Kafka. `docker compose up` is not needed, but the Docker daemon is.
- PayPal ITs read `../docs/adr/paypal-samples/*.json` (e.g. `PayPalCaptureIT`, `PayPalRefundIT`, `PayPalWebhookPostingIT`). The run therefore needs the whole repository, not only `ledger/`.
- `scripts/features.py`:
  - `verify` refuses to run with dirty tracked files, records `git rev-parse HEAD` and runs the command under `bash` with a 1800 s timeout (`VERIFY_TIMEOUT_S`);
  - `check` re-hashes every evidence log and checks that its commit exists.

## Design decisions (fixed)

1. **No production or test code changes.** The work commit contains only `docs/features.json` from `start`. If the run is green, that is the whole feature.
2. **The three real-contract ITs stay skipped.** Do not set any of these on the verification host: `PR06_STRIPE_CONTRACT`, `PAYOUT_REAL_READ_TESTS`, `STRIPE_CONTRACT_TESTS`, or any `STRIPE_*` / `PAYPAL_*` variable. They need real credentials, and AGENTS.md is sandbox only, with no credentials anywhere. Real PayPal checks are F12.
3. **"With the PayPal adapter in place" means in the build, not active alongside Stripe.** A process selects exactly one provider:
   - `PayPalCheckoutConfiguration#scope` throws `Select exactly one provider implementation` if Stripe or the fake is also enabled;
   - `PayPalCreateOrderTest#checkoutConfiguration` and `StripeAdapterConfigurationTest` already pin this.

   No coexistence test is added.
4. **Verification runs on a Docker host from a git checkout of the work commit.** The Windows dev machine has no Docker, so it cannot run `verify`. The host needs:
   - JDK 21;
   - a running Docker daemon;
   - `bash`, `git` and `python3`;
   - a full clone whose `HEAD` is the work commit.

   The VPS used for F08–F10 qualifies once it has a real clone (until now it only had copied sources). The commit gets there by `git bundle`, and nothing is pushed. `docs/features.json` and `docs/evidence/F11.log` come back byte for byte.
5. **Any failure stops F11.** A red, flaky or timed-out run is not fixed under this plan. The implementer reports it (Steps, step 6) and does not edit code, tests, `pom.xml`, `scripts/features.py` or its timeout. A fix needs a plan amendment. If the fix belongs to an earlier feature's code (F05–F10), it is that feature's review fix.
6. **Spotless is checked, but outside the verification command.** `./mvnw spotless:check` is a pre-flight check (C1), because CI blocks on it. It is not part of `verify` and is not added to it.

Report summary for R2–R4. Run it from `ledger/` after R1. It is a one-off command; do not save it as a file in the repository.

```bash
python3 - <<'EOF'
import glob, xml.etree.ElementTree as ET
for phase in ("surefire", "failsafe"):
    t = f = e = s = 0; skipped = []; paypal = stripe = 0
    for path in glob.glob(f"target/{phase}-reports/TEST-*.xml"):
        r = ET.parse(path).getroot()
        n = int(r.get("tests")); t += n
        f += int(r.get("failures")); e += int(r.get("errors"))
        k = int(r.get("skipped")); s += k
        name = r.get("name").rsplit(".", 1)[-1]
        if k: skipped.append(name)
        if name.startswith("PayPal"): paypal += n
        if name.startswith("Stripe"): stripe += n
    print(f"{phase} tests={t} failures={f} errors={e} skipped={s}")
    print(f"  skipped: {sorted(skipped)}  PayPal*={paypal} Stripe*={stripe}")
EOF
```

If R2 shows different totals but 0 failures, 0 errors and exactly the three expected skips, still stop before V1. Report both numbers. A different count means tests were discovered differently from the F10 run, and someone has to explain why before it becomes evidence.

## Risks

- **No Docker on the dev machine.** Handled by decision 4. Running `features.py verify F11` there fails at the first IT, and F11 stays `active` with a failing `docs/evidence/F11.log`. That is harmless: a failed `verify` does not touch `docs/features.json`, and the next `verify` overwrites the log. Delete the stray `docs/evidence/F11.log` anyway before step 8.
- **The run takes longer than the 1800 s gate timeout.** R1 measures it first. If `real` is 25 min or more, stop and report the time; do not change `VERIFY_TIMEOUT_S`.
- **Flaky ITs (Kafka, timing).** If R1 fails, rerun only the failing class once: `./mvnw -B -Dit.test='<Class>' -Dtest='NoSuchTest' -Dsurefire.failIfNoSpecifiedTests=false verify`. Report both results. A test that passes on rerun is still reported as flaky, and F11 still stops (decision 5).
- **Docker resource limits on the VPS** (disk, memory, container start timeouts) look like test failures. Before calling a failure a code problem, check `docker system df` and the first stack trace in `f11-run.log`.
- **Evidence moved between machines.** `features.py check` hashes `docs/evidence/F11.log` as UTF-8 text, and `core.autocrlf` is `false`, so a byte-for-byte copy keeps the hash. Copy with `scp`, not through an editor. V2 on the dev machine proves the copy.
- **A stale `target/`.** R1 and V1 both start with `clean`, so classes from another checkout or an older commit cannot hide a failure.
