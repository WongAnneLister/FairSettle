# F22 · Propose, pause, resume

## Goal

Behavior (copied from docs/features.json):

> A passing decision is submitted as a proposal; the graph pauses with state in Postgres; after a process restart, approval resumes the same thread without resubmitting.

Verification (copied from docs/features.json):

```bash
cd agent && python -m pytest -q tests/test_resume.py
```

F22 turns F21's functions into a LangGraph graph with a Postgres checkpointer, one thread per complaint:

1. **gather** (F21 `gather`), then **count** the customer's complaints in the last 7 days (PRD rule 6 input, F20 decision 9), then **decide** (F21 `decide`, which runs F20's policy).
2. A `propose` verdict is **submitted** to the ledger as a refund proposal (`POST /v1/refund-proposals`, F18). Any other outcome ends the thread with no ledger write: the contract says reject and escalate "stay with the agent and are never submitted as proposals".
3. The thread **pauses** with `interrupt()`. Its state is in Postgres.
4. Later, possibly in a new process, `Agent.poll()` reads the proposal (`GET /v1/refund-proposals/{id}`; the contract says "There is no webhook to the agent"). When a person has approved or rejected it, the same thread resumes from its checkpoint and **finishes**. Nothing before the pause runs again: no gather, no model call, no second POST.

Execution after approval (following `refundId`) and Langfuse are F23. The long-running process that calls `poll()` on a timer, and the compose service, are F24.

### Decisions made with the user (2026-10-29)

- **F22 counts complaints per customer** in the agent's own Postgres table. F21's `Complaint` keeps `prior_complaints_in_7_days`; callers now submit a `ComplaintInput` without it, and the graph fills it in.
- **Tests start Postgres with Testcontainers** (`postgres:16`, as the ledger ITs do). The verification command needs Docker running and nothing else. Without Docker the tests **fail**; they never skip.
- **The agent's ledger credential comes from the environment only** (`LEDGER_BASE_URL`, `LEDGER_APP_TOKEN`). F22 changes no ledger production code. F24 seeds a second credential of dispatch's ledger application (F14 note: payment reads are filtered by application, so any other application gets 404).
- **Proposal wire format is proven by recorded fixtures.** `AgentFixturesHttpIT` (ledger test code only) gains a test that records seven proposal fixtures from the real ledger, as F19 did.
- **F19's credential check is made precise.** `test_fixtures_contain_no_credentials` bans the substring `ops_`, but a real decided proposal contains `"role": "OPS_REVIEWER"`. The plain `ops_` substring is replaced by a regex for the real ops token shape (`ops_<uuid>.`); every other banned string stays. This is a deliberate change to an F19 assertion, approved by the user.

### What was checked while planning (Python 3.11, network on for PyPI only)

- These pins resolve together with every existing pin unchanged (93 packages, no `psycopg2`): `langgraph==1.2.18`, `langgraph-checkpoint==4.3.1`, `langgraph-checkpoint-postgres==3.2.0`, `psycopg[binary]==3.3.6`, `psycopg-pool==3.3.3`, dev `testcontainers[postgres]==4.15.0`.
- **The node that calls `interrupt()` runs again from its first line on resume.** A probe graph `submit → wait(interrupt)` ran `submit` once and `wait` twice. So the review node must do nothing before `interrupt()`, and the ledger POST must be in a separate node that completed before the pause (decision 6).
- **Resuming a finished thread is a no-op** that returns the final state.
- **`Command(resume=…)` on a thread with no checkpoint silently starts a new run from `START`.** So `poll()` checks that the thread is really waiting before it resumes (decision 9).
- **A node that raises leaves the thread at the last checkpoint.** `ainvoke(None, config)` later re-runs only the failed node (probe: `a` ran once, the failing `b` twice). This is the retry path for a failed submit (decision 7).
- **The checkpoint serializer only warns on unregistered Pydantic types now, and with `LANGGRAPH_STRICT_MSGPACK=true` silently turns them into plain dicts.** "This will be blocked in a future version." So graph state holds JSON values only (decision 4).
- `ainvoke` takes `durability`; F22 always passes `durability="sync"`, so the checkpoint is written before `ainvoke` returns.
- `AsyncPostgresSaver(conn)` accepts an `AsyncConnectionPool`; its own `from_conn_string` opens connections with `autocommit=True, prepare_threshold=0, row_factory=dict_row`, so the pool uses the same. `await saver.setup()` must be called once; it creates `checkpoint_migrations`, `checkpoints`, `checkpoint_blobs`, `checkpoint_writes`.
- **psycopg connects through libpq (C), so F21's `socket.socket.connect` guard does not block the test database.** A psycopg connect to `127.0.0.1:9` under the guard raised psycopg's `OperationalError`, not the guard's `AssertionError`.
- **The Docker SDK under Testcontainers uses Python sockets**, so the guard blocks it. The container is started in a session-scoped fixture, which pytest sets up before the function-scoped `no_network` guard and tears down after it.
- Testcontainers 4.15: import `PostgresContainer` from `testcontainers.community.postgres` (the old path warns `DeprecationWarning`). `PostgresContainer("postgres:16", driver=None).get_connection_url()` gives a plain `postgresql://` URL.
- Docker was not running on this Mac while planning, so the Postgres saver itself was not run here; the probes used `InMemorySaver`, which uses the same serializer and the same resume logic.
- **Ryuk is disabled** (plan amendment, 2026-10-29, after Codex stopped at Step 6). Testcontainers-python 4.15.0 starts a Ryuk container (`testcontainers/ryuk:0.8.1`) that cleans up after a crashed run, and it failed in two ways on Docker Desktop for Mac:
  - Codex: `ConnectionError: Port mapping for container … and port 8080 is not available`, twice. `DockerClient.port()` asks Docker for Ryuk's port mapping exactly once, with no retry; a moment later the mapping existed.
  - Here: `APIError 500 … mkdir /host_mnt/Users/anne_lister/.docker/run/docker.sock: operation not supported`. It mounts the Mac's socket path into Ryuk, a path that does not exist inside Docker Desktop's VM (Java Testcontainers mounts `/var/run/docker.sock`, which is why the ledger ITs work).

## Design decisions (fixed)

1. **One thread per complaint, and `thread_id == complaint_id`.** The complaint id pattern (`^[A-Za-z0-9._:-]{1,128}$`) fits the contract's `AgentRun.threadId` (1–128). A complaint id seen before is refused (`DuplicateComplaint`); it is never run twice.

2. **Input.** Callers submit `ComplaintInput`: `Complaint` without `prior_complaints_in_7_days` (same fields, same constraints, same strict base). The agent stamps `received_at` from its injected clock when it registers the complaint.

3. **The agent's own table**, created by `ComplaintStore.setup()` with `CREATE … IF NOT EXISTS` (no migration tool in the agent yet):

   ```sql
   CREATE TABLE IF NOT EXISTS agent_complaint (
       complaint_id    text PRIMARY KEY,
       order_id        bigint NOT NULL,
       customer_id     bigint,
       received_at     timestamptz NOT NULL,
       status          text NOT NULL CHECK (status IN (
                           'running', 'submitting', 'submit_retry', 'awaiting_review',
                           'approved', 'rejected', 'declined', 'escalated')),
       proposal_id     text,
       submit_attempts integer NOT NULL DEFAULT 0 CHECK (submit_attempts >= 0),
       updated_at      timestamptz NOT NULL
   );
   CREATE INDEX IF NOT EXISTS agent_complaint_customer ON agent_complaint (customer_id, received_at);
   CREATE INDEX IF NOT EXISTS agent_complaint_status ON agent_complaint (status);
   ```

   - It never holds the complaint text, the decision or any token. The thread id is the complaint id, so it needs no column.
   - `status` is for finding work (`poll`) and for `Agent.status`; the checkpoint is the source of truth for the run itself.
   - Final statuses: `approved`, `rejected` (by the reviewer), `declined` (a policy-passing `reject` decision), `escalated`.

4. **Graph state holds JSON values only** (`str`, `int`, `bool`, `None`, `list`, `dict`), never a model or dataclass. `RunState` is a `TypedDict` (`total=False`):

   | Key | Written by | Value |
   | --- | --- | --- |
   | `complaint` | `Agent.start` | `ComplaintInput.model_dump(mode="json")` |
   | `received_at` | `Agent.start` | ISO 8601 with offset |
   | `evidence` | gather, count | `{"order", "timeline", "payment", "refundable"}`: each `model_dump(mode="json", by_alias=True)`; plus `"prior_complaints_in_7_days": int` after count |
   | `verdict` | decide | `{"outcome": str, "decision_json": RefundDecision.model_dump_json(), "violations": [{"rule": str, "message": str}]}` |
   | `run` | decide | `{"model", "attempts", "prompt_tokens", "completion_tokens", "stage_ms"}` from F21's numbers |
   | `escalation` | any node | `{"stage", "reason", "detail"}` |
   | `proposal` | submit | `{"id", "status"}` |
   | `review` | await_review | `{"status", "refund_id", "rejection_reason", "reviewed_at"}` |
   | `final` | finish | the final status |

   Evidence is rebuilt with `Order.model_validate`, `OrderTimeline.model_validate`, `Payment.model_validate`, `RefundableAmount.model_validate` and `Evidence(...)`. The complaint text is in the checkpoint (the decide node needs it), never in `agent_complaint`.

5. **Graph** (`build_graph(deps) -> StateGraph`, compiled by `Agent` with the Postgres saver):

   ```
   START → gather ─┬─ escalation ──────────────────────────────┐
                   └→ count ─┬─ escalation ────────────────────┤
                             └→ decide ─┬─ not "propose" ──────┤
                                        └→ submit ─┬─ escalation┤
                                                   └→ await_review → finish → END
                                                                     ↑ (all branches)
   ```

   | Node | Does | Escalations (`stage`, `reason`, `detail`) |
   | --- | --- | --- |
   | `gather` | F21 `gather(complaint.to_complaint(0), dispatch, ledger)`; the `0` is replaced in `count` | a `GatherFailure` → `("gather", failure.reason, failure.detail)` |
   | `count` | `customer = evidence.order.customer`; `store.record_customer`; `store.count_prior`; writes `prior_complaints_in_7_days` | no customer → `("count", "customer_unknown", "order <id> has no customer")` |
   | `decide` | F21 `decide(complaint.to_complaint(n), evidence(n), model, policy, complete)`; writes `run`, and `verdict` or `escalation` | an F21 `Escalation` → `("decide", e.reason, e.detail)` |
   | `submit` | decision 7 | decision 7 |
   | `await_review` | `review = interrupt({"proposal_id": state["proposal"]["id"]})` as its **first statement**; then checks the review (decision 9) and returns it | none |
   | `finish` | decision 10 | none |

   Routing: after `gather`, `count`, `submit`: `"finish"` if `escalation` is in the state, else the next node. After `decide`: `"submit"` only when `verdict.outcome == "propose"`, else `"finish"`.

   `langgraph` is imported only in `graph.py` and `agent.py`.

6. **Side effects and replay.** A node runs again only if it raised or was interrupted (probes). Every store write in a node is idempotent (an `UPDATE` to a value, or `ON CONFLICT DO NOTHING`), so a re-run is harmless. The only ledger write is in `submit`, which completes before the pause, so a resume never reaches it again.

7. **Submit** (`POST /v1/refund-proposals`):
   1. `attempts = await store.begin_submit(complaint_id)`: one `UPDATE … SET status = 'submitting', submit_attempts = submit_attempts + 1, updated_at = now() … RETURNING submit_attempts`.
   2. `request = proposal_request(verdict, evidence, complaint_id, thread_id)` (decision 8); `proposal = await ledger.create_proposal(request)`.
   3. Success (201 created, or 200 replay of the same key and body): the returned proposal must have the request's `complaint_id`, `payment_id` and `amount_minor`, else `("submit", "proposal_mismatch", "<field> differs")` naming the first differing field in that order. Then `store.mark_awaiting(complaint_id, proposal.id)` and return `{"proposal": {"id", "status"}}`.
   4. A `ClientError` with `retryable` true (every `Unavailable`, and any ledger error body with `retryable: true`):
      - `attempts < max_submit_attempts` (default 3): `store.set_status(complaint_id, "submit_retry")`, then raise `SubmitDeferred(complaint_id)`. The thread stays at the `decide` checkpoint; `poll()` retries it with `ainvoke(None)` (decision 9).
      - otherwise: `("submit", "ledger_unavailable", "<ExceptionClass> after <attempts> attempts")`.
   5. Any other `ClientError`: `("submit", "proposal_refused", "<ExceptionClass>: <code>")`, with `<code>` the ledger code, or `HTTP <status>` when the body had none. No retry: a 4xx will not change.
   6. Any other exception propagates (a bug).

   A crash after the POST and before the checkpoint leaves `status = 'submitting'` and the thread at `decide`. `poll()` re-runs `submit`; the same key and body make the ledger replay the original proposal (200), so there is still exactly one proposal (test R23).

8. **Proposal mapping** (`proposal_request`), only for `verdict.outcome == "propose"` (else `ValueError`):

   | Contract field | Value |
   | --- | --- |
   | `complaintId` | `complaint_id` |
   | `orderRef` | `str(evidence.order.id)` |
   | `paymentId` | `evidence.payment.id` |
   | `decision` | `decision.decision.upper()`: `FULL_REFUND` or `PARTIAL_REFUND` |
   | `amountMinor` | `decision.amount_cents` |
   | `currency` | `evidence.payment.currency` |
   | `reasonCode` | `decision.reason_code.upper()` |
   | `liability` | three `{party: party.upper(), basisPoints}`, always in the order `RESTAURANT`, `DRIVER`, `PLATFORM`, whatever the decision's order |
   | `explanation` | `decision.explanation` |
   | `evidenceRefs` | `list(decision.evidence_refs)`, in the decision's order |
   | `agentRun` | `{"threadId": thread_id}`; no `traceId` (F23) |

   - The fixed party order makes the body identical on every retry, so the ledger replays instead of answering `IDEMPOTENCY_CONFLICT`.
   - Idempotency key: `refund-proposal:<complaintId>` (contract), at most 144 characters, within the ledger's 8–255 printable-ASCII rule.

9. **`Agent.poll()`**, one pass, under the agent's `asyncio.Lock` (decision 11). Rows are read with `store.resumable()`, ordered by `received_at`, then `complaint_id`:
   - `submitting` or `submit_retry`: `state = await graph.aget_state(config)`; `state.next` must be `("submit",)`, else `ThreadStateError(complaint_id, "not waiting to submit")`. Then `ainvoke(None, config, durability="sync")`; a `SubmitDeferred` is caught as in `start`.
   - `awaiting_review`: `proposal = await ledger.get_proposal(row.proposal_id)`.
     - A `ClientError`: skip this row for this pass (it stays `awaiting_review`) and continue with the next row.
     - `proposal.complaint_id != row.complaint_id`: `ThreadStateError(complaint_id, "proposal belongs to another complaint")`.
     - `PENDING_REVIEW`: skip.
     - `APPROVED` or `REJECTED`: `state.next` must be `("await_review",)`, else `ThreadStateError(complaint_id, "not waiting for review")` (a `Command` on a thread without a checkpoint would start a new run). Then `ainvoke(Command(resume=review), config, durability="sync")` with `review = {"status": proposal.status, "refund_id": proposal.refund_id, "rejection_reason": proposal.rejection_reason, "reviewed_at": proposal.reviewed_at.isoformat()}`.
   - Returns a `RunStatus` for each row whose status changed in this pass, in the order processed. A skipped row is not in the list.
   - `await_review` re-checks the resumed value: `status` `APPROVED` with a `refund_id`, or `REJECTED` with a `rejection_reason`; anything else → `ValueError` (a bug in `poll`).

10. **Finish** writes the final status, from the state:

    | State | `final` |
    | --- | --- |
    | `escalation` present | `escalated` |
    | `verdict.outcome == "escalate"` | `escalated` |
    | `verdict.outcome == "reject"` | `declined` |
    | `review.status == "APPROVED"` | `approved` |
    | `review.status == "REJECTED"` | `rejected` |

    `store.finish(complaint_id, final)` then returns `{"final": final}`. `approved` is where F23 inserts execution.

11. **Concurrency: one agent process.** `start` and `poll` share one `asyncio.Lock` per `Agent`, so a thread is never invoked twice at once inside a process. Two agent processes on one database are not supported in F22 (Risks).

12. **Counting (PRD rule 6).** `count_prior(customer_id, complaint_id, received_at)` counts rows with the same `customer_id`, a different `complaint_id`, and `received_at - interval '7 days' <= received_at < this received_at`. Every earlier complaint counts, whatever its outcome. `record_customer` runs before the count, so later complaints count this one.

13. **Configuration** (`AgentConfig.from_env(env: Mapping[str, str])`), every value required, else `ValueError("<NAME> is required")`:

    | Field | Variable |
    | --- | --- |
    | `database_url` | `FAIRSETTLE_DATABASE_URL` |
    | `dispatch_base_url` | `DISPATCH_BASE_URL` |
    | `dispatch_service_token` | `AGENT_SERVICE_TOKEN` (F19's dispatch token) |
    | `ledger_base_url` | `LEDGER_BASE_URL` |
    | `ledger_app_token` | `LEDGER_APP_TOKEN` |
    | `model` | `ModelConfig.from_env(env)` (F21) |

    `repr` shows the two base URLs and the model, and `<set>` for the database URL and both tokens. No value is ever logged.

## Risks

- **Two agent processes on one database** could invoke the same thread at once (`poll` in both). F22 supports one process; the lock is per process. F24 runs one agent. A database advisory lock per thread is the fix if that changes; recorded, not built.
- **A crash before `submit`** (in gather, count or decide) leaves the row `running` and the thread at an earlier checkpoint. `poll` does not pick it up, so it waits for a person or a later feature. Nothing was written to the ledger, so no money is at risk; F24 decides whether its process restarts such threads at startup.
- **Complaints from one customer arriving at the same moment** can miss each other in the count, because each records its customer after its own gather. The cost is a missed rule-6 escalation for a near-simultaneous pair; the ledger and a person still review every proposal.
- **A complaint that escalates in gather is never counted** (its customer is unknown). Accepted: it already went to a person.
- **The ledger may answer with an error code outside the contract.** F18's plan mentions `409 EVIDENCE_CONFLICT`, which is not in the contract's `ErrorCode` enum, so F19's client leaves `code` empty and the detail reads `HTTP 409`. The case still escalates; record it if it appears in recording.
- **LangGraph serialization will get stricter** ("This will be blocked in a future version"). JSON-only state (decision 4) and R11's round-trip check keep F22 independent of it.
- **The approved fixture depends on the fake provider accepting the reservation** that approval makes. `RefundProposalHttpIT` already approves over HTTP with the same seeding, so it should; if not, stop (ledger finding).
- **Docker pulls on this Mac hang sometimes** (`docs/progress.md`). Pull `postgres:16` before running the tests or `verify`.
- **Without Ryuk, a hard kill leaves the container running** (`kill -9`, a crashed interpreter). A normal failure or Ctrl-C still runs the `finally`.
