# F06 · Approval return and capture

## Goal

Behavior (copied from docs/features.json):

> After buyer approval the payment moves to approved-not-captured, then capture moves it to succeeded and posts balanced ledger entries; capture is idempotent.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='PayPalCaptureTest,PaymentStateMachinePayPalTest' test
```

Both are unit tests (no Docker). The end-to-end flow (create → approval → capture → posting) also gets an integration test, `PayPalCaptureIT`, which runs under `./mvnw verify` and must pass before the work commit.

### The flow in one paragraph

The buyer returns from PayPal. Returning is not evidence (payment R3); it only leads the merchant to call `GET /v1/payments/{id}` (or the worker's recovery query of the `CREATE_CHECKOUT` operation runs). Either one does a GET order. If the order is `APPROVED` with no capture, the merge leaves the payment approved-not-captured (ADR D2: `PROCESSING`, `provider_status='APPROVED'`, captured 0, `KNOWN`) and, in the same transaction, prepares the payment's single `CAPTURE_ORDER` operation (ADR D5). The capture is sent with `PayPal-Request-Id` = the operation key (ADR D6). After a 2xx, the ledger does a fresh GET order and merges it. A `COMPLETED` capture makes the payment `SUCCEEDED`. Its `seller_receivable_breakdown` (ADR D9) is written as a balance transaction and posted through the existing financial replay, which writes the balanced journal and sets `financial_status=POSTED`.

## Design decisions (fixed)

1. **New port `OrderCapturePort`** (`queryOrder`, `captureOrder`), implemented by the existing `PayPalCheckoutAdapter`. It is the same bean as the `CheckoutPort`. Stripe and Fake do not implement it. When it is absent (`orders == null`), every existing code path behaves exactly as today.
2. **One GET per PayPal query.** When `orders != null` and the payment has a `checkout_session_id`, `ProviderQueryService` makes one `queryOrder` call instead of session/intent/charges. The order's captures become `ChargeFact`s and the order becomes the session fact. `payment_intent_id` stays null for PayPal.
3. **A capture is a charge (ADR D4).** `ChargeFact.chargeId` = capture id and `paymentIntentId` = order id (the attempt column is NOT NULL). `balanceTransactionId` = capture id when a settlement exists. Normalized fact key: `CAPTURE:<capture id>` (existing `captureFactKey`).
4. **Capture status on the attempt is normalized, raw status in the observation.** `COMPLETED`, `PARTIALLY_REFUNDED`, `REFUNDED` → `succeeded` (captured). `PENDING` → `pending`. `DECLINED`, `FAILED` → `failed`. The raw status goes to `ChargeFact.outcomeType`, which is persisted in the observation fact. `status_details.reason` goes to `failureCode`, which is persisted on the attempt. Reason: `capturedAmount()`, `confirmsCapture()` and `FinancialReplayService` all read `provider_status='succeeded'`, and the replay is in a module this feature must not change beyond one new class. This refines ADR D3's last sentence; the ADR is updated in the work commit (Changes, last entry).
5. **Settlement = balance transaction.** Only a `COMPLETED` capture with a `seller_receivable_breakdown` yields a settlement `BalanceTransactionFact`:
   - `btId` = capture id, `type` `charge`, `amountMinor` gross, `feeMinor` paypal_fee (missing → 0), `netMinor` net.
   - `currency` as given, `balanceDomain` `PAYMENTS`, `sourceObjectId` capture id, `sourceObjectType` `charge`, `status` `available`.
   - `createdAt` = capture `create_time`, `availableOn` null.
   - `feeDetails` = `[FeeDetail(fee, currency, "paypal_fee", null)]` if fee > 0, else empty.
   - `rawDigest` = digest of `"paypal-capture|" + id + "|" + gross + "|" + fee + "|" + net`.

   A missing breakdown means no settlement (the payment is `SUCCEEDED`, `PENDING_EVIDENCE`). An inconsistent breakdown makes the whole query result `CONTRACT_MISMATCH`.
6. **Posting runs after the merge commits, in its own transactions** (`CaptureSettlementService`, new, in `financialingestion`). The user approved new code in `financialingestion` for F06: this service and its repository `financialingestion/repository/CaptureSettlementRepository`. No existing file in that module changes. The service inserts the balance transaction if absent and then calls `FinancialReplayService.replay`. A failure there never rolls back the capture fact. Retry comes for free: `financial_status` stays `PENDING_EVIDENCE`, the next query (GET payment or L2 wake) records again, and the insert and replay are idempotent.
7. **Posting needs the account's ingestion policy.** If `platform.lock_ingestion_policy` is false, nothing is inserted and the result is `OPENING_POLICY_REQUIRED`; the payment stays `PENDING_EVIDENCE`. Configuring that policy is an ops step (F12/F13), not code.
8. **Capture is prepared only from a query (ADR D5)** that is applicable (not stale, `KNOWN`), complete, not a conflict, has no intent and no charges, and whose session `paymentStatus` is `APPROVED`. The payment after the merge must also be capturable: `PROCESSING`, `provider_status='APPROVED'`, `KNOWN`, captured 0, `checkout_session_id` set, `payment_intent_id` null. Insert is `ON CONFLICT DO NOTHING` on the existing unique `(…, payment_id, operation_type)`, so there is at most one `CAPTURE_ORDER` per payment, ever. Webhook approval is F10.
9. **Operation key and command.** `operation_key` = `"pay_capture_" + operationId`; `command` = JSON of `CaptureOrderCommand(scope, key, orderId)`; `request_fingerprint` = `"capture:" + paymentId`; `expires_at` = now + 5 h (ADR D7; not read by any logic). The recovery task is inserted `READY`, due now.
10. **Who sends it.**
    - `GET /v1/payments/{id}`: `PaymentExecutor.refresh` sends a `PREPARED` capture immediately, as a first send.
    - Worker: `recoverDue` picks up the capture task on its next pass (recovery claim).
11. **After the capture call**, the executor runs one GET order when the result is `SUCCESS`, or `DEFINITIVE_REJECT` with `ORDER_NOT_APPROVED` / `INSTRUMENT_DECLINED`. The write-back merges it under the same lease. The operation outcome comes from `CaptureOutcomeRules` (table below).
12. **No resend in F06.** A capture operation that is not `PREPARED` is never sent again by F06. Recovery of such an operation only queries and merges: it is `RESOLVED` when the payment is captured, and otherwise keeps its status (`UNKNOWN` stays `UNKNOWN`). The resend within 5 hours after a GET showing `APPROVED` is F07.
13. **Task done.** `OperationLeaseRules.paymentTaskDone` also returns true for `CAPTURE_ORDER` + `RESOLVED` + payment `SUCCEEDED` + `KNOWN`. Unposted money is still found by L2 (`financial_status='PENDING_EVIDENCE'`), which wakes the task.
14. **Provider status after capture** is the raw order status (`COMPLETED`, ADR D3). `decide` sets it from a PayPal session fact whenever the evidence is not stale, also when captured.

### Capture call → classification (adapter)

`POST /v2/checkout/orders/{orderId}/capture`. Headers `PayPal-Request-Id: <key>` and `Prefer: return=representation`; body `{}`.

| `PayPalExchange` | Classification | Payload / error code |
| --- | --- | --- |
| `Responded` 200/201, JSON with `id` == the requested order id and a text `status` | SUCCESS | `CaptureOrderFact(id, status, capture ids from purchase_units[0].payments.captures[].id, in order; empty list if absent)` |
| `Responded` 200/201, anything else | CONTRACT_MISMATCH | `paypal_contract_mismatch` |
| 422 issue `ORDER_NOT_APPROVED` or `INSTRUMENT_DECLINED` | DEFINITIVE_REJECT | the issue |
| 422 issue `ORDER_ALREADY_CAPTURED` | TIMEOUT_UNKNOWN | `ORDER_ALREADY_CAPTURED` (ADR §5: a capture exists; never a failure) |
| 422 any other issue, or none | CONTRACT_MISMATCH | the issue or null |
| 400 | DEFINITIVE_REJECT | `PayPalOrderMapping.errorCode` |
| every other status | `PayPalOrderMapping.classify(status)` (F05) | `errorCode(body)` |
| `NoResponse` | TIMEOUT_UNKNOWN | reason; `idempotencyKeyUsed` = key |
| `NotSent` | RETRYABLE_TRANSIENT | reason; `idempotencyKeyUsed` null |

Evidence: as in F05, with these differences:

- `idempotencyKeyUsed` = key when sent.
- `rawDigest` = digest of `"paypal-capture|" + orderId + "|" + status` for a payload, else the F05 error digest.

### Order query → `OrderFact` (adapter)

`GET /v2/checkout/orders/{orderId}`, no `PayPal-Request-Id`. A 200/201 maps to `OrderFact` or to CONTRACT_MISMATCH (`paypal_contract_mismatch`). Non-2xx statuses follow F05's query table.

1. **Order.** `session` = `PayPalOrderMapping.fact(order, queryExpiry(order))`. Empty means mismatch.
2. **Purchase units.** `purchase_units` must have exactly one element. Its `amount` (`currency_code`, `value`) → `amountMinor` via `minor(...)`, else mismatch.
3. **Captures.** `captures` = `purchase_units[0].payments.captures[]`, at most one element (more → mismatch; ADR §3). Each capture needs:
   - `id` matching `[A-Z0-9]{1,36}`;
   - `status` in the six capture statuses (anything else → mismatch);
   - `amount` convertible by `minor`, in the unit's currency (else mismatch).

   `create_time` is parsed if present. If it is missing or does not parse, `createdAt` is null.
4. **Settlement (decision 5).** Only for `COMPLETED`. A present breakdown is a mismatch if:
   - a currency differs from the capture currency;
   - a value is not convertible;
   - gross ≠ the capture amount;
   - gross − fee ≠ net;
   - `create_time` is missing.
5. **`failureCode`** = `status_details.reason` if it matches `[A-Z0-9_]{1,64}`, else null.

### `financialingestion/CaptureSettlementService.java` (new)

Uses no `JdbcTemplate`; all SQL goes through `CaptureSettlementRepository`.

```java
/**
 * Records a settlement a provider reports together with a capture (PayPal seller_receivable_breakdown, ADR D9) as a
 * balance transaction, then posts it through the normal replay. For providers without a balance-transaction import.
 * Runs outside any caller transaction; each step owns its local transaction; never calls a provider.
 */
public final class CaptureSettlementService {
    public CaptureSettlementService(
            CaptureSettlementRepository store,
            PlatformTransactionManager tx,
            ObjectMapper mapper,
            FinancialReplayService replay,
            Clock clock)

    /**
     * Returns the replay outcome (POSTED, PENDING_EVIDENCE, QUARANTINED, EXCLUDED, ZERO), OPENING_POLICY_REQUIRED when the
     * account has no ingestion policy, or EVIDENCE_CONFLICT when a different fact is already stored under the same id.
     */
    public String record(ProviderScope scope, BalanceTransactionFact fact, ProviderEvidence evidence)
}
```

- Constructor: `mapper.copy().findAndRegisterModules()` as in `FinancialImportService`; `new FinancialTransactions(tx)`.
- `record`:
  1. If a transaction is active: `IllegalStateException("Settlement recording requires no local transaction")`.
  2. In `transactions.run(...)`:
     - `store.lockPolicy(scope)`. If false, return `OPENING_POLICY_REQUIRED`.
     - `immutable` = `FinancialFacts.immutable(mapper, fact).toString()`.
     - `store.lockBalanceTransaction(scope, fact.btId())`:
       - Absent: `observation = store.insertObservation(scope, btId, encode(evidence), encode(fact), clock.instant())`, then `store.insertBalanceTransaction(scope, fact, evidence.apiVersion(), immutable, encode(fact), observation, clock.instant())`.
       - Present, and its `immutableFact` JSON tree (`mapper.readTree`) differs from `immutable`: insert an observation as above, then `store.insertConflict(scope, stored.id(), observation, stored.immutableFact(), immutable)`, and return `EVIDENCE_CONFLICT`.
       - Present and equal: insert nothing.
     - Return null to continue.
  3. If step 2 returned a value, return it. Otherwise return `replay.replay(scope, fact.btId())`.
- No logging. Never stores provider text other than the fact and evidence records.

### `payment/domain/CaptureOutcomeRules.java` (new)

```java
/** Pure rules for a PayPal capture call's write-back (ADR §5, 2xx and 4xx rows; the timeout path is F07). */
public final class CaptureOutcomeRules {
    public record Outcome(String operationStatus, String operationResolution, boolean markUnknown, boolean conflict) {}

    /** True if the capture result is followed by one GET order before the write-back. */
    public static boolean queriesAfter(ProviderCallClassification classification, String errorCode)

    public static Outcome decide(
            ProviderCallClassification classification, String errorCode, boolean orderMatches, PaymentProgress payment)
}
```

`queriesAfter` returns true when the classification is `SUCCESS`, or `DEFINITIVE_REJECT` with `errorCode` in {`ORDER_NOT_APPROVED`, `INSTRUMENT_DECLINED`}.

`decide`: the first matching row wins.

| # | Condition | Outcome |
| --- | --- | --- |
| 1 | payment `SUCCEEDED`, `capturedMinor > 0`, `KNOWN` | `RESOLVED`, `KNOWN`, false, false |
| 2 | `SUCCESS` and `orderMatches` | `UNKNOWN`, `UNKNOWN`, true, false |
| 3 | `SUCCESS` and not `orderMatches` | `UNKNOWN`, `CONFLICT`, true, true |
| 4 | `CONTRACT_MISMATCH` | `UNKNOWN`, `CONFLICT`, true, true |
| 5 | `DEFINITIVE_REJECT`, code `ORDER_NOT_APPROVED` or `INSTRUMENT_DECLINED` | `ACKNOWLEDGED`, `KNOWN`, false, false |
| 6 | `DEFINITIVE_REJECT`, other code | `ACKNOWLEDGED`, `CONFLICT`, true, true |
| 7 | `CAPABILITY_UNAVAILABLE` | `ACKNOWLEDGED`, `KNOWN`, false, false |
| 8 | anything else (`TIMEOUT_UNKNOWN`, `RETRYABLE_TRANSIENT`, `RATE_LIMITED`, `NOT_FOUND`, `AUTH_REQUIRED`, `TRANSIENT_EMPTY`, `IDEMPOTENCY_CONFLICT`) | `UNKNOWN`, `UNKNOWN`, true, false |

## Risks

- **Ingestion policy in real deployments.** Without the PayPal account's `ingestion_policy` row, captures succeed but stay `PENDING_EVIDENCE`. That is the designed behavior: `OPENING_POLICY_REQUIRED`, retried on every query. Test 44 pins it. F12 must configure the policy before checking posting against the sandbox.
- **Breakdown absent or late in the real sandbox.** Sample 05 has it on the capture. If a real GET order omits it, the payment is SUCCEEDED / PENDING_EVIDENCE until a later query returns it. A capture first seen as `REFUNDED` never posts (ADR D9 posts `COMPLETED` only). F12 checks this.
- **Capture response shape.** The adapter needs only `id`, `status` and capture ids from the capture response, because state comes from the following GET. That is the sample-05 shape.
- **Constraint name in V18.** If it fails, stop (see V18).
- **Migration counts.** The eight upgrade ITs each gain +1 for V18; the table above lists them. The F05 lesson applies: if any other test pins a migration count, report it rather than guess.
- **Posting outside the merge transaction.** Between the merge commit and the replay, a crash leaves PENDING_EVIDENCE. L2 (`financial_status='PENDING_EVIDENCE'`) wakes the capture task, and `recoverCapture` queries and records again. The insert and replay are idempotent: one `bt_id`, and replay returns the stored state.
- **Revenue share.** `CaptureSettlementService` inserts the balance transaction without locking revenue shares. `FinancialReplayService.replay` takes the payment and share locks before posting, as it does for imported BTs.
- **ADR D3 wording.** The only ADR edit is the one sentence above, approved as part of this plan.
- **Docker.** `PayPalCaptureIT` and the count changes need `./mvnw verify` with Docker. This machine has none: run verify on the VPS as for F05 and say so in the progress log. Do not skip the IT.
