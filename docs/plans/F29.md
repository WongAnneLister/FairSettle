# F29 · Deployed

## Goal

Behavior (copied from docs/features.json):

All services run on a public host with sandbox credentials only; PayPal webhooks reach it.

Verification (copied from docs/features.json, manual):

- Health endpoints respond on the public URL
- A sandbox payment's webhook arrives at the deployed ledger

## Host

A user-provided VPS (CentOS 7, 8 vCPU, 7.6 GB RAM, 70 GB disk, plus 4 GB swap), reached over SSH with a key. CentOS 7 is end of life: its yum repositories point at vault.centos.org; Docker CE 26.1 and Compose 2.27 come from download.docker.com. The full live stack runs as is (memory note: about 5.1 GB idle), self-hosted Langfuse included.

Hostnames are first-level subdomains of the operator's domain, one per service (`SHOP_HOST`, `API_HOST`, `CLAIM_HOST`, `OPS_HOST`, `LF_HOST` in `deploy/.env.deploy`), proxied by Cloudflare so the server's IP is not shown. First-level names because Cloudflare's universal certificate covers `*.example.com` but not `*.sub.example.com`. Caddy obtains an origin certificate for each while the records are DNS-only, then the records are switched to proxied with SSL mode Full (strict).

| Host | Service | Access |
| --- | --- | --- |
| `SHOP_HOST` | storefront :3001 | public |
| `API_HOST` | dispatch :4000 (PayPal return and cancel, `/webhooks/ledger`, GraphQL websocket) | public; each endpoint checks its own signature or token |
| `CLAIM_HOST` | complaint page :7860 | public |
| `OPS_HOST` | ledger API :8080 (review page, ops console) | basic auth, except `/webhooks/paypal` (PayPal signature-verified) |
| `LF_HOST` | Langfuse :3000 | basic auth, then Langfuse sign-in |

`PUBLIC_HOST` in the server's `.env.live` is `API_HOST`, so PayPal returns and ledger notifications go to dispatch as in the ngrok setup.

## Changes

### `deploy/docker-compose.deploy.yml` (new)

Third overlay on `docker-compose.yml` and `docker-compose.live.yml`:

- `ledger-api`, `ledger-worker`, `dispatch`: `ports: !override` to `127.0.0.1` only. `ledger-api` also gets `PAYPAL_WEBHOOK_ENABLED=true` and `PAYPAL_WEBHOOK_ID`. Docker-published ports bypass the host firewall, so nothing but Caddy may publish on a public interface.
- `dispatch.STOREFRONT_URL`, `complaint-ui.TRACE_BASE_URL`, `langfuse-web/worker.NEXTAUTH_URL`: the public URLs.
- `storefront` build args `NEXT_PUBLIC_COMPLAINT_PAGE_URL` and `NEXT_PUBLIC_WS_GRAPHQL_ENDPOINT`.
- `caddy` (caddy:2.8.4) on 80/443 with `deploy/Caddyfile`, volumes for certificates.

### `deploy/Caddyfile` (new)

The routes in the table above. Basic auth user and bcrypt hash come from the environment.

### `deploy/.env.deploy` (new, git-ignored)

The five hosts, `PAYPAL_WEBHOOK_ID`, `BASIC_AUTH_USER`, `BASIC_AUTH_HASH` (single-quoted: the hash contains `$`). The plain basic-auth password stays in the git-ignored `deploy/basic-auth.txt` on the operator's machine.

### `dispatch/frontend/Dockerfile` (modified)

Build args `NEXT_PUBLIC_COMPLAINT_PAGE_URL` and `NEXT_PUBLIC_WS_GRAPHQL_ENDPOINT`, empty by default so local builds keep the code's localhost defaults.

### `.gitignore` (modified)

`deploy/.env.deploy`, `deploy/basic-auth.txt`.

## Steps

1. Server: vault repos, Docker, swap; SSH key login.
2. `rsync` the working tree (no `.git`, `node_modules`, build output) to `/opt/fairsettle`; copy `.env.live` (mode 600) and set `PUBLIC_HOST`.
3. `docker compose --env-file .env.live --env-file deploy/.env.deploy -f docker-compose.yml -f docker-compose.live.yml -f deploy/docker-compose.deploy.yml up -d --build --wait`.
4. Check every host over HTTPS; check that 8080, 4000, 5432 and the other internal ports refuse connections from outside.
5. PayPal webhooks (the second verification step): in the PayPal developer dashboard, the sandbox app's webhook URL becomes `https://OPS_HOST/webhooks/paypal`; put its id in `PAYPAL_WEBHOOK_ID` and restart the ledger API; make one sandbox payment and confirm the webhook is received and verified (`platform.webhook_inbox`).
6. Seed the demo data (demo accounts and Malatang House) through dispatch GraphQL from inside the agent container (the host has no Python 3).

## Out of scope (known gaps, accepted for a sandbox demo)

- The storefront's one-click demo logins (fixed password) stay: all money is PayPal sandbox.
- `POST /v1/complaints` and the complaint page have no sign-in.
- KI-5 (a dish must belong to its restaurant).
- The VPS root password was shared in chat: the operator changes it and turns password login off once key login is confirmed.

## Risks

- sslip.io or Let's Encrypt rate limits: five hosts, one certificate each.
- Memory: idle stack about 5.1 GB of 7.6 GB; builds use the 4 GB swap.
- CentOS 7 kernel 3.10 with Docker 26: works today, no further updates from CentOS.

## Server-side fixes (not in the repository)

- `dispatch/package-lock.json` and `dispatch/frontend/package-lock.json` resolve packages from `registry.npmmirror.com`, which resets connections from this host (`npm ci` ends with "Exit handler never called"). The server's copies point at `registry.npmjs.org` instead (same tarballs, same integrity hashes).
- `net.ipv4.tcp_mtu_probing=1` (`/etc/sysctl.d/90-mtu-probing.conf`): TLS handshakes to the PayPal API stalled often; this helped but did not cure it.

## Known issue found on the live host

Calls from this host to the PayPal API sometimes stall in the TLS handshake. The ledger refreshes a payment from PayPal on every read (`PaymentService.get`), so a stall can push the agent's 10 s ledger timeout and escalate a complaint (`source_unavailable`); a stalled call once held the worker's only scheduler thread past the 15 s request timeout, so a reserved refund did not start until the worker was restarted, and the next refund attempt ended `UNKNOWN` and waits for a provider query. Not fixed here: it needs a different network path or ledger changes outside this feature.
