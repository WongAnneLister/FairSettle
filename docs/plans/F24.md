# F24 · M2: full chain with PayPal

## Goal

Behavior (copied from docs/features.json):

> Live run: order paid with PayPal, complaint submitted, proposal approved in the console, refund visible in the sandbox, ledger shows the cost on the liable party.

Verification (copied from docs/features.json):

> kind `manual`:
> 1. Complaint id, proposal id, PayPal refund id recorded in docs/progress.md
> 2. Ledger shows the allocation entries for the liable party
> 3. Langfuse trace for the run opens and shows cited evidence

F24 has two parts, like F12.

1. **Code (Codex, one work commit).** Everything the real chain needs that does not exist yet, each piece proven by tests without PayPal, DeepSeek or a live Langfuse:
   - a compose overlay that runs the whole chain live, Langfuse included (decisions 1–4 and 11);
   - an agent credential in the ledger's local fixtures (decision 5);
   - a refund proposal review page in the ledger (decision 6);
   - the agent as a long-running HTTP service that also polls (decisions 7–8);
   - cited evidence in the trace, and a strict refund id (decisions 9–10);
   - a live-run script and a runbook (decisions 13–14).
2. **The live run (a human).** After review, a person follows `docs/m2-live-run.md` against the real sandbox, records the ids in `docs/progress.md` and runs `python3 scripts/features.py verify F24` themself. F24 is `kind: manual`: no agent confirms it (root `AGENTS.md`).

### Why code is needed at all

Every link of the chain was tested alone; the chain has never run. Gaps found while planning:

| Gap | Where | Effect today |
| --- | --- | --- |
| The root compose runs the ledger with no provider, no fixtures and checkout disabled, and F13's tests forbid secrets in it | `docker-compose.yml`, `scripts/tests/test_compose.py` | No PayPal payment can be made in the stack |
| The ledger console has no refund proposal view or decision action | `ledger/src/main/resources/static/ops-console.*` | "approved in the console" is impossible; only `curl` can approve |
| The agent has no process: nothing calls `Agent.start` from outside a test, and nothing calls `poll()` on a timer | `agent/` | A complaint cannot be submitted and an approval is never seen |
| The agent has no ledger credential of the payment's application (F22 decision) | ledger `LocalFixtureInitializer` | The agent's payment reads would get 404 |
| The trace records the decision but not the evidence it cites | `agent/fairsettle_agent/graph.py`, `decide` stage | Verification step 3 cannot be shown |
| Real ledger → dispatch payment notifications need Kafka on, a topic, a target row with a public HTTPS URL, allowed hosts and a signing key (F16, Out of scope) | ledger worker config, `platform.merchant_notification_target` | The dispatch order never becomes `Paid` |
| No Langfuse server; the SDK was checked only against an in-memory exporter (F23, Risks) | | No trace can be opened |

### Decisions made with the user (2026-10-30)

- **The live chain runs from a compose overlay.** A new `docker-compose.live.yml` is layered on the root file with `-f`, and reads its secrets only from the gitignored `.env.live` through `--env-file`. The root `docker-compose.yml` and its F13 tests do not change.
- **Langfuse is self-hosted in the overlay, version 4.58.0**, with its Postgres, ClickHouse, Redis and S3 (SeaweedFS). Its project and API keys are created headlessly (`LANGFUSE_INIT_*`). No trace data leaves the machine.
- **The console approval is a new English page**, `refund-proposals.html`, in the ledger's static files, built on `ui/core.mjs`. The existing Chinese console gets one link to it and is otherwise unchanged.
- **The agent runs as one FastAPI process** on port 8000: `POST /v1/complaints`, `GET /v1/complaints/{id}`, `GET /health`, and a background task that calls `poll()` every `FAIRSETTLE_POLL_SECONDS` (default 5) in the same process. F22's lock is per process, so submitting and polling must share a process.
- **Rows left `running` by a crashed process are logged at startup, not resumed.** No ledger write happened for them.
- **F23 open issue 2 is fixed:** `RefundProposal.refund_id` uses the strict `RefundId` type. **F23 open issue 1 is recorded** as KI-4 (switching `FAIRSETTLE_TRACING` during `submit_retry`); the overlay never sets it.
- **No PayPal webhooks in the live run.** The refund reaches `SUCCEEDED` and posts from PayPal's synchronous response (F08, F12). One ngrok tunnel, to dispatch, carries the ledger's payment notifications.
- **No poll backoff.** One pass every `FAIRSETTLE_POLL_SECONDS`; each waiting refund is read once per pass. A backoff is recorded for F29.
- Inherited from F22 (2026-10-29): the agent gets **a second credential of dispatch's ledger application**, seeded by the local fixtures.

## Design decisions (fixed)

### The live stack

1. **Overlay and env file.**
   - `docker-compose.live.yml` is only ever used with the root file:

     ```bash
     docker compose --env-file .env.live -f docker-compose.yml -f docker-compose.live.yml up -d --build --wait
     ```

   - Every value that is a secret or depends on the operator is written `${NAME:?NAME is required in .env.live}`. Nothing else is interpolated. There is no `env_file:` anywhere.
   - `--env-file .env.live` replaces Compose's default root `.env`, so the F12 values there (`DB_PORT=5434`, `WORKER_PORT=8091`, …) never reach this stack.
   - `.env.live` is gitignored by the existing `.env.*` rule. The committed template is `env.live.example` (no leading dot, as `dispatch/env.test.example`), with every key and an **empty** value, so a copy left unfilled fails at `config` time.
   - The 16 keys, in this order: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `LOCAL_APP_SECRET`, `LOCAL_OPS_SECRET`, `LOCAL_AGENT_SECRET`, `PUBLIC_HOST`, `LEDGER_NOTIFICATION_SECRET`, `AGENT_SERVICE_TOKEN`, `DEEPSEEK_API_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_NEXTAUTH_SECRET`, `LANGFUSE_SALT`, `LANGFUSE_ENCRYPTION_KEY`, `LANGFUSE_ADMIN_EMAIL`, `LANGFUSE_ADMIN_PASSWORD`.
   - Passwords of services that are never published (the agent's and Langfuse's Postgres, ClickHouse) are literals, as in the root file.

2. **Services.** The overlay changes five root services and adds eleven.

   | Service | Change or role |
   | --- | --- |
   | `ledger-postgres`, `dispatch-postgres`, `kafka` | data volume replaced by `fairsettle-live-ledger-postgres`, `fairsettle-live-dispatch-postgres`, `fairsettle-live-kafka` (same container path). The live PayPal-mode ledger database never meets the root stack's database (F12: a FAKE-provisioned database refuses PayPal fixtures) |
   | `ledger-api` | `command: ["--spring.profiles.active=api,local"]`; PayPal and fixture variables (decision 3) |
   | `ledger-worker` | PayPal variables, Kafka messaging and notification settings (decision 4); also waits for `kafka-init` and `ledger-notification-target` to complete |
   | `dispatch` | checkout and agent variables (decision 4); also waits for `ledger-api` healthy |
   | `kafka-init` (new, one-shot) | creates topic `payment-notifications-v1` before the worker starts |
   | `ledger-notification-target` (new, one-shot) | upserts the notification target row (decision 4) |
   | `agent-postgres` (new) | `postgres:16`, user `agent`, password `agent`, database `fairsettle_agent`, volume `fairsettle-live-agent-postgres` |
   | `agent` (new) | decision 8 |
   | `langfuse-postgres`, `langfuse-redis`, `langfuse-clickhouse`, `langfuse-s3`, `langfuse-s3-init` (one-shot), `langfuse-worker`, `langfuse-web` (new) | decision 11 |

   - Published ports: the root's 8080, 8081 and 4000, plus `127.0.0.1:8000` (agent) and `127.0.0.1:3000` (Langfuse web). Nothing else.
   - One-shot services have `restart: "no"` and no healthcheck; every other service has a healthcheck, except `langfuse-worker` (its health endpoint was not checked while planning; nothing depends on it).
   - Images: `postgres:16`, `redis:7-alpine`, `apache/kafka:3.9.0`, `clickhouse/clickhouse-server:25.12`, `chrislusf/seaweedfs:4.48`, `langfuse/langfuse:4.58.0`, `langfuse/langfuse-worker:4.58.0`; the agent builds `./agent` as `fairsettle-agent:local`.

4. **Notifications and checkout.**

     ```sql
     INSERT INTO platform.merchant_notification_target(organization_id,environment_id,application_id,url,key_ref,version,enabled)
     VALUES ('10000000-0000-0000-0000-000000000001','10000000-0000-0000-0000-000000000011','10000000-0000-0000-0000-000000000031','https://${PUBLIC_HOST:?PUBLIC_HOST is required in .env.live}/webhooks/ledger','dispatch',1,true)

   - `dispatch`:

     ```yaml
     LEDGER_CHECKOUT: enabled
     LEDGER_BASE_URL: http://ledger-api:8080
     LEDGER_APP_TOKEN: app_10000000-0000-0000-0000-000000000041.${LOCAL_APP_SECRET:?…}
     LEDGER_CHECKOUT_SUCCESS_URL: https://${PUBLIC_HOST:?…}/checkout/success

     ```

     The success and cancel paths do not exist in dispatch; the buyer sees a 404 after approving, which is harmless. Capture is triggered by the script's `GET /v1/payments/{id}` or the worker's recovery (F06), not by the redirect.
   - `PUBLIC_HOST` is the bare ngrok host name, for example `name.ngrok-free.dev`: no scheme, no path, no port.

### The ledger

5. **Agent credential in the local fixtures** (`LocalFixtureInitializer`, identity module).
   - `public static final UUID AGENT_CREDENTIAL = id(42);`
   - New property `platform.fixtures.agent-secret`, mapped in `application.yml` as `agent-secret: ${LOCAL_AGENT_SECRET:}`.
   - **Optional.** Blank or absent: no agent credential, and every existing behavior and test is unchanged.
   - Set: validated before the transaction, after the app and ops secrets:

     ```sql
     INSERT INTO platform.application_credential(id,key_id,organization_id,environment_id,application_id,provider_account_id,secret_hash,not_before,expires_at,granted_scopes)
     VALUES (?,'agent',?,?,?,?,?,?,?,ARRAY['payments:read','refunds:read','refund-proposals:read','refund-proposals:write'])

If it inserted nothing, `verifyExisting(jdbc, "application_credential", agent)` (a different secret throws the existing "Existing fixture credentials differ; …" message). Then `INSERT INTO platform.credential_currency(credential_id,organization_id,environment_id,currency) VALUES (?,?,?,'USD') ON CONFLICT (credential_id,currency) DO NOTHING`.

### The agent

7. **`fairsettle_agent/service.py`** (new): FastAPI app and poll loop.
   - Routes:

     | Route | Behavior |
     | --- | --- |
     | `GET /health` | `200 {"status": "UP"}`; never touches the agent |
     | `POST /v1/complaints` | body is `ComplaintInput` (snake_case JSON, strict, extra fields refused): `await agent.start(complaint)` → `201` with `complaint_body`; `DuplicateComplaint` → `409 {"code": "DUPLICATE_COMPLAINT"}`; an invalid body → FastAPI's `422`, and nothing is registered |
     | `GET /v1/complaints/{complaint_id}` | `await agent.status(id)` → `200` with `complaint_body`; `None` → `404 {"code": "NOT_FOUND"}` |

   - `complaint_body(status, tracing)` → exactly `{"complaint_id", "thread_id", "status", "proposal_id", "trace_id"}`; `trace_id` is `Tracing.trace_id(complaint_id)` when `tracing.enabled`, else `None`.
   - The `POST` waits for the whole first invocation (gather, decide, submit), so its answer is the run's status after `start` (`awaiting_review`, `declined`, `escalated`, `submit_retry`, …).
   - `poll_loop(agent, interval, *, sleep=asyncio.sleep)`: forever: `changed = await agent.poll()`; log `"complaint %s is %s"` per change at INFO; any `Exception` → log `"poll pass failed: %s"` with the exception's class name only, at ERROR, and continue; then `await sleep(interval)`. The first pass runs immediately. `CancelledError` ends it.
   - Lifespan (`create_app`): `async with open_agent() as agent`; for each id of `await agent.running()`, log WARNING `"complaint %s was left running by an earlier process and is not resumed"`; start `poll_loop` as a task; on shutdown cancel it and await it, suppressing `CancelledError`; then the context manager closes the agent (which shuts tracing down, so spans are flushed).
   - Logging: logger `fairsettle_agent.service`. Only ids, statuses and class names; never the complaint text.
   - `ServiceConfig.from_env(env)`: `host = env.get("FAIRSETTLE_HTTP_HOST", "127.0.0.1")`; `poll_seconds = float(env.get("FAIRSETTLE_POLL_SECONDS", "5"))`, which must parse and be from 1 to 300, else `ValueError("FAIRSETTLE_POLL_SECONDS must be a number from 1 to 300")`. The port is always 8000.

- `proposalView(p)` → `{ id, complaintId, orderRef, paymentId, status, decision, reasonCode, amount, liability, explanation, evidenceRefs, traceId, createdAt }` with `amount = formatMinor(p.amountMinor, p.currency, 2)` for `USD` and `` `${p.amountMinor} ${p.currency} (minor units)` `` for any other currency; `liability = p.liability.map(l => ({ party: l.party, basisPoints: l.basisPoints, percent: (l.basisPoints / 100).toFixed(2) + '%' }))`; `traceId = p.agentRun?.traceId ?? null`; the rest copied.
- `createProposalReview`:
  - **Never show `error.message`** from `ui/core.mjs`: `ApiSession` and `CommandIntent` throw Chinese messages (for example `请输入 ops_… 项目凭据` for a malformed credential), and `core.mjs` is not changed by F24. Every notice is English text from this module plus, at most, the error code `error.data?.code ?? error.name`. (Amended before the work commit, after Codex's read-only check found it.)
  - `identify()`: first `OPS_CREDENTIAL.test(api.credential)`, where `export const OPS_CREDENTIAL = /^ops_[0-9a-f-]+\.[A-Za-z0-9_-]+$/i` (the same shape `ApiSession.request` requires); if it fails, `notice('Enter an ops_… credential.')` and return without any request. Then `api.latest('identity', '/ops/identity', data => { api.identity = data; })`; then `notice('Signed in as ' + role + (role === 'OPS_REVIEWER' ? '. You can approve or reject.' : '. You can only view proposals.'))` and `load()`. On error: `notice('Sign-in failed: ' + (error.data?.code ?? error.name))`.
  - `load()` errors: `notice('Could not load proposals: ' + (error.data?.code ?? error.name))`.
  - `load(status = 'PENDING_REVIEW')`: `api.latest('proposals', proposalListPath(status), data => render(data.items.map(proposalView), { canReview: view => canReview(api.identity, view), pending: intent.pending?.context ?? null }))`.
  - `decide(id, action, reason = '')`: if `intent.pending` exists for another proposal id → `notice('Retry or finish the pending decision for <pendingId> first.')`, return `null`, send nothing. Build the body with `decisionBody` (its error is shown with `notice` and nothing is sent). `intent.prepare(decisionPath(id), JSON.stringify(body), { proposalId: id, action })`; `await intent.send()`. Success → `notice('Proposal <id> approved; refund <refundId>.')` or `notice('Proposal <id> rejected.')`, then `load()`, return the response data. Failure → `notice('Decision for <id> is not confirmed (<code>). Retry sends the same request with the same key.')`, where `<code>` is `error.data?.code ?? error.name`; return `null`; the pending intent stays.
  - `retry()`: with no pending intent → `notice('No decision is waiting for a retry.')`, return `null`; else the same send and notices as `decide`.

- **PayPal fixtures refuse a database provisioned in another mode.** The live volumes are separate from the root stack's, so only an earlier live run can have provisioned them, always in PayPal mode with the same secrets.
