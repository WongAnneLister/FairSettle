# F17 · Liability accounts and allocation

## Goal

Behavior (copied from docs/features.json):

> A refund with a liability split posts the cost to restaurant, courier and platform accounts in basis points; the parts always sum to the refund, the sub-cent remainder goes to the platform.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='LiabilityAllocationTest' test
```

F17 gives the ledger what F18 needs to approve a refund proposal:

- the allocation arithmetic;
- storage for one allocation per refund;
- three new ledger accounts and the journal that posts to them;
- a worker that posts each allocation once its refund has posted;
- the read endpoint `GET /v1/refunds/{refundId}/liability` (contract op 6, F14).

F18 creates proposals, and on approval calls `LiabilityService.record(...)` in the same transaction that creates the refund. F17 has no proposal table, so its tests pass a proposal id directly.

"Courier" in the feature text is the contract's `DRIVER` party (F14 decision 4). Code, columns and accounts use `DRIVER`.

## Design decisions (fixed)

1. **Allocation rule** (F14 decision 5). For a refund of `A` minor units and shares `r`, `d`, `p` basis points:
   - `restaurant = floor(A × r / 10000)`;
   - `driver = floor(A × d / 10000)`;
   - `platform = A − restaurant − driver`.

   Computed with `BigInteger`. The lines always sum to `A`, and the platform gets the sub-cent remainder. `platform − floor(A × p / 10000)` is always 0, 1 or 2.
2. **Split validation.** Each share is 0..10000, and the three sum to exactly 10000. Otherwise `ApiException(LIABILITY_SPLIT_INVALID)`. This error code is new: `422`, not retryable, as in the F14 contract.
3. **Three new INTERNAL accounts**, one per party. `source_domain='INTERNAL'`, no provider account, no balance domain:

   | Party | `account_purpose` | Kind | Meaning |
   | --- | --- | --- | --- |
   | `RESTAURANT` | `REFUND_RECEIVABLE_RESTAURANT` | asset, debit-normal | refund cost the restaurant owes the platform |
   | `DRIVER` | `REFUND_RECEIVABLE_DRIVER` | asset, debit-normal | refund cost the driver owes the platform |
   | `PLATFORM` | `REFUND_COST_PLATFORM` | expense, debit-normal | refund cost the platform bears |

4. **The journal (`L-LIABILITY`).** One journal per allocation. It moves the posted refund principal out of `SALES_RETURNS` to the parties that bear it:
   - debit each party account with its amount, skipping parties whose amount is 0;
   - credit `SALES_RETURNS` with `A`.

   Example, `A = 1250`, 3333/3333/3334:

   | Account | Debit | Credit |
   | --- | ---: | ---: |
   | `REFUND_RECEIVABLE_RESTAURANT` | 416 | |
   | `REFUND_RECEIVABLE_DRIVER` | 416 | |
   | `REFUND_COST_PLATFORM` | 418 | |
   | `SALES_RETURNS` | | 1250 |

   Together with the refund's own `L-REFUND` journal (debit `SALES_RETURNS` 1250, credit `PSP_FUNDS` 1250), the refund's `SALES_RETURNS` nets to 0, and the whole cost sits in the three party accounts. The platform's result changes only by the platform share; the restaurant and driver shares become receivables.
   - Event key `liability.allocate:<refundId>` (UUID string); event type `L-LIABILITY`; source domain `INTERNAL`; source ref the allocation id.
   - Facts (a JSON object): `liability_id`, `refund_id`, `payment_id`, `proposal_id` (UUID strings); `amount_minor`, `restaurant_bp`, `driver_bp`, `platform_bp`, `restaurant_minor`, `driver_minor`, `platform_minor` (numbers).
   - Ledger scope: the refund's organization, environment and currency, provider account `null` (like revenue share).
   - At least two lines always: `A ≥ 1`, so at least one party amount is positive.
5. **When it posts.** Recording an allocation posts nothing; it stores `posting_status = PENDING`. The journal is posted when the refund itself has posted: `refund_status = 'SUCCEEDED'` and the refund's `financialStatus` (the same `RefundViewRules.financialStatus` that `GET /v1/refunds/{id}` shows) is `POSTED`. Then the row becomes `POSTED` with `journal_id` and `posted_at`. A refund that fails, is canceled or stays unknown never posts its allocation; the row stays `PENDING`. Posting before the money has moved would put a receivable on the books for a refund that may never happen.
6. **Who posts.** `LiabilityWorker` (worker role) calls `LiabilityService.postReady(25)` every `platform.liability.poll-ms` (default 30000 ms). It scans all scopes; each journal uses the row's own scope. The modules that post refund BTs (financial ingestion, the webhook handler, `RefundExecutor`) are not changed.
7. **Idempotency.**
   - `record`: one allocation per refund (`UNIQUE refund_id`) and per proposal (`UNIQUE proposal_id`). The same refund, proposal and shares again returns the existing id. A different proposal or different shares for the same refund, or the same proposal on another refund, is `EVIDENCE_CONFLICT`.
   - `post`: locks the row, and returns `false` if it is already `POSTED`. The event key is stable, so a retry after a crash returns the same journal from `post_ledger`.
8. **Lock order.** `refund_liability` gets rank 55, between `share_allocation` (50) and `payout` (60). `post` locks the liability row, then only reads the refund (no lock), then posts (accounts, rank 80). `record` runs inside F18's approval transaction after the refund reservation's payment (20) and control (30) locks, and inserts the row (55). Neither path takes a lock of a lower rank after a higher one.
9. **The database enforces the rule too.** CHECK constraints repeat decision 1 and 2. A guard trigger makes the row immutable except for the single `PENDING → POSTED` transition, requires the stored amount to equal the refund's amount, and checks that the journal's event matches the allocation.
10. **Read API** (contract op 6). `GET /v1/refunds/{refundId}/liability`, `ApplicationBearer` scope `refunds:read`. It returns `LiabilityAllocation`:
    - `refundId` (`ref_…`), `proposalId` (`prop_…`), `currency`, `amountMinor`;
    - `lines`: exactly three, in the order `RESTAURANT`, `DRIVER`, `PLATFORM`, each `{party, basisPoints, amountMinor}`;
    - `postingStatus`: `PENDING` or `POSTED`;
    - `journalId`: the journal UUID as a string, or `null`.

    It returns `404 NOT_FOUND` when the refund is not in the caller's organization, environment, application and provider account, when its currency is not allowed for the caller, or when the refund has no allocation. A missing scope gives the usual `403 FORBIDDEN` from `TenantAccessGuard.requireScope`.

### `ledger/src/main/java/com/paymentsledger/liability/repository/LiabilityRepository.java` (new)

```java
public class LiabilityRepository {
    public LiabilityRepository(JdbcTemplate jdbc);

    /** The refund fields an allocation copies. */
    public record RefundScope(UUID organizationId, UUID environmentId, UUID applicationId,
            UUID providerAccountId, String currency, UUID paymentId, long amountMinor) {}

    /** One stored allocation; the allocation is rebuilt through the LiabilityAllocation constructor. */
    public record Liability(UUID id, UUID organizationId, UUID environmentId, UUID applicationId,
            UUID providerAccountId, String currency, UUID paymentId, UUID refundId, UUID proposalId,
            LiabilityAllocation allocation, String postingStatus, UUID journalId) {}

    public Optional<RefundScope> refund(UUID refundId);
    public Optional<UUID> insert(UUID refundId, RefundScope refund, UUID proposalId, LiabilityAllocation allocation);
    public Optional<Liability> findByRefund(UUID refundId);
    public Optional<Liability> lock(UUID liabilityId);
    public Map<String, UUID> provisionAccounts(UUID refundId, UUID organizationId, UUID environmentId, String currency);
    public void markPosted(UUID liabilityId, UUID journalId);
    public List<UUID> readyCandidates(int limit);
    public Optional<Liability> findScoped(UUID refundId, TenantContext tenant);

```

| Method | SQL |
| --- | --- |
| `refund` | `SELECT organization_id, environment_id, application_id, provider_account_id, currency, payment_id, amount_minor FROM platform.refund WHERE id=?` (no lock) |
| `insert` | `INSERT INTO platform.refund_liability(…) VALUES (…) ON CONFLICT (refund_id) DO NOTHING RETURNING id`; empty when the refund already has a row. A `DuplicateKeyException` (the proposal is on another refund) propagates to the service |
| `findByRefund` | `SELECT * FROM platform.refund_liability WHERE refund_id=?` |
| `lock` | `SELECT * FROM platform.refund_liability WHERE id=? FOR UPDATE` |
| `provisionAccounts` | `SELECT platform.ensure_liability_accounts(?)` with the refund id, then the ids of `REFUND_RECEIVABLE_RESTAURANT`, `REFUND_RECEIVABLE_DRIVER`, `REFUND_COST_PLATFORM` and `SALES_RETURNS` for that organization, environment and currency, `source_domain='INTERNAL'`, `provider_account_id IS NULL`, as purpose → id |
| `markPosted` | `UPDATE platform.refund_liability SET posting_status='POSTED', journal_id=?, posted_at=now() WHERE id=? AND posting_status='PENDING'`; throws `IllegalStateException` unless exactly one row changed |
| `readyCandidates` | `SELECT l.id FROM platform.refund_liability l JOIN platform.refund r ON r.id=l.refund_id WHERE l.posting_status='PENDING' AND r.refund_status='SUCCEEDED' ORDER BY l.created_at, l.id LIMIT ?` |
| `findScoped` | `SELECT * FROM platform.refund_liability WHERE refund_id=? AND organization_id=? AND environment_id=? AND application_id=? AND provider_account_id=?`, with the tenant's values |

The row mapper for `Liability` builds `new LiabilitySplit(restaurant_bp, driver_bp, platform_bp)` and `new LiabilityAllocation(amount_minor, split, restaurant_minor, driver_minor, platform_minor)`, so a stored row that breaks the rule fails loudly when read.

### `ledger/src/main/java/com/paymentsledger/liability/LiabilityService.java` (new)

No `JdbcTemplate` and no SQL (`LayeringArchitectureTest`); every database access goes through `LiabilityRepository` or `RefundRecordRepository`.

```java
public final class LiabilityService {
    public LiabilityService(LiabilityRepository repository, PlatformTransactionManager manager,
            ObjectMapper mapper, LedgerPostingService ledger, RefundRecordRepository refunds);

    public UUID record(UUID refundId, UUID proposalId, LiabilitySplit split);
    public boolean post(UUID liabilityId);
    public int postReady(int limit);
    public Map<String, Object> read(TenantContext tenant, UUID refundId);
}
```

Holds a `TransactionTemplate` built from `manager`. Logger as in `RevenueShareService`.

- **`record`**, inside `tx.execute(…)` (it joins F18's transaction when there is one):
  1. `refundId`, `proposalId` or `split` null → `ApiException(VALIDATION_ERROR, …)`.
  2. `repository.refund(refundId)`. Empty → `ApiException(NOT_FOUND, "Refund not found")`.
  3. `LiabilityAllocation.allocate(refund.amountMinor(), split)`.
  4. `repository.insert(…)`. A `DuplicateKeyException` → `ApiException(EVIDENCE_CONFLICT, "Proposal already has a liability allocation")`. An id → return it.
  5. Empty: `repository.findByRefund(refundId)`. Same `proposalId` and the same split → return its id. Otherwise `ApiException(EVIDENCE_CONFLICT, "Refund already has a different liability allocation")`.
- **`post`**, inside `tx.execute(…)`:
  1. `repository.lock(liabilityId)`. Empty → `ApiException(NOT_FOUND, "Refund liability not found")`. `POSTED` → return `false`.
  2. `refunds.find(refundId)` (new, below). Ready when the refund's status is `SUCCEEDED` and `RefundViewRules.financialStatus(refund, transactions, conflict)` is `POSTED`, where `transactions = refunds.balanceTransactions(refund)` and `conflict` is computed exactly as in `RefundReader` (any `QUARANTINED` transaction, or `refunds.hasEvidenceConflict(id)`). Not ready → return `false`.
  3. `repository.provisionAccounts(refundId, org, env, currency)`.
  4. Build the command with `LiabilityPosting.command` from the row's allocation, and post it with `ledger.post(new LedgerScope(org, env, currency, null), command)`.
  5. `repository.markPosted(liabilityId, journal)`. Return `true`.
- **`postReady`**:
  - Throws `IllegalStateException` when a transaction is active (each item owns its own transaction, like `catchUp`), and `IllegalArgumentException` unless `1 <= limit <= 100`.
  - Candidates: `repository.readyCandidates(limit)`.
  - For each, `post(id)`. Count the `true` results. A `RuntimeException` is logged as `LOG.warn("liability_post reason=RETRY_REQUIRED liabilityId={}", id)` and the loop continues. Never log amounts or tokens.
  - Return the count.
- **`read`**:
  - `TenantAccessGuard.requireScope(tenant, "refunds:read")`.
  - `repository.findScoped(refundId, tenant)`.
  - Empty, or its currency not in `tenant.allowedCurrencies()` → `ApiException(NOT_FOUND, "Refund liability not found")`.
  - Returns a `LinkedHashMap` in this field order: `refundId` (`PaymentIds.format("ref", …)`), `proposalId` (`PaymentIds.format("prop", …)`), `currency`, `amountMinor`, `lines` (list of `LinkedHashMap` `party`, `basisPoints`, `amountMinor`, from `allocation.lines()`), `postingStatus`, `journalId` (`journal_id.toString()` or `null`).

### `ledger/src/main/resources/db/migration/V19__refund_liability.sql` (new)

Header comment: `-- F17: refund liability allocation, three party accounts and their posting guard.`

1. **Account purposes.** In a `DO` block:
   - find the `ledger_account` CHECK constraints whose `pg_get_constraintdef` contains `PARTNER_PAYABLE`;
   - raise an exception unless there is exactly one;
   - drop it.

   Then `ALTER TABLE platform.ledger_account ADD CONSTRAINT ledger_account_purpose_shape CHECK (…)`. The body is V3's CHECK unchanged, except that the INTERNAL list also holds `'REFUND_RECEIVABLE_RESTAURANT','REFUND_RECEIVABLE_DRIVER','REFUND_COST_PLATFORM'`.
2. **Table `platform.refund_liability`:**

   ```sql
   id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
   organization_id uuid NOT NULL, environment_id uuid NOT NULL, application_id uuid NOT NULL,
   provider_account_id uuid NOT NULL, currency text NOT NULL, payment_id uuid NOT NULL,
   refund_id uuid NOT NULL UNIQUE, proposal_id uuid NOT NULL UNIQUE,
   amount_minor bigint NOT NULL CHECK(amount_minor>0),
   restaurant_bp integer NOT NULL CHECK(restaurant_bp BETWEEN 0 AND 10000),
   driver_bp integer NOT NULL CHECK(driver_bp BETWEEN 0 AND 10000),
   platform_bp integer NOT NULL CHECK(platform_bp BETWEEN 0 AND 10000),
   restaurant_minor bigint NOT NULL CHECK(restaurant_minor>=0),
   driver_minor bigint NOT NULL CHECK(driver_minor>=0),
   platform_minor bigint NOT NULL CHECK(platform_minor>=0),
   posting_status text NOT NULL DEFAULT 'PENDING' CHECK(posting_status IN ('PENDING','POSTED')),
   journal_id uuid UNIQUE, posted_at timestamptz,
   created_at timestamptz NOT NULL DEFAULT now(),
   CHECK(restaurant_bp+driver_bp+platform_bp=10000),
   CHECK(restaurant_minor=floor(amount_minor::numeric*restaurant_bp/10000)),
   CHECK(driver_minor=floor(amount_minor::numeric*driver_bp/10000)),
   CHECK(restaurant_minor::numeric+driver_minor+platform_minor=amount_minor),
   CHECK((posting_status='POSTED')=(journal_id IS NOT NULL) AND (journal_id IS NULL)=(posted_at IS NULL)),
   FOREIGN KEY(organization_id,environment_id,application_id,provider_account_id,currency,payment_id,refund_id)
    REFERENCES platform.refund(organization_id,environment_id,application_id,provider_account_id,currency,payment_id,id),
   FOREIGN KEY(organization_id,environment_id,currency,journal_id)
    REFERENCES platform.journal(organization_id,environment_id,currency,id)
   ```

   Plus a partial index: `CREATE INDEX refund_liability_pending ON platform.refund_liability(created_at,id) WHERE posting_status='PENDING'`.
3. **Guard** `platform.f17_liability_guard()`: `BEFORE INSERT OR UPDATE OR DELETE … FOR EACH ROW`, `SET search_path=pg_catalog,platform`. Every rejection raises `ERRCODE='23514'`:
   - DELETE → `'Immutable refund liability'`;
   - INSERT: `posting_status` must be `'PENDING'` with `journal_id` and `posted_at` null, and `amount_minor` must equal `platform.refund.amount_minor` for `NEW.refund_id`;
   - UPDATE:
     - every column except `posting_status`, `journal_id` and `posted_at` must be unchanged;
     - the change must be `OLD.posting_status='PENDING'` to `NEW.posting_status='POSTED'`;
     - the journal's `financial_event` must have `event_key = 'liability.allocate:' || NEW.refund_id`, `event_type = 'L-LIABILITY'`, `source_domain = 'INTERNAL'` and `source_ref = NEW.id::text`.
4. **Provisioning** `platform.ensure_liability_accounts(refund_arg uuid) RETURNS void`, `SECURITY DEFINER`, `SET search_path=pg_catalog,platform`. It inserts, for the refund's organization, environment and currency with `source_domain='INTERNAL'`, the purposes `REFUND_COST_PLATFORM`, `REFUND_RECEIVABLE_DRIVER`, `REFUND_RECEIVABLE_RESTAURANT` and `SALES_RETURNS`, `ORDER BY purpose`, `ON CONFLICT DO NOTHING`. Same form as `ensure_share_accounts`.
5. **Grants**, like V10:
   - `REVOKE ALL ON FUNCTION … FROM PUBLIC` for both new functions;
   - inside `DO $$ … IF EXISTS(payments_app) …`: `REVOKE ALL ON platform.refund_liability FROM payments_app`, then `GRANT SELECT,INSERT,UPDATE ON platform.refund_liability TO payments_app` and `GRANT EXECUTE ON FUNCTION platform.ensure_liability_accounts(uuid) TO payments_app`;
   - `REVOKE ALL ON FUNCTION platform.f17_liability_guard() FROM payments_app`.

## Risks

- **Late refund failure.** A refund that posted and later receives a failure BT (`L-REFUND-REVERSE`) leaves the liability journal in place, so `SALES_RETURNS` for that refund goes negative. PayPal refunds rarely fail after `COMPLETED`. It is recorded here and in the progress entry as not handled; a later feature can reverse it through `ReversalService`.
- **Failed refunds stay `PENDING`.** An allocation whose refund fails never posts and keeps showing `PENDING`. The agent reads the refund's own status (F22/F23). If the reviewer of F18 needs a terminal state, that is a contract change, in a later feature.
- **Constraint name.** V3's CHECK has a generated name; the migration finds it by its definition and refuses to continue unless exactly one matches, so a wrong match cannot silently drop another constraint.
- **Revenue share overlap.** If a restaurant is also a revenue-share partner, the refund reservation already reduces its accrual (`L-SHARE-REVERSE`), and the liability then charges it the refund cost too. This is a policy question, not a ledger error; F17 posts only the split it is given. Recorded under Out of scope.
- **Reconciliation.** Nightly checks scan all journals. `L-LIABILITY` is a balanced INTERNAL journal with an accepted event, so trial balance and rebuild cover it. Run the reconciliation ITs listed in step 3 to confirm.
- **Worker in every scope.** The worker query is not limited to one provider account. Every posting uses the row's own organization, environment and currency, and `post_ledger` rejects accounts outside that scope.

## Deviations
