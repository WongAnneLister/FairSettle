# F25 · Proactive trigger

## Goal

Behavior (copied from docs/features.json):

> A dispatch delivery-failure event starts the same flow as a complaint, deduplicated per order.

Verification (copied from docs/features.json, `kind: command`):

```bash
cd agent && python -m pytest -q tests/test_proactive.py
```

This is PRD evaluation scenario 10: "a fulfillment callback reports delivery failed (proactive)", expected decision full refund. The PRD's liability table puts the full amount on the driver or the platform, by failure reason (`docs/plans/F20.md`, "Source: the FairSettle Agent PRD").

### Gap

| Needed | Today |
| --- | --- |
| Dispatch can record a failed delivery | `OrderStatus` is `Pending → Cooking → Cooked → PickedUp → Delivered`. A fulfillment callback with any other status is dropped as `unknown status`, and `order_event` has no failure reason |
| The agent learns about it | The agent's service token reads `getOrder` and `orderTimeline` only. There is no feed of events |
| The agent can read such an order | The agent's `OrderStatus` is a strict `StrEnum`. A new dispatch status would fail validation, and the complaint would escalate as `source_unavailable` |
| One case per order | `Agent.start` already refuses a second `complaint_id` (`DuplicateComplaint`), so a deterministic id per order deduplicates |
| The case must not count against the customer | Every row in `agent_complaint` counts toward the customer's 7-day total (`ComplaintStore.count_prior`, PRD rule "repeat complaint") |

### Decisions (user, 2026-11-01)

1. **New terminal order status `DeliveryFailed`.**
   - Reached only from `PickedUp`.
   - Recorded as a `STATUS_CHANGED` order event that carries a failure reason.
2. **Two failure reasons:**
   - `DRIVER_FAULT`: the driver is liable;
   - `PLATFORM_FAULT`: the platform is liable.
3. **The agent pulls.**
   - Dispatch adds a service-token query, `deliveryFailures(afterEventId, limit)`.
   - The agent reads it from its existing poll loop.
   - It keeps the cursor in its own database.
4. **Who may report a failure:**
   - the fulfillment provider's signed callback;
   - the assigned driver, through `editOrder`.

   No storefront change in F25.
5. **A proactive case neither counts toward the customer's 7-day complaints nor is limited by them.** Its prior count is 0.
6. **Switch:** `FAIRSETTLE_PROACTIVE=on|off`, default `on`.

Planner decisions (no user choice needed):
- **Proactive complaint id.** It is `delivery-failed-<orderId>`, and `POST /v1/complaints` refuses ids with that prefix. Otherwise a customer could escape the repeat rule.
- **Complaint text.** Built by the agent; the exact text is under `proactive.py` below.
- **Cursor.** It only moves forward. An event whose `start` raised stays unprocessed and is retried on the next pass.
- **Liability by reason.** The model prompt and the evidence document state the reason. No new policy rule.
- **Contract.** The contract changes first: `contracts/dispatch-agent-operations.graphql` gains the query and `failureReason` on timeline events. All dispatch agent fixtures are re-recorded.

### `dispatch/src/database/migrations/1790000003000-DeliveryFailure.ts` (new)

Class `DeliveryFailure1790000003000`, `name = 'DeliveryFailure1790000003000'`, doc comment `/** A terminal DeliveryFailed status with a failure reason on its order event (F25). */`.

`up` runs these statements, in order:

1. `ALTER TYPE "public"."order_status_enum" ADD VALUE IF NOT EXISTS 'DeliveryFailed'`
2. `ALTER TABLE "order_event" ADD "failureReason" character varying(16)`
3. `ALTER TABLE "order_event" DROP CONSTRAINT "CHK_order_event_status"`
4. Add `CHK_order_event_status` again:

   ```sql
   ALTER TABLE "order_event" ADD CONSTRAINT "CHK_order_event_status" CHECK (
     ("fromStatus" IS NULL OR "fromStatus" IN ('Pending', 'Cooking', 'Cooked', 'PickedUp', 'Delivered', 'DeliveryFailed'))
     AND ("toStatus" IS NULL OR "toStatus" IN ('Pending', 'Cooking', 'Cooked', 'PickedUp', 'Delivered', 'DeliveryFailed')))
   ```

5. Add `CHK_order_event_failure`:

   ```sql
   ALTER TABLE "order_event" ADD CONSTRAINT "CHK_order_event_failure" CHECK (
     ("failureReason" IS NULL OR "failureReason" IN ('DRIVER_FAULT', 'PLATFORM_FAULT'))
     AND (("kind" = 'STATUS_CHANGED' AND "toStatus" = 'DeliveryFailed') = ("failureReason" IS NOT NULL)))
   ```

6. `CREATE INDEX "IDX_order_event_delivery_failed" ON "order_event" ("id") WHERE "toStatus" = 'DeliveryFailed'`

Postgres 16 allows `ADD VALUE` inside the migration transaction, because the new value is not used later in that transaction (the event columns are `varchar`).

`down` undoes everything:

1. If `SELECT count(*) FROM "order" WHERE "status" = 'DeliveryFailed'` is not 0, throw `new Error('Cannot remove DeliveryFailed while orders use it')`.
2. Drop the index and `CHK_order_event_failure`.
3. Restore the old `CHK_order_event_status` (without `DeliveryFailed`).
4. Drop the column `failureReason`.
5. Recreate `order_status_enum` without `DeliveryFailed`. Postgres cannot drop an enum value, so swap the type. Run exactly these statements, in order:

   ```sql
   ALTER TYPE "public"."order_status_enum" RENAME TO "order_status_enum_old";
   CREATE TYPE "public"."order_status_enum" AS ENUM('Pending', 'Cooking', 'Cooked', 'PickedUp', 'Delivered');
   ALTER TABLE "order" ALTER COLUMN "status" DROP DEFAULT;
   ALTER TABLE "order" ALTER COLUMN "status" TYPE "public"."order_status_enum" USING "status"::text::"public"."order_status_enum";
   ALTER TABLE "order" ALTER COLUMN "status" SET DEFAULT 'Pending';
   DROP TYPE "public"."order_status_enum_old";
   ```

   - **Why the default is dropped and set again:** the column's default `'Pending'` is typed with the old enum, so the type change fails while that default is still on the column.
   - **Why the cast is safe:** step 1 guarantees that no row holds `DeliveryFailed`. The comment in `1789741740482-FixSchemaTypos.ts` describes how this swap breaks when a row holds a value the new type lacks.
   - **No new pattern:** this repository has no earlier migration that swaps a type, which is why the statements are written out here.

### `agent/fairsettle_agent/proactive.py` (new)

```python
"""Proactive cases: a dispatch delivery failure starts the complaint flow once per order (F25)."""

PROACTIVE_PREFIX = "delivery-failed-"
CURSOR = "dispatch.delivery_failures"
BATCH = 50


def is_proactive(complaint_id: str) -> bool:
    return complaint_id.startswith(PROACTIVE_PREFIX)


def complaint_for(failure: DeliveryFailure) -> ComplaintInput:
    return ComplaintInput(
        complaint_id=f"{PROACTIVE_PREFIX}{failure.order_id}",
        order_id=failure.order_id,
        complaint_type="delivery_failed",
        text=f"Dispatch reports that the delivery of order {failure.order_id} failed "
             f"({failure.failure_reason.value}). No customer complaint was received.",
    )


class FailureFeed(Protocol):
    async def delivery_failures(self, after_event_id: int, limit: int) -> list[DeliveryFailure]: ...


class CursorStore(Protocol):
    async def get_cursor(self, name: str) -> int: ...
    async def set_cursor(self, name: str, event_id: int) -> None: ...


class DeliveryFailureTrigger:
    def __init__(self, feed: FailureFeed, cursors: CursorStore,
                 start: Callable[[ComplaintInput], Awaitable[RunStatus]], *, limit: int = BATCH) -> None: ...

    async def run_once(self) -> list[RunStatus]: ...
```

`run_once`:

1. `after = await cursors.get_cursor(CURSOR)`.
2. `failures = await feed.delivery_failures(after, limit)`.
3. For each failure, in the order received:
   - `status = await start(complaint_for(failure))`, and append it to the result;
   - on `DuplicateComplaint`, append nothing and continue;
   - then `await cursors.set_cursor(CURSOR, failure.event_id)`.
4. Any other exception from `start` propagates. Events before it have already moved the cursor; this one and later ones are retried on the next pass.
5. Return the list.

Never log the complaint text.

## Risks

- **`ALTER TYPE ... ADD VALUE` in a transaction.** Allowed on Postgres 16 as long as the value is not used in the same transaction. If the migration fails there, stop and report; do not split migrations on your own.
- **Re-recorded fixtures change shapes.** Every timeline fixture gains `failureReason: null`. Agent tests read fixtures through models with `extra="ignore"` and a default of `None`, so older shapes would still parse. Re-record anyway, so the replay stays exact.
- **A customer complaint and a proactive case on the same order** are two cases. The ledger's refundable amount stops a second full refund: the second proposal escalates with `REFUNDABLE_AMOUNT`.
- **A failure event for an order that does not exist in the agent's view** (deleted order) makes `start` escalate as `source_unavailable`. The cursor moves on.
- **Ordering.** Event ids are serial, so ordering by id is stable. Failures committed out of order around the cursor could be skipped. One dispatch database with short write transactions makes this unlikely; KI material if it is ever observed.
