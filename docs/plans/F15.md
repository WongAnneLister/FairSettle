# F15 · Dispatch checkout through the ledger

## Goal

Behavior (copied from docs/features.json):

> Creating an order calls ledger POST /v1/payments with an Idempotency-Key derived from the order id; a retried order creation never creates a second payment.

Verification (copied from docs/features.json):

```bash
cd dispatch && npm run test:e2e -- --testPathPattern=checkout
```

When checkout is enabled, `createOrder` records, in the order's own transaction, that a ledger payment is owed. The outbox then sends `POST /v1/payments` to the ledger:

- the `Idempotency-Key` and the ledger `orderKey` are both derived from the dispatch order id;
- the order stores the ledger payment id and the PayPal approval link (`checkoutUrl`).

"A retried order creation" means a retried payment request for the same order (user decision, 2026-10-24): a timeout, a crash between the call and its write-back, an outbox redelivery, two concurrent drains. However many times the request is retried, the ledger ends with one payment. A client that calls `createOrder` twice creates two orders. That is out of scope.

The verification runs dispatch e2e against an in-process fake ledger. The real ledger is exercised later, in F24.

### The price model (user decision, 2026-10-24)

The ledger only accepts controlled prices: `amountMinor` must equal the unit price of an active price fixture × `quantity`, with `1 ≤ quantity ≤ 10000` (`PaymentIntentRules.orderAmount`, `PaymentRequests`). A dispatch order total is computed from dishes and options, so it never matches a fixed price.

The agreed bridge:

- a ledger fixture product `dispatch-order`, price version 1, unit price **1 USD cent**, with a 0 bps share policy;
- dispatch sends `quantity = amountMinor = order total in cents`.

Consequence: a checkout-enabled order is limited to 1–10000 cents (USD 0.01–100.00). `createOrder` rejects anything outside that range before writing.

## Design decisions (fixed)

1. **Opt-in.** New env `LEDGER_CHECKOUT`, `enabled` | `disabled`, default `disabled`.
   - When `disabled`, dispatch behaves exactly as today: no payment event, no total limit. Existing e2e, `.env.test` and the root compose keep working unchanged.
   - When `enabled`, these are required:
     - `LEDGER_BASE_URL` (uri);
     - `LEDGER_APP_TOKEN` (string, the ledger application bearer token);
     - `LEDGER_CHECKOUT_SUCCESS_URL` and `LEDGER_CHECKOUT_CANCEL_URL` (uri, scheme `https` only: the ledger rejects other schemes).
   - `LEDGER_TIMEOUT_MS` (number, default `10000`) is optional.
   - Joi enforces all of this with `.when('LEDGER_CHECKOUT', {is: 'enabled', then: required})`.
2. **Keys.** `checkoutKey(orderId)` = `` `dispatch-order-${orderId}` `` is used both as `Idempotency-Key` and as the ledger `orderKey` (8–255 and ≤ 128 visible ASCII: satisfied). Two guarantees follow:
   - the same key replays the original payment;
   - a different key can never create a second payment for the order, because the ledger rejects a reused `orderKey` with `409 ORDER_INTENT_CONFLICT`.
3. **Request body**, built by a pure function, exactly:

   ```json
   {"orderKey": "dispatch-order-<id>", "productRef": "dispatch-order", "priceVersion": 1,
    "quantity": <totalCents>, "amountMinor": <totalCents>, "currency": "USD",
    "successUrl": "<LEDGER_CHECKOUT_SUCCESS_URL>", "cancelUrl": "<LEDGER_CHECKOUT_CANCEL_URL>"}
   ```

   - No `metadata` and no `customerRef`.
   - Headers: `Authorization: Bearer <LEDGER_APP_TOKEN>`, `Idempotency-Key`, `Content-Type: application/json`.
   - The token is never logged or stored, and never put in an error message.
4. **Total limit.** When checkout is enabled, `createOrder` computes the total as today. If it is `< 1` or `> 10000`, it throws `ValidationError('Order total must be between 1 and 10000 cents for checkout')` inside the transaction. The transaction rolls back, nothing is written, and the mutation returns `ok: false` through `failure`.
5. **Outbox event.** New `OutboxEventType.OrderPayment = 'order.payment'`.
   - `OutboxService.enqueueOrderPayment(manager, orderId, {totalCents})` writes it.
   - When checkout is enabled, `createOrder` calls it in the same transaction, right after `enqueueOrderDispatch`.
   - The existing `order.dispatch` event and its delivery are unchanged. Gating fulfillment on payment is F16 or later.
6. **Delivery by type.** `OutboxService.deliver` switches on `event.type`:
   - `order.dispatch` keeps today's code, moved unchanged into `deliverDispatch`;
   - `order.payment` goes to `deliverPayment`, below;
   - an unknown type is marked `Dead` with `lastError = 'unknown outbox event type <type>'`.
7. **Ledger client.** A `LedgerClient` interface with an injection token `LEDGER_CLIENT`, implemented by `HttpLedgerClient` with Node's global `fetch` and `AbortSignal.timeout(LEDGER_TIMEOUT_MS)`. It has one method, `createPayment(request, idempotencyKey): Promise<LedgerPaymentOutcome>`. Outcomes:

   | Ledger answer | Outcome |
   | --- | --- |
   | `201` or `200`, with `nextAction.type === 'REDIRECT_TO_HOSTED_CHECKOUT'` and a `hostedUrl` | `{kind: 'accepted', paymentId: body.id, checkoutUrl: body.nextAction.hostedUrl}` |
   | `201` or `200` without that redirect | `{kind: 'pending', paymentId: body.id}` |
   | `500` with `code === 'PROVIDER_UNKNOWN_RESULT'` | `{kind: 'pending', paymentId: <details[field=paymentId].issue or null>}` |
   | `400`, `401`, `403`, `404`, `409`, `422` | `{kind: 'rejected', status, code: body.code ?? 'UNKNOWN'}` |
   | `429`, any other `5xx`, timeout, network error, unparsable body | throws `LedgerRetryableError(message)`. The message is `ledger <status> <code>` or the error name, never headers or the token |

8. **`deliverPayment`.**
   - **accepted.** In one transaction:
     - update the order: `ledgerPaymentId = paymentId`, `checkoutUrl = checkoutUrl`, but only `WHERE id = :orderId AND ("ledgerPaymentId" IS NULL OR "ledgerPaymentId" = :paymentId)`;
     - mark the event `Sent` with `providerRef = paymentId`, `lastError = null`.

     If the update matched no row (a different payment id is already stored), mark the event `Dead` with `lastError = 'ledger payment id mismatch'` and leave the order untouched.
   - **pending.** If `paymentId` is known, store it on the order under the same guard. Then `recordFailure(event, 'ledger checkout not ready')`: normal backoff, and `Dead` at `MAX_ATTEMPTS`.
   - **rejected.** Mark the event `Dead` at once (`attempts + 1`, `lastError = 'ledger <status> <code>'`), with an error log naming the order id. Nothing is retried, because the answer is deterministic.
   - **thrown.** `recordFailure` as today.
9. **Order columns.** `ledgerPaymentId` (`varchar(64)`, nullable) and `checkoutUrl` (`text`, nullable). Both are exposed as nullable GraphQL fields on `Order` (`@Field(type => String, {nullable: true})`).
   - A partial unique index `ON "order" ("ledgerPaymentId") WHERE "ledgerPaymentId" IS NOT NULL` lets F16 find an order by payment id, and makes one payment per order a database fact.
   - The migration is hand-written, with a working `down`.
10. **Ledger fixture.** `LocalFixtureInitializer` adds, in both FAKE and PayPal mode:
    - a share policy `id(72)`: product `dispatch-order`, version 1, partner `fixture-partner`, 0 bps;
    - a price `id(82)`: product `dispatch-order`, version 1, `USD`, `amount_minor 1`, share policy `id(72)`.

    Insert them in the fresh-database branch, mirroring the existing `demo-product` inserts and validity columns. In the existing-database branch, after the provider check and the credential checks, insert the same two rows with `ON CONFLICT (id) DO NOTHING`. That is additive only, never an update, so databases provisioned before F15 gain the product. Expose `public static final UUID DISPATCH_ORDER_PRICE = id(82)`.
11. **Contract.** `contracts/ledger-openapi.yaml` gains:
    - **operation 9**, `POST /v1/payments`, `createPayment`, tag `payments`, ApplicationBearer `payments:write`, with `IdempotencyKeyRequired`. Responses:
      - `201` (`PaymentSummary`, `Location`), and `200` replay with `Idempotent-Replay`;
      - `400`, `401`, `403`, `404` (unknown price), `409` (`IDEMPOTENCY_CONFLICT`, `ORDER_INTENT_CONFLICT`), `422` (`AMOUNT_MISMATCH`, `CURRENCY_NOT_ENABLED`), `429`, `500` (`PROVIDER_UNKNOWN_RESULT`, detail `paymentId`), `503`.

      Its description states the dispatch convention: `productRef dispatch-order`, unit 1 cent, `quantity = amountMinor`, at most 10000.
    - **`PaymentCreateRequest`**: `orderKey` (1–128), `productRef`, `priceVersion` (integer ≥ 1), `quantity` (integer 1–10000), `amountMinor`, `currency`, `successUrl`, `cancelUrl` (string, format `uri`, https), optional `customerRef`, optional `metadata` (object of strings); `additionalProperties: false`.
    - **`NextAction`**: `type` enum `NONE`, `REDIRECT_TO_HOSTED_CHECKOUT`, `WAIT_FOR_CONFIRMATION` (the three values in `PaymentViewRules`); optional `hostedUrl`, `expiresAt`.
    - **`PaymentSummary.nextAction`**: `NextAction`.
    - **`ErrorCode` additions**: `ORDER_INTENT_CONFLICT` (409), `AMOUNT_MISMATCH` (422), `CURRENCY_NOT_ENABLED` (422), `PROVIDER_UNKNOWN_RESULT` (500, retryable false: query, never resend with a new key), each added to the description table.
12. **No change** to:
    - ledger payment code, the PayPal adapter, `ledger/docs/contracts/openapi.yaml`;
    - dispatch's fulfillment provider, webhooks, order state machine;
    - the root `docker-compose.yml` (checkout stays disabled there; enabling it with a real token is F24's job).

### `dispatch/src/ledger/ledger-client.ts` (new)

```ts
export const LEDGER_CLIENT = Symbol('LEDGER_CLIENT');

export interface LedgerPaymentRequest {
  orderKey: string; productRef: 'dispatch-order'; priceVersion: 1; quantity: number;
  amountMinor: number; currency: 'USD'; successUrl: string; cancelUrl: string;
}

export type LedgerPaymentOutcome =
  | {kind: 'accepted'; paymentId: string; checkoutUrl: string}
  | {kind: 'pending'; paymentId: string | null}
  | {kind: 'rejected'; status: number; code: string};

export interface LedgerClient {
  createPayment(request: LedgerPaymentRequest, idempotencyKey: string): Promise<LedgerPaymentOutcome>;
}

export class LedgerRetryableError extends Error {}
```

### `dispatch/test/utils/fake-ledger.ts` (new)

`export class FakeLedger`. A `node:http` server on `127.0.0.1` with an ephemeral port.

- `start(): Promise<string>` returns the base URL; `stop(): Promise<void>`.
- `requests: Array<{method, path, headers, body}>`.
- `payments: Map<orderKey, {id, key, body}>`.
- `script(orderKey, steps: Step[])`. `Step` is one of:
  - `{respond: 'ok'}`;
  - `{respond: 'status', status, code}`;
  - `{respond: 'unknown'}`: `500 PROVIDER_UNKNOWN_RESULT`, with detail `paymentId` of the stored payment;
  - `{respond: 'slow', delayMs}`: store the payment, then answer `201` after `delayMs`.

`POST /v1/payments` follows the ledger's rules:

1. It requires `Authorization: Bearer …` (else `401`) and `Idempotency-Key` (else `400 IDEMPOTENCY_KEY_REQUIRED`).
2. If the key is already stored for this `orderKey`, it replays: `200`, header `Idempotent-Replay: true`, the same payment with the redirect.
3. If the `orderKey` exists under another key, it answers `409 ORDER_INTENT_CONFLICT`.
4. Otherwise it takes the next scripted step (default `ok`). `ok` stores the payment (id `pay_` + 26 ULID characters) and answers `201` with `{id, orderKey, paymentStatus: 'AWAITING_CUSTOMER', amountMinor, currency, nextAction: {type: 'REDIRECT_TO_HOSTED_CHECKOUT', hostedUrl: 'https://www.sandbox.paypal.com/checkoutnow?token=FAKE<n>'}}`.

Steps are consumed per request for that `orderKey`. A replay consumes no step.

## Out of scope

- A client-side idempotency key on `createOrder` (user decision).
- Payment status driving the order state (F16); holding fulfillment until payment (F16 or later).
- Enabling checkout in the root compose or provisioning a real ledger token (F24).
- Orders above USD 100.00; other currencies.
- Ledger payment code, the ledger's internal OpenAPI file, the PayPal adapter, revenue share code.
