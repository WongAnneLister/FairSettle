# F33 · Storefront pays through PayPal

## Goal

Behavior (copied from docs/features.json):

> The dispatch storefront (dispatch/frontend) sends the customer from checkout to the order's PayPal sandbox checkout, triggers the ledger's payment read when the customer returns, and shows the order's payment status; it runs in the live compose overlay on port 3001.

Verification (copied from docs/features.json, `kind: manual`):

1. Place an order in the storefront at http://localhost:3001 and approve it on the PayPal sandbox page
2. Back in the storefront, the order page shows the order as paid without a reload error, and the payment appears in the ledger console

Today the storefront (`dispatch/frontend`, the Next.js "CravingFast" app imported in `e44ec88` and untouched since) ignores `checkoutUrl` and `paymentStatus`, adds fees that dispatch never charges, offers fake dishes that can enter an order, and does not build (`next build` fails on two type errors in `src/app/page.tsx`). It is in no compose file. This feature makes it the customer-facing half of the F31 demo: order, pay on PayPal, come back, see `Paid`.

### Gap

| Needed | Today |
| --- | --- |
| Something reads the ledger payment after the buyer approves, so the ledger captures | Only `GET /v1/payments/{id}` captures (`PaymentService.get` calls `executor.refresh`); the worker's L2 scan only wakes stranded operations. In F24 the live-run script's reads did it. The browser must not hold the ledger token |
| PayPal's return lands somewhere useful | `LEDGER_CHECKOUT_SUCCESS_URL` / `CANCEL_URL` point at dispatch `/checkout/success` and `/checkout/cancel`, which return 404 |
| Storefront total equals what PayPal charges | The cart adds a 250-cent delivery fee and a 150-cent service fee client-side; dispatch charges the dish sum only |
| Only real dishes reach `createOrder` | Home page `FEATURED_HOME_DISHES`, restaurant `FALLBACK_DISHES` and a fake restaurant, order page "Fallback demo order" |
| A production build | `next build` fails: `src/app/page.tsx(293,28)` and `(295,15)` pass `number \| undefined` where `number` is required (both inside the fake featured-dish code) |
| Runs with the live stack | Not in any compose file; `dev`/`start` use port 3000, which Langfuse uses in the live overlay |

### Decisions (user, 2026-10-31)

1. **Capture trigger: the order page.** New customer-only mutation `refreshOrderPayment(orderId)` in dispatch reads the ledger payment once (which makes the ledger query PayPal and capture an approved order). The order page calls it on load, when the tab becomes visible again, and from a button. PayPal's return goes to dispatch, which only redirects (302) to the storefront. Rejected: appending `?order=<id>` to the success URL and reading on return (changes F15's expected `successUrl`, and a buyer who never returns is never captured).
2. **Fees: remove them from the storefront.** The storefront shows the dish sum, which is what dispatch charges and PayPal collects. Dispatch pricing is unchanged.
3. **Language: Chinese**, like the rest of the storefront. All strings below are exact.
4. **Runs in the live overlay**: `dispatch/frontend/Dockerfile` (Next standalone output) and a `storefront` service in `docker-compose.live.yml` on `127.0.0.1:3001`.
5. **Fake data: remove all of it** from the order path (home featured dishes, restaurant fallback menu and restaurant, order page fallback order), replaced by empty states. This also removes the code with the two type errors.
6. **`createOrder` does not check that dishes belong to the restaurant: record as KI-5**, do not fix in F33.

Planner decisions (no user choice needed): the new failure code `UNAVAILABLE`; vitest `2.1.9` for storefront helper tests; `node:20.19.5-bookworm-slim` for the image; checkout links are followed only when they are `https://www.sandbox.paypal.com/...` (sandbox only).

### `dispatch/src/ledger/payment-refresh.service.ts` (new)

```ts
export const REFRESH_UNAVAILABLE = 'Payment status could not be checked; try again shortly.';

@Injectable()
export class PaymentRefreshService {
  private readonly logger = new Logger(PaymentRefreshService.name);

  constructor(
    @InjectRepository(Order) private readonly orders: Repository<Order>,
    @Inject(LEDGER_CLIENT) private readonly ledger: LedgerClient,
  ) {}

  async refresh(user: User, {orderId}: RefreshOrderPaymentInput): Promise<RefreshOrderPaymentOutput>
}
```

`refresh`, inside `try { … } catch (error) { return failure(error, this.logger, {op: 'refreshOrderPayment', customerId: user.id, orderId}); }`:

1. `order = await this.orders.findOne({where: {id: orderId}})`; none → `throw new NotFoundError('Order not found')`.
2. `order.customerId !== user.id` → `throw new ForbiddenError("You can't refresh that.")`. Only the order's customer may trigger a provider read; owners, drivers and other customers get `FORBIDDEN`.
3. `order.paymentStatus !== OrderPaymentStatus.AwaitingPayment || !order.ledgerPaymentId` → `return {ok: true, paymentStatus: order.paymentStatus}` with no ledger call.
4. `outcome = await this.ledger.readPayment(order.ledgerPaymentId)`. A `LedgerRetryableError` → `this.logger.warn('ledger payment read failed ' + JSON.stringify({orderId, reason: error.message}))`, then `throw new UnavailableError(REFRESH_UNAVAILABLE)`. Any other error is rethrown (a bug, logged by `failure`).
5. `outcome.kind === 'rejected'` → `this.logger.warn('ledger payment read refused ' + JSON.stringify({orderId, status: outcome.status, code: outcome.code}))`, then `throw new UnavailableError(REFRESH_UNAVAILABLE)`.
6. Read the order again (`findOne` by id) and `return {ok: true, paymentStatus: (again ?? order).paymentStatus}`. Never write the order and never record an order event here: `paymentStatus` changes only through signed notifications (F16).

Never log the token, the ledger body, or PayPal's query parameters.

### `dispatch/frontend/src/lib/payment.ts` (new)

Pure helpers, no React, no `window`:

```ts
export const CHECKOUT_ORDER_KEY = 'fairsettle.checkoutOrderId';

export interface PaymentView {
  label: string;
  tone: 'neutral' | 'waiting' | 'success' | 'danger';
  canPay: boolean;
  canRefresh: boolean;
}

export function isSandboxCheckoutUrl(url: string | null | undefined): boolean
export function paymentView(order: Pick<Order, 'paymentStatus' | 'checkoutUrl'>): PaymentView | null
export function rememberCheckoutOrder(storage: Pick<Storage, 'setItem'>, orderId: number): void
export function takeCheckoutOrder(storage: Pick<Storage, 'getItem' | 'removeItem'>): number | null
export function returnPath(result: string | null, orderId: number | null): string
```

- `isSandboxCheckoutUrl`: `true` only if `new URL(url)` parses, `protocol === 'https:'` and `hostname === 'www.sandbox.paypal.com'`; `false` for null, undefined, empty or unparsable input.
- `paymentView`:
  - `paymentStatus` undefined or `NotRequired` → `null` (no card).
  - `AwaitingPayment` and `isSandboxCheckoutUrl(checkoutUrl)` → `{label: '待支付', tone: 'waiting', canPay: true, canRefresh: true}`.
  - `AwaitingPayment` and no `checkoutUrl` → `{label: '正在创建 PayPal 付款…', tone: 'neutral', canPay: false, canRefresh: false}`.
  - `AwaitingPayment` and a `checkoutUrl` that is not sandbox → `{label: '付款链接无效，请联系客服', tone: 'danger', canPay: false, canRefresh: false}`.
  - `Paid` → `{label: '已支付', tone: 'success', canPay: false, canRefresh: false}`.
  - `Failed` → `{label: '支付失败', tone: 'danger', canPay: false, canRefresh: false}`.
- `rememberCheckoutOrder`: `storage.setItem(CHECKOUT_ORDER_KEY, String(orderId))`.
- `takeCheckoutOrder`: read the key, `removeItem` it (always, even when invalid), return the value as a number if it matches `^[1-9][0-9]{0,9}$`, else `null`.
- `returnPath`: `orderId === null` → `'/orders'`; `result === 'canceled'` → `` `/orders/${orderId}?payment=canceled` ``; otherwise `` `/orders/${orderId}` ``.

Before F29 makes dispatch public.

## Risks

- **ngrok browser warning.** On the free plan, a browser's first request to the ngrok host shows ngrok's warning page before `/checkout/success`. The runbook says to choose Visit Site; the webhook path is unaffected (not a browser).
- **Fake-IP DNS proxies** (F24 pitfall) still apply to notifications; the runbook's Troubleshooting covers them.
- **Provider calls per refresh.** Each refresh is one ledger read and at least one PayPal call. The page calls it on load, on becoming visible and on the button, with an in-flight guard, never on the 4-second poll.
- **`useSearchParams` without Suspense** fails `next build` in Next 14; the plan wraps both pages. If the build still reports a missing Suspense boundary for another page, stop and report.
- **Demo login passwords in code** (`auth-context.tsx`, `demo123456`): existing, local demo accounts; they become public with F29. Not changed here; F29 must decide.
- **Rewrites are fixed at build time**; the image is built for the compose network (`dispatch:4000`). Running the image elsewhere needs a rebuild with other build arguments.
- **A closed PayPal tab** leaves the order `AwaitingPayment` until the customer opens the order (load or visibility refresh) or presses the button.
