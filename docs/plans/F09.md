# F09 · Webhook verification and inbox

## Goal

Behavior (copied from docs/features.json):

> PayPal webhooks are verified through the verification API (webhook id from config), deduplicated by event id in the existing inbox; a failed or timed-out verification never posts to the ledger.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='PayPalWebhookVerificationTest' test
```

`PayPalWebhookVerificationTest` is a unit test (no Docker): the verifier against `PayPalTestTransport`, the event snapshot, and the endpoint configuration. The HTTP-to-inbox path also gets an integration test, `PayPalWebhookIT`, which runs under `./mvnw verify` and must pass before the work commit.

### The flow in one paragraph

PayPal sends `POST /webhooks/paypal` with five signature headers and the event JSON. The controller:

1. reads the body up to a configured limit;
2. requires each signature header exactly once;
3. calls `POST /v1/notifications/verify-webhook-signature` with the headers, the configured `webhook_id`, and the raw event embedded byte for byte.

Only `verification_status: SUCCESS` leads to storage. The event is then written once into the existing `platform.webhook_inbox`, keyed by `(scope, event_id)`, as a sanitized snapshot. A repeat with the same bytes is acknowledged as a duplicate; a repeat with different bytes is `EVIDENCE_CONFLICT`. Anything else stores nothing:

- verification `FAILURE` → 400 `SIGNATURE_VERIFICATION_FAILED`;
- timeout or transient error → 503 `SERVICE_UNAVAILABLE`, so PayPal retries.

PayPal events are not processed in F09. The existing worker leaves them `WAITING` with reason `FUTURE_RESOURCE_HANDLER` (ADR §8: "stored, not processed"); F10 adds the handlers. So nothing an F09 webhook does can reach a payment, a refund or the ledger.

## Design decisions (fixed)

1. **The raw event goes to PayPal verbatim.** The verification request body is built by string concatenation:

   ```text
   {"auth_algo":A,"cert_url":C,"transmission_id":I,"transmission_sig":S,"transmission_time":T,"webhook_id":W,"webhook_event":<raw body>}
   ```

   - A, C, I, S, T and W are JSON string literals written by Jackson.
   - `<raw body>` is the received bytes decoded as UTF-8, unchanged.

   Re-serializing the event can change bytes and make PayPal's check fail. The raw body is parsed first and must be a JSON object, so the concatenation is valid JSON.
2. **Only the configured webhook id is used:** `platform.paypal.webhook-id`, falling back to `PAYPAL_WEBHOOK_ID`. It must match `[A-Z0-9]{8,64}`. Nothing in the request can select a webhook id, account or scope (same rule as `StripeWebhookEndpoint`).
3. **Headers.**
   - The five headers are `PAYPAL-AUTH-ALGO`, `PAYPAL-CERT-URL`, `PAYPAL-TRANSMISSION-ID`, `PAYPAL-TRANSMISSION-SIG` and `PAYPAL-TRANSMISSION-TIME`.
   - Each must appear exactly once (the controller checks, else 400). Each value is 1–2048 characters of visible ASCII (33–126).
   - `PAYPAL-CERT-URL` must start with `https://api.sandbox.paypal.com/` or `https://api-m.sandbox.paypal.com/`: sandbox only. The ledger never fetches the certificate; PayPal does.
   - The verifier checks the values and the sandbox prefix before any call.
4. **Verification outcome → HTTP:**
   - `SUCCESS` with a payload → store, then 200 `{"received":true,"duplicate":…}`.
   - `DEFINITIVE_REJECT` or `CONTRACT_MISMATCH` → 400 `SIGNATURE_VERIFICATION_FAILED`.
   - Every other classification → 503 `SERVICE_UNAVAILABLE` with message "Webhook verification unavailable; retry later". Nothing is stored in either error case (ADR §8 rule 1).
5. **Inbox row for a PayPal event** (same table and columns as Stripe; no migration):

   | Column | Value |
   | --- | --- |
   | `provider_account_ref` | the PayPal client id |
   | `event_id` | `id` |
   | `event_type` | `event_type` |
   | `object_id` | `resource.id` |
   | `object_type` | the snapshot's `object` (`paypal.` + lower-case `resource_type`) |
   | `event_created_at` | `create_time` |
   | `received_at`, `available_at` | now |
   | `verified_at` | the verification `respondedAt`, else now |
   | `api_version` | `paypal-notifications-v1` |
   | `raw_digest` | `WebhookNormalizer.digest(raw)` |
   | `object_snapshot` | `PayPalWebhookEvents.snapshot` |

   The binding check requires `provider='PAYPAL'` and `provider_account_ref` = the client id, and everything active and test mode, exactly as Stripe's check.
6. **Dedup (ADR §8 rule 2):**
   - Insert `ON CONFLICT (organization_id,environment_id,provider_account_id,livemode,event_id) DO NOTHING`.
   - Inserted → `duplicate=false`.
   - Not inserted and the stored `raw_digest` equals → `duplicate=true` with the stored id.
   - Different digest → `EVIDENCE_CONFLICT`.
7. **Snapshot whitelist** (`PayPalWebhookEvents.snapshot`). Only these keys, each only if valid, nothing else (no payer, no links, no addresses):

   | Key | Source | Rule |
   | --- | --- | --- |
   | `object` | `"paypal." + resource_type.toLowerCase(Locale.ROOT)` | `resource_type` required, `[A-Za-z_-]{1,64}` |
   | `id` | `resource.id` | required, `[A-Za-z0-9-]{1,64}` |
   | `event_type` | `event_type` | required, `[A-Z0-9._-]{1,128}` |
   | `resource_version` | `resource_version` | text ≤ 16 |
   | `status` | `resource.status` | `[A-Z_]{1,64}` |
   | `custom_id` | `resource.custom_id` | UUID form only |
   | `order_id` | `resource.supplementary_data.related_ids.order_id` | `[A-Z0-9]{1,36}` |
   | `capture_id` | the `href` of `resource.links[rel=up]` ending in `/v2/payments/captures/{id}` | `[A-Z0-9]{1,36}` |
   | `amount` | `resource.amount` → `{currency_code, value}` | `[A-Z]{3}` and `\d+(\.\d+)?`; both or none |
   | `breakdown` | `resource.seller_receivable_breakdown`, else `seller_payable_breakdown` → `{gross, fee, net}` from `gross_amount.value`, `paypal_fee.value`, `net_amount.value` | each `\d+(\.\d+)?`; a key is omitted if absent; the object is omitted if empty |
   | `create_time`, `update_time` | `resource.create_time` / `update_time` | text ≤ 40 |

   A missing required key → `IllegalArgumentException("PayPal webhook event shape is unsupported")`. The receiver turns that into 400 `SIGNATURE_VERIFICATION_FAILED`, as Stripe's receive turns a mismatching event into the same error.
8. **The verifier builds `VerifiedWebhook` from the raw event.** It uses `id`, `event_type`, `resource.id`, `create_time` (`Instant.parse`) and `livemode=false`. Any of them missing or invalid → CONTRACT_MISMATCH `paypal_event_invalid` without a call. The receiver re-checks that the parsed event matches the verified payload, as Stripe's receive does.
9. **No processing change.** `WebhookProcessor` already parks an unknown `object` with `FUTURE_RESOURCE_HANDLER`; test 27 pins that a stored PayPal event changes nothing else.

### Verification call → classification (`PayPalWebhookVerifier`)

`POST /v1/notifications/verify-webhook-signature`, no `PayPal-Request-Id`.

| `PayPalExchange` | Classification | Error code |
| --- | --- | --- |
| `Responded` 200, `{"verification_status":"SUCCESS"}` | SUCCESS + `VerifiedWebhook` | null |
| `Responded` 200, `"FAILURE"` | DEFINITIVE_REJECT | `paypal_signature_invalid` |
| `Responded` 200, any other value, or not JSON | CONTRACT_MISMATCH | `paypal_contract_mismatch` |
| any other status | `PayPalOrderMapping.classify(status)` | `PayPalOrderMapping.errorCode(body)` |
| `NoResponse` | TIMEOUT_UNKNOWN | reason |
| `NotSent` | RETRYABLE_TRANSIENT | reason |

Evidence:

- `idempotencyKeyUsed` null;
- `apiVersion` `paypal-notifications-v1`;
- `rawDigest` = `PayPalOrderMapping.digest("paypal-webhook|" + eventId + "|" + verification status or error)`;
- `providerRequestId` = debug id.

### `provider/adapter/paypal/PayPalWebhookVerifier.java` (new)

```java
/** Verifies PayPal webhooks through PayPal's verification API with the deployment's configured webhook id. */
public final class PayPalWebhookVerifier {
    public static final List<String> HEADERS = List.of(
            "PAYPAL-AUTH-ALGO", "PAYPAL-CERT-URL", "PAYPAL-TRANSMISSION-ID", "PAYPAL-TRANSMISSION-SIG",
            "PAYPAL-TRANSMISSION-TIME");

    public PayPalWebhookVerifier(PayPalAuthClient client, String webhookId, Clock clock)

    /** headers: exactly the five HEADERS keys, single values; raw: the request body bytes. */
    public ProviderCallResult<VerifiedWebhook> verify(byte[] raw, Map<String, String> headers)
}
```

- **Constructor:** null arguments → NPE. A `webhookId` not matching `[A-Z0-9]{8,64}` → `IllegalArgumentException("Valid PayPal webhook id is required")`; never include the value in the message.
- **`verify`:**
  1. Build the `VerifiedWebhook` per decision 8. If it fails: CONTRACT_MISMATCH `paypal_event_invalid`, no call.
  2. Headers missing, invalid or with a non-sandbox cert URL (decision 3) → CONTRACT_MISMATCH. The code is `paypal_cert_url_not_sandbox` for the cert URL, else `paypal_headers_invalid`. No call.
  3. Build the body per decision 1. Call `client.exchange(PayPalHttpRequest.post("/v1/notifications/verify-webhook-signature", Map.of(), body))` and map the result per the table.
  4. `requestedAt` / `respondedAt` as in the other PayPal adapters.
- No logging. The transmission signature, the cert URL and the event never appear in a returned value except inside `VerifiedWebhook`'s ids.

### `webhook/PayPalWebhookReceiver.java` (new)

```java
/** Stores a verified PayPal event once; no business processing. */
@Component
public class PayPalWebhookReceiver {
    public PayPalWebhookReceiver(
            PayPalWebhookInboxRepository inbox, PlatformTransactionManager manager, ObjectMapper json, Clock clock)

    public WebhookInboxRepository.Receipt receive(
            ProviderScope scope, String accountRef, byte[] raw, ProviderCallResult<VerifiedWebhook> verified)
}
```

The transaction template is REQUIRES_NEW / READ_COMMITTED, as in `WebhookInboxRepository`.

`receive`:

1. **Check the input.** Any of the following → `ApiException(SIGNATURE_VERIFICATION_FAILED, "Verified webhook does not match event")`:
   - the raw body does not parse;
   - `verified` is not SUCCESS or has no payload;
   - `scope.livemode()`;
   - `!PayPalWebhookEvents.matches(event, verified.payload())`;
   - `snapshot` throws.
2. **In the transaction:**
   - `!bindingActive` → `ApiException(SERVICE_UNAVAILABLE, "Webhook account binding unavailable")`.
   - `insert` with the values of decision 5. If 1 → `Receipt(id, false)`.
   - Otherwise `stored(...)`. Equal digest → `Receipt(stored.id, true)`; different digest → `ApiException(EVIDENCE_CONFLICT, "Webhook event content conflict")`.

### `webhook/PayPalWebhookEndpoint.java` (new)

```java
/** Trusted PayPal webhook binding; no request field selects an account, scope or webhook id. */
@Component
@Profile("api")
@ConditionalOnProperty(name = "platform.webhooks.paypal.enabled", havingValue = "true")
public final class PayPalWebhookEndpoint {
    @Autowired
    public PayPalWebhookEndpoint(Environment environment, PayPalAuthClient client, Clock clock)

    /** For tests and wiring without Spring. */
    public PayPalWebhookEndpoint(ProviderScope scope, String accountRef, int maximumBytes, PayPalWebhookVerifier verifier)

    ProviderScope scope()
    String accountRef()
    int maximumBytes()
    ProviderCallResult<VerifiedWebhook> verify(byte[] raw, Map<String, String> headers)
}
```

The Spring constructor reads:

- scope: `platform.paypal.organization-id`, `environment-id`, `provider-account-id` (with the F05 env fallbacks);
- `accountRef`: `platform.paypal.client-id` / `PAYPAL_CLIENT_ID`;
- webhook id: `platform.paypal.webhook-id` / `PAYPAL_WEBHOOK_ID`;
- `maximumBytes`: `platform.webhooks.paypal.max-body-bytes`, default 262144, valid 1–1048576.

Any invalid value → `IllegalArgumentException("Enabled PayPal webhook requires valid trusted scope, client id, webhook id and limits")`, never with a cause or a value. Without `platform.paypal.enabled` there is no `PayPalAuthClient` bean and startup fails, which is intended.

`receive` copies `StripeWebhookController.receive` with these differences:

## Out of scope

- **Processing PayPal events** (ADR §8 rules 3–8, posting, the PayPal handlers in `WebhookProcessor`): F10.
- **Freshness checks on `PAYPAL-TRANSMISSION-TIME`, and local certificate validation.** PayPal's API verifies the signature. Replay is covered by the event-id dedup.
- **Webhook registration in the PayPal dashboard, and the compose/env wiring of `PAYPAL_WEBHOOK_ID`:** F12/F13.
- **Files that do not change:**
  - every existing main file, including `WebhookInboxRepository`, `WebhookProcessor`, `WebhookNormalizer` and the Stripe webhook classes;
  - migrations, `contracts/`, `openapi.yaml` (the webhook endpoint is provider-facing, like `/webhooks/stripe`), `dispatch/` and `agent/`.

## Risks

- **Byte-exact verification.** Sending the raw body unchanged is PayPal's documented requirement in practice. If the real sandbox still answers `FAILURE` for genuine events, F12 finds it; do not switch to re-serialized JSON without a replan.
- **Redelivered bodies.** The dedup rule treats the same event id with different bytes as `EVIDENCE_CONFLICT` (Stripe's rule). If PayPal resends the same event with different bytes, those deliveries get 409-class errors and stay unstored after the first. That is safe, because the first copy is stored, but it is noisy. F12 observes it.
- **The verification API is a network call on the webhook request.** A slow PayPal makes the webhook request slow. PayPal retries non-2xx deliveries, so a 503 on timeout loses nothing.
- **Docker.** `PayPalWebhookIT` runs under `./mvnw verify` on the VPS. Sync `ledger/` and `docs/adr/paypal-samples/`, and strip CRLF from `mvnw`.
