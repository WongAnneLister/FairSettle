# F14 · Ledger contract for new endpoints

## Goal

Behavior (copied from docs/features.json):

> contracts/ledger-openapi.yaml describes the refund-proposal and liability endpoints (amounts in integer cents, basis points summing to 10000) and lints clean.

Verification (copied from docs/features.json):

```bash
npx --yes @redocly/cli lint contracts/ledger-openapi.yaml
```

F14 writes the contract that the agent and the ledger build against. It produces no service code. Downstream:

- F17 implements the liability allocation;
- F18 implements the proposal API and review;
- F19 builds the agent's typed ledger client from this file;
- F22 and F23 use the proposal status.

AGENTS.md: "A change to an API between services starts in `contracts/`, then both sides." This is that start.

### Sources

- **FairSettle Agent PRD** (claude.ai doc, 2026-10-22, not in the repository). It contributes:

  - the tool table: `get_payment`, `get_refundable_amount` and `create_refund_proposal` against the ledger;
  - the seven hard policy rules;
  - FR-5: a proposal's idempotency key is derived from `complaint_id`, and the proposal enters the existing human review;
  - FR-7: the three parties' shares sum to the refund amount, and the sub-cent remainder goes to the platform.
- **docs/features.json** F17, F18, F19, F22, F23.
- **`ledger/docs/contracts/openapi.yaml`**: the ledger's own existing API contract (OpenAPI 3.0.3). Its conventions are reused: `amountMinor`, `Error`, `ErrorCode`, `ApplicationBearer` / `OpsBearer`, `Idempotency-Key`, ULID-prefixed ids.

### Decisions made with the user (2026-10-24)

The PRD and the feature list disagree on two points, and the PRD lists a third as an open question:

1. **Approval executes.** When a reviewer approves, the ledger creates the refund and records the liability split in the same transaction (F18's wording). The agent never calls an endpoint that moves money. It polls the proposal, then the refund (F22/F23). The PRD's `execute_refund` tool therefore has no endpoint.
2. **No edits on review.** A reviewer approves the proposal exactly as submitted, or rejects it with a reason. A proposal's content never changes after creation.
3. **Approval signal: polling.** The agent polls `GET /v1/refund-proposals/{proposalId}`, as the PRD's open question leaned. There is no webhook to the agent.

## Design decisions (fixed)

1. **One self-contained file**, `contracts/ledger-openapi.yaml`, OpenAPI `3.0.3` like the ledger's own contract.
   - No external `$ref`.
   - All text in English.
   - `info.title`: `FairSettle Ledger API (cross-service contract)`, `info.version`: `0.1.0-F14`, `info.license`: `{name: Proprietary, url: https://github.com/WongAnneLister/FairSettle}`.
   - `servers`: one templated entry, `url: '{scheme}://{host}:{port}'`, with these variables:
     - `scheme`: enum `[http, https]`, default `http`;
     - `host`: default `localhost`;
     - `port`: default `'8080'`.

     The description says the defaults are the root compose stack seen from the host, and that inside the compose network the host is `ledger-api`.
   - Why a template: a literal `http://localhost:8080` triggers Redocly's `no-server-example.com` warning, which breaks decision 14's zero warnings; Codex found this on 2026-10-24 and the template was checked to lint clean with 2.71.0. A template also covers the compose network and a later deployment (F29).
   - It describes only what other services call. `ledger/docs/contracts/openapi.yaml` stays the ledger's full internal contract and is not changed.
2. **Operations** (exactly these eight):

   | # | Method and path | operationId | Auth and scope | Exists today |
   | --- | --- | --- | --- | --- |
   | 1 | `GET /v1/payments/{paymentId}` | `getPayment` | ApplicationBearer `payments:read` | yes |
   | 2 | `GET /v1/payments/{paymentId}/refundable` | `getRefundableAmount` | ApplicationBearer `payments:read` | no (F18) |
   | 3 | `POST /v1/refund-proposals` | `createRefundProposal` | ApplicationBearer `refund-proposals:write` | no (F18) |
   | 4 | `GET /v1/refund-proposals/{proposalId}` | `getRefundProposal` | ApplicationBearer `refund-proposals:read` | no (F18) |
   | 5 | `GET /v1/refunds/{refundId}` | `getRefund` | ApplicationBearer `refunds:read` | yes |
   | 6 | `GET /v1/refunds/{refundId}/liability` | `getRefundLiability` | ApplicationBearer `refunds:read` | no (F17) |
   | 7 | `GET /ops/refund-proposals` | `listRefundProposals` | OpsBearer `ops:refund-proposal:read` (OPS_VIEWER and above) | no (F18) |
   | 8 | `POST /ops/refund-proposals/{proposalId}/decision` | `decideRefundProposal` | OpsBearer `ops:refund-proposal:review` (OPS_REVIEWER only) | no (F18) |

   Operations 1 and 5 exist already and are documented as they are. The other six are new.
   - Tags: `payments`, `refund-proposals`, `refunds`, `ops-review`, each with a one-line description.
   - Every operation has `summary`, `description`, `operationId`, one tag, `security`, a `2xx` response, `401`, at least one more `4xx`, and `500`. All error responses use `Error`.
3. **Money and shares.**
   - Every amount is `AmountMinor`: `integer`, `format: int64`, `minimum: 0`. The description says "integer minor units; for USD, cents (10000 = USD 100.00); never a float". Amount fields in request bodies use `allOf: [AmountMinor]` with `minimum: 1`.
   - No schema anywhere uses `type: number`.
   - Shares are `BasisPoints`: `integer`, `minimum: 0`, `maximum: 10000`.
   - A liability split is an array of exactly three `LiabilityShare` objects, one per party. Its description states: "the three basisPoints sum to exactly 10000; each party appears once; otherwise 422 LIABILITY_SPLIT_INVALID". JSON Schema cannot express the sum; the server enforces it (F18), and the description says so.
4. **Parties:** `LiabilityParty` enum `RESTAURANT`, `DRIVER`, `PLATFORM`. `DRIVER` follows the PRD and dispatch's own naming (`driver` 21 times in `dispatch/src`); F17's "courier" means the same party.
   - Enums in this contract are UPPER_SNAKE, like the ledger's existing enums. The agent client maps the PRD's lowercase literals 1:1, for example `driver` ↔ `DRIVER`.
5. **Allocation rule** (`LiabilityAllocation`, implemented by F17). For a refund of `A` minor units:
   - `RESTAURANT` gets `floor(A × bp_restaurant / 10000)`;
   - `DRIVER` gets `floor(A × bp_driver / 10000)`;
   - `PLATFORM` gets `A − restaurant − driver`.

   So the lines always sum to `A`, and the sub-cent remainder goes to the platform (PRD FR-7). The schema description states this rule and carries one worked example: A = 1250, 3333/3333/3334 → 416/416/418.
6. **Reasons and decisions:**
   - `RefundReasonCode` enum: `LATE_DELIVERY`, `MISSING_ITEM`, `WRONG_ITEM`, `QUALITY`, `DELIVERY_FAILED`, `OTHER` (PRD `reason_code`).
   - `ProposalDecision` enum: `FULL_REFUND`, `PARTIAL_REFUND`. The PRD's `reject` and `escalate` are never submitted as proposals: those stay with the agent.
   - The ledger stores `decision` as given and does not derive rules from it.
7. **`POST /v1/refund-proposals` idempotency** has two layers:
   - **The key.** `Idempotency-Key` is required, as on every ledger POST; the agent derives it as `refund-proposal:<complaintId>`. Same key and same body → `200` with header `Idempotent-Replay: true` and the original proposal. Same key and a different body → `409 IDEMPOTENCY_CONFLICT`.
   - **The complaint.** `complaintId` is unique per application. A new key for a complaint that already has a proposal → `409 PROPOSAL_EXISTS`, with `details: [{field: "complaintId", issue: "<existing proposal id>"}]`.

   A new proposal → `201`, with header `Location: /v1/refund-proposals/{id}`.
8. **Validation at creation** (F18 implements; the contract lists each case and its response):

   | Condition | Response |
   | --- | --- |
   | Malformed body, unknown field, `explanation` or `evidenceRefs` out of bounds | `400 VALIDATION_ERROR` |
   | Missing `Idempotency-Key` | `400 IDEMPOTENCY_KEY_REQUIRED` |
   | `paymentId` not found in the caller's scope | `404 NOT_FOUND` |
   | `currency` differs from the payment's | `422 VALIDATION_ERROR`, detail field `currency` |
   | Shares do not sum to 10000, a party is repeated or missing | `422 LIABILITY_SPLIT_INVALID` |
   | `amountMinor` > the payment's current `refundableMinor` | `422 REFUND_LIMIT_EXCEEDED` |
   | The payment's refund control state is not `NORMAL` | `409 REFUND_BLOCKED` |

   A proposal reserves nothing. The refundable amount is checked again at approval.
9. **Proposal lifecycle:** `RefundProposalStatus` enum `PENDING_REVIEW` → `APPROVED` or `REJECTED`. Both outcomes are final.
   - **Approve** (`{action: APPROVE}`). In one transaction the ledger:
     1. re-checks the refundable amount and the control state;
     2. creates the refund through the existing refund reservation;
     3. stores the allocation;
     4. sets the proposal to `APPROVED` with `refundId`, `reviewer` and `reviewedAt`.

     The worker then sends the refund to PayPal, as for any refund. If the re-check fails, the response is `422 REFUND_LIMIT_EXCEEDED` or `409 REFUND_BLOCKED`, and the proposal stays `PENDING_REVIEW`: nothing is changed, and the reviewer may reject.
   - **Reject** (`{action: REJECT, reason}`, reason 1–500 characters). Sets `REJECTED`, `reviewer`, `reviewedAt` and `rejectionReason`. Nothing else changes.
   - **Repeats.** The same decision again (any `Idempotency-Key`) → `200` with the current proposal and `Idempotent-Replay: true`. A different decision on a decided proposal → `409 PROPOSAL_NOT_PENDING`.
   - **No edits.** The decision request has no amount or liability fields, and `additionalProperties: false` (decision 2 with the user).
10. **Liability endpoint.** `GET /v1/refunds/{refundId}/liability` → `LiabilityAllocation`. Fields:
    - `refundId`, `proposalId`, `currency`, `amountMinor`;
    - `lines`: three `LiabilityLine` items, each `party`, `basisPoints`, `amountMinor`;
    - `postingStatus`: `PENDING` | `POSTED`;
    - `journalId`: nullable string.

    A refund that did not come from a proposal → `404 NOT_FOUND`. When the allocation is posted and to which accounts is F17's decision; the contract only exposes `postingStatus` and `journalId`.
11. **Refundable amount.** `GET /v1/payments/{paymentId}/refundable` → `RefundableAmount` with:
    - `paymentId`, `currency`;
    - `capturedMinor`, `refundedMinor`, `reservedMinor`;
    - `refundableMinor`: `max(0, captured − refunded − reserved)` when `controlState` is `NORMAL`, else `0`;
    - `controlState`.

    This is the PRD hard rule 1's "captured minus refunded and reserved".
12. **Existing operations are documented, not changed.**
    - `PaymentSummary` (op 1) lists these fields from `PaymentReader`: `id`, `orderKey`, `provider`, `paymentStatus`, `resolutionStatus`, `financialStatus`, `amountMinor`, `currency`, `capturedAmountMinor`, `checkoutSessionId`, `latestChargeId`, `createdAt`, `updatedAt`.
    - `RefundSummary` (op 5) lists these from `RefundReader`: `id`, `paymentId`, `amountMinor`, `currency`, `refundStatus`, `resolutionStatus`, `financialStatus`, `providerRefundId`, `providerStatus`, `controlState`, `createdAt`, `updatedAt`.
    - Both have `additionalProperties: true`, because the real responses carry more fields than other services need.
    - Before writing them, check each name against the reader classes. A name that does not exist there is a plan error: stop and report it.
13. **New error codes**, added to a contract-local `ErrorCode` enum. The enum is a copy of the ledger's, limited to the codes these operations return, plus:
    - `LIABILITY_SPLIT_INVALID` (422, not retryable);
    - `PROPOSAL_EXISTS` (409, not retryable);
    - `PROPOSAL_NOT_PENDING` (409, not retryable).

    The description table lists `code | HTTP | retryable | meaning` for every code in the enum.
14. **Lint target: zero errors and zero warnings** with the default (recommended) Redocly ruleset. No `redocly.yaml` is added, so the verification command lints with defaults. Do not suppress rules.

## Deviations

Filled in during review: what changed from this plan, why, and in which commit.

- **Templated server URL (plan correction before the work commit).** The first version had a literal `http://localhost:8080`, which trips Redocly's `no-server-example.com` warning and so breaks decision 14. Decision 1 now specifies `{scheme}://{host}:{port}` with defaults `http`, `localhost`, `8080`, and test 1 checks it. The review lint with 2.71.0 gives no errors and no warnings.
- **`PaymentSummary`: provider ids are nested (review, recorded only).** Decision 12 lists `checkoutSessionId` and `latestChargeId` as if they were top-level fields. `PaymentReader#resource` puts them under `provider`, together with `paymentIntentId` and `attempts`. The work commit `58f75cc` declares `provider` as a required object holding the two nullable ids, with `additionalProperties: true`. That matches the real response. The other eleven `PaymentSummary` names and all twelve `RefundSummary` names are top-level keys in `PaymentReader` and `RefundReader`. No code change.
- **Responses beyond the plan's minimum (review, recorded only).** Every operation also declares `403` and `429`. Ops 3 and 8 also declare `400`, `409`, `422` and `503`, and op 7 declares `404`. Op 8's description adds one sentence: reusing an `Idempotency-Key` with different content gives `409 IDEMPOTENCY_CONFLICT`. That is the ledger's general rule for the header (`IdempotencyKeyRequired`). Because of the `oneOf`, `{action: APPROVE, reason: …}` is rejected with 400. All of this is consistent with decisions 2, 7 and 9. No code change.
- **Currency mismatch is `400 VALIDATION_ERROR` (review fix, decided with the user on 2026-10-24).** Decision 8 says `422 VALIDATION_ERROR`, detail field `currency`. The ledger cannot return that: `common/error/ErrorCode.java` binds each code to one HTTP status, and `VALIDATION_ERROR` is `BAD_REQUEST`. The user chose to keep the code and change the status, so no new error code is needed. The contract now says 400 in op 3's validation table, the `BadRequest` and `UnprocessableEntity` descriptions and the `ErrorCode` table. The detail field `currency` is unchanged. F18 implements 400.
