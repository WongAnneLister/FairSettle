# F10 · Webhook events posted

## Goal

Behavior (copied from docs/features.json):

> Capture-completed and refund-completed events update payment/refund state and ledger entries; out-of-order or duplicate events are rejected by the state machine without side effects.

Verification (copied from docs/features.json):

```bash
cd ledger && ./mvnw -q -Dtest='PayPalWebhookPostingTest' test
```

`PayPalWebhookPostingTest` is a unit test (no Docker). It covers:

- snapshot → fact mapping, which must be identical to the query and refund-response mappings;
- routing;
- the state-machine rules the events go through.

The inbox-to-ledger path also gets an integration test, `PayPalWebhookPostingIT`. It runs under `./mvnw verify` and must pass before the work commit.

### The flow in one paragraph

F09 stores verified PayPal events in `platform.webhook_inbox`, with a snapshot whose `object` is `paypal.<resource_type>`. Today `WebhookProcessor` parks them as `FUTURE_RESOURCE_HANDLER`. F10 sends every `paypal.*` snapshot to a new `PayPalWebhookHandler`, which handles exactly two events:

- **`PAYMENT.CAPTURE.COMPLETED` (`paypal.capture`).** The handler builds the same `ChargeFact` and `BalanceTransactionFact` that `PayPalOrderMapping.orderFact` builds from a GET order. It finds the payment by `order_id`, checks `custom_id`, amount and currency, and merges through the existing `PaymentRepository.mergeWebhook`. Then it posts the settlement through the existing `CaptureSettlementService`.
- **`PAYMENT.CAPTURE.REFUNDED` (`paypal.refund`).** The handler builds the same `RefundFact` that `PayPalRefundMapping.refund` builds. It finds the local refund by provider refund id, else by `custom_id`, and merges through the existing `RefundRepository.accept`. Then it posts the refund settlement through `CaptureSettlementService`.

Every other PayPal event stays `WAITING` / `FUTURE_RESOURCE_HANDLER`, as in F09.

Duplicates and out-of-order events are absorbed by the existing rules, not by new ones:

- `CAPTURE:<id>` normalized facts and attempt upserts;
- `PaymentEvidenceRules.isStale` / `decide`;
- `RefundFactRules.merge`: terminal is final, terminal → other terminal is CONFLICT;
- the BT `immutable_fact` comparison, then replay, which never posts a BT twice.

A webhook copy of a fact already seen through a query or a refund response matches it field for field. So it adds no attempt, no BT, no journal and no notification.

## Design decisions (fixed)

1. **Only two events are handled.** `PayPalWebhookHandler.route(object, eventType)`:

   | `object` | `event_type` | Route |
   | --- | --- | --- |
   | `paypal.capture` | `PAYMENT.CAPTURE.COMPLETED` | CAPTURE |
   | `paypal.refund` | `PAYMENT.CAPTURE.REFUNDED` | REFUND |
   | anything else, or a null argument | | UNSUPPORTED → `waitFor(claim, "FUTURE_RESOURCE", id, "FUTURE_RESOURCE_HANDLER")`, exactly as F09 |

   `PAYMENT.CAPTURE.PENDING/DECLINED/REVERSED`, `PAYMENT.REFUND.PENDING/FAILED` and `CHECKOUT.ORDER.APPROVED` stay unprocessed (out of scope below).
2. **Webhook facts are byte-for-byte the API facts.** `PayPalWebhookFacts.capture` produces exactly the `ChargeFact` and `BalanceTransactionFact` that `orderFact` produces for the same capture. `PayPalWebhookFacts.refund` produces exactly the `RefundFact` (with settlement) that `PayPalRefundMapping.refund` produces. This is what makes a query, a response and a webhook one fact:
   - the capture fact key `CAPTURE:<id>` (D4);
   - the attempt keyed by provider object id;
   - the BT `immutable_fact` and `bt_id`.

   Tests 1 and 2 pin the equality.
3. **Payment link for a capture (ADR §8):**
   - Find the payment by `order_id` = `payment.checkout_session_id` in the claim's scope.
     - 0 rows → `waitFor("PAYMENT", order_id, "MISSING_PAYMENT_DEPENDENCY")` (rule 6: retried with the inbox backoff, never dropped).
     - 2 or more → `waitFor("EVIDENCE", id, "AMBIGUOUS_RELATIONSHIP")`.
   - Under the payment lock, either mismatch below is CONFLICT via the Stripe error path, then `waitFor("EVIDENCE", capture id, reason)`:
     - `custom_id` ≠ payment id → `RELATIONSHIP_CONFLICT`;
     - capture amount ≠ `amount_minor` or currency ≠ the payment currency (case-insensitive) → `AMOUNT_CURRENCY_CONFLICT`.
4. **Capture merge.**
   - Call `mergeWebhook(payment, new PaymentFacts(null, null, List.of(charge), true, false, eventTime))`.
   - `eventTime` = the snapshot's `update_time`, else `create_time`, else the inbox `event_created_at` (ADR §8 rule 4).
   - `PaymentStateMerger` then applies the existing rules:
     - a capture moves the payment to SUCCEEDED from any non-canceled status (rule 7);
     - a stale or duplicate copy changes no status;
     - a contradicting attempt is CONFLICT;
     - capture after CANCELED is CONFLICT.
5. **Posting follows the committed merge.**
   - **Capture.** Post if `mergeWebhook` returned true (the same `applicable` rule the query path uses) and the fact has a settlement. Then call `CaptureSettlementService.record(scope, settlement, evidence)` outside the transaction.
   - **Refund.** Post if all of the following hold, then call `record` the same way:
     - `accept` returned a refund id;
     - the fact has a settlement;
     - the row `refunds.lookup(scope, refund id)` exists, has that id, `refund_status='SUCCEEDED'` and `resolution_status<>'CONFLICT'`.
   - **Order.** `done` runs in its own transaction after posting, and only if the claim is still owned. If `record` throws, the exception reaches `processDue`, which calls `inbox.retry`. The event is processed again later; the merge is idempotent and the BT is never posted twice.
   - **No settlement service** (`settlements` null) → no posting, `done`. Posting is then left to the next query (as F06).
6. **Refund link (ADR §8: "matched by refund id, else by custom_id").**
   - `existing = refunds.lookup(scope, refund id)`. If found, `local = existing.id` and `payment = existing.payment_id`.
   - Otherwise:
     - `charged = refunds.paymentForCharge(scope, capture_id)`;
     - `custom = customId == null ? null : paymentRefs.refundPayment(scope, customId)`;
     - `custom` and `charged` both non-null and different → `waitFor("EVIDENCE", refund id, "RELATIONSHIP_CONFLICT")`, no merge;
     - `local = custom != null ? customId : null`;
     - `payment = charged != null ? charged : custom`.
   - In the transaction:
     - lock `payment` if non-null;
     - `owns`;
     - `accepted = refunds.accept(scope, fact, evidence, local)`;
     - null → `waitFor("CHARGE", capture_id, "MISSING_REFUND_PAYMENT_DEPENDENCY")`, as in `RefundWebhookHandler`.
   - `RefundFactRules.merge` decides the rest: terminal SUCCEEDED again → no change and no settlement; FAILED/CANCELED → CONFLICT; amount or charge mismatch → CONFLICT.
7. **`latest_charge_id` from a capture webhook.** A capture that arrives by webhook first (for example, the capture response was lost, F07) must still give the payment its refund anchor (F08 refunds by `latest_charge_id`). Today `latestChargeId` returns null when there is no session.
   - The new rule: with no intent and no session, the single captured, succeeded charge is returned if every charge's `outcomeType` is a PayPal capture status.
   - Stripe charge webhooks carry `outcomeType` null and Stripe outcome types are lower-case, so Stripe is unchanged. Test 8 pins this.
8. **The inbox row status after handling:**
   - DONE when the merge ran (including duplicate and CONFLICT results, as Stripe does);
   - WAITING with the reasons above otherwise.

   No new reason strings beyond `INCOMPLETE_CAPTURE` and `INCOMPLETE_REFUND_FACT`, for snapshots the mapping refuses.

### `provider/adapter/paypal/PayPalWebhookFacts.java` (new)

```java
/** Ledger facts from stored PayPal webhook snapshots; the same values and digests as the API mappings (ADR D4, D9). */
public final class PayPalWebhookFacts {
    /** @param updatedAt update_time, else create_time, else null */
    public record Capture(
            String orderId, UUID paymentId, ChargeFact charge, BalanceTransactionFact settlement, Instant updatedAt) {}

    /** @param customId the ledger refund id from custom_id, or null */
    public record Refund(UUID customId, RefundFact fact, Instant updatedAt) {}

    private PayPalWebhookFacts() {}

    public static Optional<Capture> capture(JsonNode snapshot)

    public static Optional<Refund> refund(JsonNode snapshot)
}
```

The input is the `object_snapshot` that F09's `PayPalWebhookEvents.snapshot` wrote. Times parse with `Instant.parse`; an unparseable time counts as absent.

**`capture`** returns empty unless every rule below holds:

- **Event:**
  - `object` = `paypal.capture`;
  - `event_type` = `PAYMENT.CAPTURE.COMPLETED`;
  - `status` = `COMPLETED`;
  - `id` matches `[A-Z0-9]{1,36}`.
- **Correlation:**
  - `order_id` present;
  - `custom_id` present and `UUID.fromString` succeeds.
- **Amount:** `amount.currency_code` and `amount.value` give `PayPalOrderMapping.minor(value, currency)` present and > 0.
- **If `breakdown` is present:**
  - `gross` and `net` are present; `fee` is optional and counts as `"0"` when absent;
  - each converts with `minor(…, currency)`;
  - `gross` = amount and `gross − fee` = `net`;
  - `create_time` is present and parses.
- **Charge:** `new ChargeFact(id, order_id, "succeeded", true, amount, amount, currency, settlement == null ? null : id, null, "COMPLETED", createTime)`, where `createTime` may be null without a breakdown.
- **Settlement:** with a breakdown, exactly `orderFact`'s:

  ```java
  new BalanceTransactionFact(id, "charge", gross, fee, net, currency, "PAYMENTS", id, "charge", "available", createTime, null,
          fee > 0 ? List.of(new FeeDetail(fee, currency, "paypal_fee", null)) : List.of(),
          PayPalOrderMapping.digest("paypal-capture|" + id + "|" + gross + "|" + fee + "|" + net))
  ```

  Without a breakdown it is null.

**`refund`** returns empty unless every rule below holds:

- **Event:**
  - `object` = `paypal.refund`;
  - `event_type` = `PAYMENT.CAPTURE.REFUNDED`;
  - `status` = `COMPLETED`;
  - `id` matches `[A-Z0-9]{1,36}`.
- **Capture link:** `capture_id` present.
- **Amount:** minor and > 0, as for `capture`.
- **`custom_id`:** absent or not a UUID → `customId` null. It is never a reason for empty.
- **If `breakdown` is present:** the same checks as for `capture`, including that `create_time` is required.
- **Settlement:** exactly `PayPalRefundMapping.refund`'s:

  ```java
  new BalanceTransactionFact(id, "refund", -gross, -fee, -net, currency, "PAYMENTS", id, "refund", "available", createTime, null,
          fee > 0 ? List.of(new FeeDetail(-fee, currency, "paypal_fee", null)) : List.of(),
          PayPalOrderMapping.digest("paypal-refund|" + id + "|" + gross + "|" + fee + "|" + net))
  ```

- **Fact:** `new RefundFact(id, capture_id, "COMPLETED", amount, currency, settlement == null ? null : id, null, null, createTime, settlement)`.

No logging, no I/O.

### `webhook/PayPalWebhookHandler.java` (new)

```java
/** Applies verified PayPal capture-completed and refund-completed snapshots; posts after the state commit; no provider I/O. */
@Component
public final class PayPalWebhookHandler {
    public enum Route { CAPTURE, REFUND, UNSUPPORTED }

    @Autowired
    public PayPalWebhookHandler(
            WebhookInboxRepository inbox,
            PaymentRepository payments,
            RefundRepository refunds,
            PayPalWebhookPaymentRepository paymentRefs,
            ObjectProvider<CaptureSettlementService> settlements)

    /** For tests and wiring without Spring; settlements may be null. */
    public PayPalWebhookHandler(
            WebhookInboxRepository inbox,
            PaymentRepository payments,
            RefundRepository refunds,
            PayPalWebhookPaymentRepository paymentRefs,
            CaptureSettlementService settlements)

    /** Decision 1. */
    public static Route route(String object, String eventType)

    /** Called by WebhookProcessor for every paypal.* snapshot, outside transactions. */
    public void process(WebhookInboxRepository.Claim claim, JsonNode object)
}
```

Helpers:

- `scope(row)` = `new ProviderScope(organization_id, environment_id, provider_account_id, false)` from the claim row.
- `evidence(row)` = `new ProviderEvidence(null, null, t, t, 200, null, raw_digest, api_version)` with `t` = `event_created_at`.
- `waitOwned(claim, type, id, reason)` = `inbox.transaction(() -> { if (inbox.owns(claim)) inbox.waitFor(claim, type, id, reason); return null; })`.
- `doneOwned(claim)` does the same with `inbox.done(claim)`.

`process` takes `route(object.object, row.event_type)`:

- UNSUPPORTED → `waitOwned(claim, "FUTURE_RESOURCE", object.id, "FUTURE_RESOURCE_HANDLER")`.
- CAPTURE:
  1. `PayPalWebhookFacts.capture(object)`. If empty → `waitOwned("EVIDENCE", object.id, "INCOMPLETE_CAPTURE")`.
  2. `ids = paymentRefs.paymentsForOrder(scope, orderId)`. 0 rows or 2 rows → decision 3.
  3. In `inbox.transaction`:
     - `p = payments.lockWebhookPayment(id)`;
     - `!inbox.owns(claim)` → return null;
     - the decision 3 checks against `p.amount_minor` / `p.currency` (error path, return null);
     - `applicable = payments.mergeWebhook(…)` per decision 4;
     - return `applicable && settlement != null`.
  4. A null return (wait or lost lease) → stop.
  5. Otherwise, if true and `settlements != null` → `settlements.record(scope, settlement, evidence(row))`.
  6. `doneOwned(claim)`.
- REFUND:
  1. `PayPalWebhookFacts.refund(object)`. If empty → `waitOwned("EVIDENCE", object.id, "INCOMPLETE_REFUND_FACT")`.
  2. Resolve `local` / `payment` per decision 6. The RELATIONSHIP_CONFLICT case → `waitOwned` and stop.
  3. In `inbox.transaction`:
     - lock `payment` if non-null;
     - `owns`;
     - `accepted = refunds.accept(scope, fact, evidence(row), local)`;
     - null → `inbox.waitFor("CHARGE", capture_id, "MISSING_REFUND_PAYMENT_DEPENDENCY")`, return null;
     - otherwise return the decision 5 refund posting condition.
  4. Then as CAPTURE steps 4–6, with `fact.settlement()`.

## Out of scope

- **The other PayPal events:** `CHECKOUT.ORDER.APPROVED`, `CHECKOUT.PAYMENT-APPROVAL.REVERSED`, `PAYMENT.CAPTURE.PENDING/DECLINED/REVERSED`, `PAYMENT.REFUND.PENDING/FAILED`. They stay `FUTURE_RESOURCE_HANDLER`; no feature in the list covers them yet. ADR §8 lists their effect for a later feature.
- **Webhook-triggered GET order.** The webhook is applied as level-3 evidence without provider I/O; the existing recovery queries still run as before.
- **External refunds discovered only by webhook** (no local refund, no `custom_id` match). They go through the existing `RefundFactMerger` external path unchanged, and F10 adds no test for it.
- **Files that do not change:**
  - every main file other than `WebhookProcessor` and `PaymentEvidenceRules`, including `PayPalWebhookEvents`, `PayPalWebhookReceiver`, `RefundWebhookHandler`, `RefundFactMerger`, `PaymentStateMerger`, `CaptureSettlementService` and the PayPal API mappings;
  - migrations, the F09 fixtures, `PayPalCaptureFixture`, the existing tests;
  - `contracts/`, `openapi.yaml`, `docs/adr/` (the §11 table gets its F10 row in a later docs change), `dispatch/` and `agent/`.

## Risks

- **Breakdown currency.** The F09 snapshot keeps only the breakdown values, not their currency codes, so F10 assumes the capture currency. PayPal reports seller breakdowns in the capture currency for same-currency accounts, which is all the sandbox uses. A cross-currency account would need the snapshot extended (replan).
- **Real event shape.** `PAYMENT.CAPTURE.REFUNDED` was not observed in F02 (ADR §8). If the real resource lacks `create_time` or the `up` link, the event waits as `INCOMPLETE_REFUND_FACT` and the refund still settles through F08's query path. F12 observes it.
- **Staleness uses the resource `update_time`.** A webhook older than the last successful query is stale and changes no status, but its capture is still recorded as a fact (existing merger behavior). In the IT, times are set relative to the fake clock, which starts at `Instant.now()`.
- **Posting after commit.** If posting fails, the event is retried, and the merge repeats harmlessly. A permanently failing post keeps the event retrying with the inbox backoff (max 300 s), visible as `PROCESSING_RETRY`.
- **Docker.** `PayPalWebhookPostingIT` runs under `./mvnw verify` on the VPS. Sync `ledger/` and `docs/adr/paypal-samples/`, and strip CRLF from `mvnw`.
