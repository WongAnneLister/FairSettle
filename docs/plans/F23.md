# F23 · Execute and trace

## Goal

Behavior (copied from docs/features.json):

> After approval the agent triggers execution through the ledger only; every run is traceable in Langfuse by complaint id.

Verification (copied from docs/features.json):

```bash
cd agent && python -m pytest -q tests/test_execute.py
```

F23 finishes the complaint's life cycle in the F22 graph and makes it visible in Langfuse.

1. **Execution.** In this system, approving a proposal *is* the execution trigger. The reviewer's approval in the ledger (F18, op 8) reserves the refund, records the liability split, and hands the refund to the ledger worker, which sends it to PayPal. The agent never moves money and has nothing to send. After approval it **follows the refund through the ledger**: the same thread pauses again (`await_refund`), and `Agent.poll()` reads `GET /v1/refunds/{refundId}` until the refund is final. The contract says so: "On approval, poll refundId through getRefund". This is also how the agent tells apart an approved proposal whose refund failed (KI-3).
2. **"Through the ledger only"** is proven twice:
   - over a whole run, the agent's only ledger calls are its five reads and the single proposal POST;
   - a static test shows the ledger client has no other write, and that no agent module mentions PayPal.
3. **Tracing.** Every invocation (start, submit retry, review resume, refund resume) is a Langfuse trace observation. Each trace id is derived from the complaint id, `Langfuse.create_trace_id(seed=complaint_id)`, and the session id is the complaint id. So everything about one complaint, across processes and restarts, is one Langfuse trace and one session. The trace id also goes to the ledger in `agentRun.traceId`.

The long-running process that calls `poll()` on a timer, the agent's compose service, a live Langfuse server and a real refund in the sandbox are F24.

### Decisions made with the user (2026-10-30)

- **Refund following is in the graph**: one thread covers the whole life cycle. Because of this, three F22 tests change deliberately, and no assertion is weakened (Changes, `test_resume.py`):
  - R13 now expects `state.next == ("await_refund",)` after approval, not `()`;
  - R15's second `poll()` now reads the refund once;
  - R28 builds its full config with `FAIRSETTLE_TRACING=off`.
- **Langfuse gets metadata only**: ids, stage timings, model name, token counts, decision kind, amount, violated rules, escalation reasons, proposal and refund statuses. Never the complaint text, the model's reply or explanation, the evidence, a reviewer's rejection reason, or a customer id. This is the F21 `RunRecord` rule.
- **Refund fixture: one recorded refund, terminal states in memory.** `AgentFixturesHttpIT` records the real refund that an approval creates (`RESERVED`). `SUCCEEDED`, `FAILED`, `CANCELED`, `SUBMITTED`/`UNKNOWN` and a `CONFLICT` are built in the tests from that recorded body, in memory (F22 R7's method). The real terminal shapes are checked live in F24.
- **Tracing is on by default.** `AgentConfig.from_env` requires `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL`, unless `FAIRSETTLE_TRACING=off` is set explicitly.

### What was checked while planning (Python 3.11; langfuse 5.0.4; Docker running)

- `langfuse==5.0.4` and `opentelemetry-sdk==1.45.1` resolve with every existing pin unchanged (105 packages). Langfuse 5 is built on OpenTelemetry.
- **No network in tests**: `Langfuse(public_key=…, secret_key=…, base_url="http://langfuse.invalid", span_exporter=InMemorySpanExporter(), tracer_provider=TracerProvider())`, creating observations, and `flush()` made no connection under the F21 socket guard.
  - **`get_trace_url()` does connect**: it fetches the project id from the server. The agent never calls it; F28 builds the link itself.
- `Langfuse.create_trace_id(seed="complaint-missing-drink-001")` returns the same 32-character lowercase hex id every time. It fits `AgentRun.traceId` (1–128).
- `start_as_current_observation(trace_context={"trace_id": tid}, name=…)` puts the observation in that trace. Inside `propagate_attributes(session_id=…, trace_name=…)`, every span carries `session.id` and `langfuse.trace.name`.
  - A generation has `langfuse.observation.type = "generation"`, `langfuse.observation.model.name` and `langfuse.observation.usage_details` (a JSON string).
  - `update(level="WARNING", status_message=…)` sets `langfuse.observation.level` and `langfuse.observation.status_message`.
  - Metadata keys appear as `langfuse.observation.metadata.<key>`, with JSON-encoded values.
- **Context reaches LangGraph nodes.** In a probe graph with an interrupt, spans opened inside nodes were children of the invocation's root span, for the start and for the resume alike. Both roots were in the same trace, and every span had the session id.
- **An invocation span is never parentless.** With `trace_context`, Langfuse sets a non-recording parent span (a random span id, never exported) under the invocation. Tests find roots by "no exported parent" (E16), not by `parent is None`.
- **Langfuse clients are singletons per public key.** A second `Langfuse(...)` with the same public key reuses the first one's exporter, even after the first was shut down. Tests therefore use a new public key for each `Tracing` they build (`"pk-lf-test-" + uuid4().hex`). Production builds exactly one per process.

## Design decisions (fixed)

1. **Statuses.** `agent_complaint.status` gains `refunded` and `refund_failed`. `approved` stays, and now means "approved, refund not final yet". It is no longer final. `RunStatusName` adds `refunded` and `refund_failed`. `RunStatus` keeps its four fields.

   | Final status | When |
   | --- | --- |
   | `refunded` | the refund is `SUCCEEDED` and its resolution is not `CONFLICT` |
   | `refund_failed` | the refund is `FAILED` or `CANCELED`, or its resolution is `CONFLICT`; a person must act (KI-3) |
   | `rejected`, `declined`, `escalated` | as in F22 |

2. **No new column; the status check is widened.** The refund id is read from the checkpoint (`state.values["review"]["refund_id"]`), which F22 made the source of truth for the run; `agent_complaint` stays for finding work. So its columns are exactly F22's, and F22's R11 (which asserts the exact column set) is unchanged. In `ComplaintStore.setup()`, after the F22 `CREATE TABLE IF NOT EXISTS` (whose status list now includes the two new statuses):

   ```sql
   ALTER TABLE agent_complaint DROP CONSTRAINT IF EXISTS agent_complaint_status_check;
   ALTER TABLE agent_complaint ADD CONSTRAINT agent_complaint_status_check CHECK (status IN (
       'running', 'submitting', 'submit_retry', 'awaiting_review', 'approved',
       'rejected', 'declined', 'escalated', 'refunded', 'refund_failed'));
   ```

   - `agent_complaint_status_check` is the name Postgres gives F22's inline column check. Test E14 proves the upgrade on an F22-shaped table.
   - Both statements run in one transaction (`async with conn.transaction()`). The pool is autocommit, so the transaction must be explicit.
   - Amended before the work commit: the first version of this plan added a `refund_id` column, which would have broken R11. Codex found it during its read-only check.

3. **Graph** (F22's, extended). New nodes `approved` and `await_refund`; new state keys `refund` (dict) and, in `execution` escalations, stage `execute`.

   ```
   … submit → await_review ─┬─ REJECTED ─────────────────────────→ finish → END
                            └─ APPROVED → approved → await_refund → finish
   ```

   | Node | Does |
   | --- | --- |
   | `approved` | `store.mark_approved(complaint_id)`: status `approved`. Returns `{"proposal": {**state["proposal"], "status": "APPROVED"}}` |
   | `await_refund` | first statement `refund = interrupt({"refund_id": state["review"]["refund_id"]})`; then decision 5's checks; returns `{"refund": refund}` or an `execute` escalation |
   | `finish` | adds: `refund` present and no escalation → `refund_outcome(refund)` (decision 4), which is `refunded` or `refund_failed` here |

   Routing after `await_review`: `"approved"` when `review.status == "APPROVED"`, else `"finish"`. After `await_refund`: always `"finish"`.

4. **Refund outcome** (`refund_outcome(refund: Refund | dict) -> Literal["waiting", "refunded", "refund_failed"]`, pure, in `execution.py`):

   | `resolutionStatus` | `refundStatus` | Outcome |
   | --- | --- | --- |
   | `CONFLICT` | any | `refund_failed` |
   | `KNOWN` or `UNKNOWN` | `SUCCEEDED` | `refunded` |
   | `KNOWN` or `UNKNOWN` | `FAILED`, `CANCELED` | `refund_failed` |
   | `KNOWN` or `UNKNOWN` | `RESERVED`, `SUBMITTED`, `PENDING`, `REQUIRES_ACTION` | `waiting` |

   - `financialStatus` is not read. The contract says a `SUCCEEDED` refund may still be `PENDING_EVIDENCE`; the customer has been refunded either way.
   - There is no timeout. A refund that stays `waiting` stays `approved` (Risks).

5. **Resume value and its checks.** `poll()` resumes with `refund_resume_value(refund)`, exactly `{"id", "payment_id", "amount_minor", "currency", "refund_status", "resolution_status", "financial_status", "provider_status", "updated_at"}` (JSON: enums as strings, `updated_at` ISO 8601). `await_refund` then checks, in order:
   - `id == review["refund_id"]`,
   - `payment_id == evidence.payment.id`,
   - `amount_minor == decision.amount_cents`,
   - `currency == evidence.payment.currency`.

   The first difference → `("execute", "refund_mismatch", "<field> differs")`, so `escalated`. A `refund_outcome` of `waiting` here → `ValueError("refund is not final")`: a bug in `poll`.

6. **`Agent.poll()` additions.** `store.resumable()` now also returns `approved` rows. For each:
   1. `state = await graph.aget_state(config)`; `state.next` must be `("await_refund",)`, else `ThreadStateError(complaint_id, "not waiting for refund")`.
   2. `refund = await ledger.get_refund(state.values["review"]["refund_id"])`.
   3. A `ClientError` → skip this row in this pass.
   4. `refund_outcome(refund) == "waiting"` → skip.
   5. Otherwise `ainvoke(Command(resume=refund_resume_value(refund)), config, durability="sync")`.

   Rows keep F22's order. A row resumed from review to `approved` in one pass is not read again in the same pass, because `resumable()` was read at its start.

7. **The ledger is the only money path.**
   - `AgentLedger` adds `get_refund(refund_id) -> Refund`.
   - `LedgerClient`'s public methods are exactly `get_payment`, `get_refundable`, `create_proposal`, `get_proposal`, `get_refund`.
   - In `clients/ledger.py` the only HTTP method other than `GET` is the `POST` to `/v1/refund-proposals`.
   - No `.py` file under `fairsettle_agent/` contains `paypal` (any case).

   E6 checks these statically, E13 at run time.

8. **Tracing** (`fairsettle_agent/tracing.py`):

   ```python
   class Stage(Protocol):
       def update(self, **fields) -> None: ...          # level, status_message, metadata, model, usage_details

   class Tracing:
       def __init__(self, langfuse: Langfuse | None) -> None   # None: off
       @classmethod
       def off(cls) -> "Tracing"
       @classmethod
       def from_config(cls, config: TracingConfig) -> "Tracing"
       @property
       def enabled(self) -> bool
       @staticmethod
       def trace_id(complaint_id: str) -> str           # Langfuse.create_trace_id(seed=complaint_id)
       @contextmanager
       def invocation(self, complaint_id: str, name: InvocationName) -> Iterator[None]
       @contextmanager
       def stage(self, name: str, *, as_type: Literal["span", "generation"] = "span", **fields) -> Iterator[Stage]
       def flush(self) -> None
       def shutdown(self) -> None

   InvocationName = Literal["start", "retry_submit", "resume_review", "resume_refund"]
   ```

   - `invocation`: `with propagate_attributes(session_id=complaint_id, trace_name="complaint"):` then `with langfuse.start_as_current_observation(trace_context={"trace_id": trace_id(complaint_id)}, name=name, metadata={"complaint_id": complaint_id}):`.
   - `stage`: `langfuse.start_as_current_observation(name=name, as_type=as_type, **fields)`, yielding the observation.
   - When off, both yield a no-op (`stage` yields an object whose `update` does nothing), and `flush` and `shutdown` do nothing.
   - `from_config`: `Langfuse(public_key=…, secret_key=…, base_url=…, tracer_provider=TracerProvider())`. It owns its provider and never touches OpenTelemetry's global one.
   - `get_trace_url` is never called (it connects).
   - Tracing never changes an outcome. Exceptions inside a `with` propagate unchanged; Langfuse records them on the span.

9. **Where spans are opened.**
   - `Agent.start` wraps `ainvoke` in `invocation(id, "start")`. `Agent.poll` wraps each `ainvoke` in `"retry_submit"`, `"resume_review"` or `"resume_refund"`, by the row's status. A skipped row gets no span.
   - Nodes `gather`, `count`, `decide`, `submit`, `approved` and `finish` run their body inside `stage(<node name>)`; `decide` uses `as_type="generation"`.
   - `await_review` and `await_refund` open their stage only **after** `interrupt()` returns, never before (F22: the node runs again on resume).
   - Fields set on each stage, metadata only:

     | Stage | Fields |
     | --- | --- |
     | `gather` | escalation: `level="WARNING"`, `status_message=<reason>`, `metadata={"stage", "reason", "detail"}` |
     | `count` | `metadata={"prior_complaints_in_7_days": n}`; escalation as above |
     | `decide` | `model=<model id>`, `usage_details={"input": prompt_tokens, "output": completion_tokens}`, `metadata={"attempts", "outcome", "decision", "amount_cents", "reason_code", "violations": [rule, …]}`; an F21 escalation: as above, with no `decision` keys |
     | `submit` | `metadata={"attempt": n, "proposal_id": …}`; `SubmitDeferred`: `level="WARNING"`, `status_message="submit_retry"` before it is raised; escalation as above |
     | `await_review` | `metadata={"proposal_id", "review_status"}` |
     | `approved` | `metadata={"refund_id"}` |
     | `await_refund` | `metadata={"refund_id", "refund_status", "resolution_status"}`; mismatch escalation as above |
     | `finish` | `metadata={"final": final}`; `level="WARNING"` when final is `escalated` or `refund_failed` |

   - `outcome`, `decision`, `reason_code` and `violations` are fixed literals. `detail` strings are F21/F22's, which hold class names, codes and ids, never text.

10. **Trace id on the proposal.** `proposal_request(..., trace_id: str | None = None)`. `AgentRunRef` gains `trace_id: Annotated[str, StringConstraints(min_length=1, max_length=128)] | None = None`, and `ProposalRequest.body()` becomes `model_dump(mode="json", by_alias=True, exclude_none=True)`, so `traceId` is sent only when tracing is on. The submit node passes `Tracing.trace_id(complaint_id)` when `deps.tracing.enabled`. The id is deterministic, so a retried POST has the same body and the ledger replays it.

11. **Configuration** (`AgentConfig`):
    - `AgentConfig` adds `tracing: TracingConfig | None`, with `TracingConfig(public_key, secret_key (repr hidden), base_url)`.
    - `from_env` checks F22's five variables first, unchanged. Then `FAIRSETTLE_TRACING`:
      - unset or `on`: `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL` are required (`ValueError("<NAME> is required")`), in that order;
      - `off`: `tracing=None`;
      - any other value: `ValueError("FAIRSETTLE_TRACING must be on or off")`.
    - `repr` shows the Langfuse base URL and public key, and `<set>` for the secret.
    - `open_agent` builds `Tracing.from_config(config.tracing)` or `Tracing.off()`, passes it to `Agent`, and calls `tracing.shutdown()` on exit (which flushes).
    - `Agent.__init__` takes `tracing: Tracing` as a **required** keyword, so no production path can forget it.

## Risks

- **A refund that never becomes final** (KI-1, lost request: `SUBMITTED`/`UNKNOWN` forever) keeps the complaint `approved` and is read on every `poll()`. No money is at risk; the ledger's recovery resolves it or escalates. F24 decides whether `poll()` needs a backoff.
- **Langfuse SDK 5 against the server F24 uses.** Only the SDK was checked here, not the wire protocol against a real server. This Mac has a stopped Langfuse 4 server (`interview-langfuse-*`) from another project. F24 checks a live trace, and pins a server version if 5.0.4 needs one.
- **Export happens in the background.** A process killed right after a run can lose its last spans. `open_agent` flushes on exit; the checkpoint, not the trace, is the source of truth.
- **The contract's `RefundSummary` disagrees with the ledger on nulls.** It lists `providerRefundId` and `providerStatus` as required; the ledger omits them when they are null. The agent accepts both forms. Making the contract say "optional", or making the ledger write explicit nulls (as F17 did for its new endpoints), is a contract change for later; record it in the F23 progress entry.
- **Terminal refund shapes are not recorded** (decision with the user). E2's in-memory variants follow the contract. F24's live refund is the first real `SUCCEEDED`.
- **Old paused threads.** A thread paused at `await_review` before F23 resumes into `approved` and `await_refund`, because the node names are new and the old ones unchanged. No such thread exists outside tests yet.
- **Metadata could still leak text** if a later change puts a free-text field into `detail`. E18 scans every attribute for the known texts.
