# F12 · M1: real sandbox payment and partial refund

## Goal

Behavior (copied from docs/features.json):

> Against the real PayPal Sandbox: create, approve in browser, capture, partial refund, both webhooks received; ledger entries balance.

Verification (copied from docs/features.json):

> kind `manual`:
> 1. Payment and refund visible in the sandbox merchant account
> 2. Both webhooks arrived through ngrok or the deployed URL and were posted once
> 3. Ledger balance check passes; order id, capture id and refund id recorded in docs/progress.md

F12 has two parts.

1. **Code (Codex, one work commit).** Everything the real Spring application needs to run the PayPal flow end to end, plus a repeatable proof of it with PayPal stubbed:
   - a PayPal mode for local fixtures;
   - the webhook switch in `application.yml`;
   - a full-application IT;
   - a live-run script that drives the run and checks the result;
   - a runbook.
2. **The live run (a human).** After the work commit, a person follows the runbook against the real sandbox, records the ids in `docs/progress.md` and runs `python3 scripts/features.py verify F12` themself. F12 is `kind: manual`: no agent confirms it (AGENTS.md).

### Why code is needed at all

F05–F10 tested every PayPal piece with hand-wired objects (`new PaymentExecutor(...)`, `new CaptureSettlementService(...)`). The real application has never started with `platform.paypal.enabled=true`. Three gaps were found while planning and block a real run today:

| Gap | Where | Effect today |
| --- | --- | --- |
| Local fixtures only create a `FAKE` provider account (`provider_account_ref='fixture_local_account'`) and no ingestion policy or ledger accounts | `identity/LocalFixtureInitializer` | The PayPal deployment binding and webhook account binding (`provider_account_ref` must equal the PayPal client id) never match. Even with a manual fix, posting returns `OPENING_POLICY_REQUIRED` (F06 decision 7). |
| No `PARTNER_SHARE_EXPENSE` / `PARTNER_PAYABLE` accounts | the same | Revenue share is enabled by default (`platform.revenue-share.enabled:true`). The fixture price links a 1500 bps share policy. `RevenueShareService` looks both accounts up with `orElseThrow()`, so the first capture posting throws. The PayPal ITs never saw this, because they wire `RevenueShareService.disabled()`. |
| `platform.webhooks.paypal.enabled` has no env-var mapping | `application.yml` | Deferred by F09 to F12/F13. |

Earlier plans also deferred these observations to F12. The live run records them, and the plan does not change code for them (decision 9):

- `custom_id` echo on create (F05);
- capture breakdown present (F06);
- refund representation with `seller_payable_breakdown` (F08);
- byte-exact webhook verification (F09);
- the real `PAYMENT.CAPTURE.REFUNDED` shape (F03, F10).

## Design decisions (fixed)

1. **PayPal fixture mode.** `LocalFixtureInitializer` provisions PayPal when `platform.paypal.enabled=true`. Otherwise it behaves exactly as today (`FAKE`).
   - In PayPal mode, provider account `id(21)` is `provider='PAYPAL'` with `provider_account_ref` = the PayPal client id. That ref is what both `PaymentRepository#deployment` and `PayPalWebhookEndpoint` bind to.
   - It also inserts one `ingestion_policy` row: `opening_mode='ZERO'`, `business_zone='UTC'`, `livemode=false`.
   - It inserts seven USD ledger accounts:
     - `PSP_FUNDS`, `PSP_FEE_EXPENSE`, `SUSPENSE`: `PROVIDER`, provider `id(21)`, `PAYMENTS`;
     - `SALES_REVENUE`, `SALES_RETURNS`, `PARTNER_SHARE_EXPENSE`, `PARTNER_PAYABLE`: `INTERNAL`, provider and domain null.
   - Everything else (organization, environment, application, credentials, price 10000 USD, 1500 bps share policy) is unchanged.
2. **Fail fast on a mismatched database or scope.**
   - **Existing database.** It must match the requested mode: provider `id(21)` has the same `provider` and `provider_account_ref`. Otherwise throw `IllegalStateException("Existing fixture provider differs; recreate the local database")`. Nothing is migrated or overwritten, which matches the existing "never rotates or overwrites" rule.
   - **Configured PayPal scope.** In PayPal mode the configured scope (`organization-id`, `environment-id`, `provider-account-id`) must equal `id(1)`, `id(11)`, `id(21)`. Otherwise throw `IllegalStateException("PayPal fixtures require the local fixture scope ids")`.
   - **Client id.** It must be non-blank. Otherwise throw `IllegalStateException("PayPal fixtures require PAYPAL_CLIENT_ID")`.

   All checks run before any insert.
3. **One config line.** `application.yml` gets `platform.webhooks.paypal.enabled: ${PAYPAL_WEBHOOK_ENABLED:false}`, next to the Stripe one. Every other PayPal key already falls back to an env var. No new property names.
4. **No change** to:
   - the PayPal adapters, state machines, posting, `financialingestion` or `revenueshare`;
   - migrations, the ADR, `scripts/features.py` or the verification steps.

   The revenue-share gap is closed by fixture accounts only.
5. **Prove the real wiring with PayPal stubbed.** The new `PayPalSandboxFlowIT` boots the real application context with profiles `api,local`, fixtures in PayPal mode, and the PayPal webhook enabled.
   - **Stub.** It replaces the `payPalAuthClient` bean with `@TestBean` → `PayPalTestTransport.client(clock)`. No production seam is added.
   - **Driving.** It drives the flow over HTTP. Worker work runs by calling the same beans the worker schedules (`RefundExecutor#execute`, `WebhookProcessor#processDue`); no schedulers run in the `api` profile.
   - **Coverage.** It covers what F12's live run does. It runs under `./mvnw verify` and must pass before the work commit.
6. **The live-run script never calls PayPal and never writes.** `ledger/scripts/paypal_sandbox_run.py` (stdlib only):
   - talks only to the local ledger (`/v1`, `/ops`);
   - reads the local database with `SELECT`s through `docker exec … psql` under `PGOPTIONS=-c default_transaction_read_only=on`;
   - prints no secret.

   Only the ledger calls PayPal (AGENTS.md).
7. **Fixed amounts.**
   - Payment: 10000 USD, the fixture price; `productRef='demo-product'`, `priceVersion=1`.
   - Partial refund: 2500.
   - After the run the expected share effective amount is `1500 × (10000 − 2500) / 10000 = 1125`.
8. **What "posted once" and "balance check passes" mean.** They are checked by both the IT and the script:
   - **Webhooks.** For the capture id there is at least one `webhook_inbox` row with `event_type='PAYMENT.CAPTURE.COMPLETED'`, and every such row is `DONE`. The same holds for the refund id with `PAYMENT.CAPTURE.REFUNDED`.
   - **Postings.** There is exactly one `balance_transaction` per id (`bt_id`) with `state='POSTED'` and a journal. The PayPal account's `PSP_FUNDS` has exactly 2 journal entries.
   - **Balances.** `GET /ops/balances?currency=USD`:
     - every returned account has `rebuildMatches=true`, and the signed `balanceMinor` sum is 0;
     - `PSP_FUNDS` = capture net + refund net (the refund BT's net is negative);
     - `PSP_FEE_EXPENSE` = capture fee + refund fee;
     - `SALES_REVENUE` = −10000, `SALES_RETURNS` = 2500;
     - `PARTNER_SHARE_EXPENSE` = −`PARTNER_PAYABLE` = 1125.

     Balances are debit-positive, as `OpsQueryService#balances` computes them.
9. **The live run observes; it does not fix.** If the real sandbox differs from the fixtures, the human stops and records the observed response in `docs/progress.md`. Examples: `custom_id` missing on create, no breakdown, verification `FAILURE` on genuine events, or a refund event waiting as `INCOMPLETE_REFUND_FACT`. A fix needs a plan amendment.
10. **ADR follow-through after a good run.** The ADR has rows marked "spec, not yet observed": the `PAYMENT.CAPTURE.REFUNDED` resource type, and the `custom_id` echo in GET order refunds. If the run confirms them, the human (or a later session) changes only those two rows to "observed in sandbox, F12 (<date>)". That edit is its own commit, `docs: PayPal ADR rows observed in sandbox (F12)`, made before `verify` because `verify` needs a clean tree. If the run does not confirm them, the rows stay and the observation goes into `docs/progress.md`.

Functions:

- `@dataclass(frozen=True) class Config: api_url: str; worker_url: str; app_token: str; ops_token: str; db_container: str; db_name: str; db_user: str`. `__repr__` must not include the tokens: override it to print `Config(api_url=…, worker_url=…, db_container=…, db_name=…)`.
- `load_config(env: Mapping[str, str]) -> Config`:
  - `LOCAL_APP_SECRET` and `LOCAL_OPS_SECRET` are required, and each must be exactly 43 characters. Otherwise raise `ValueError("<NAME> must be a 43-character secret")`.
  - `api_url` = `http://localhost:` + `API_PORT` (default 8080); `worker_url` the same with `WORKER_PORT` (default 8081).
  - `db_container` = `F12_DB_CONTAINER` or `"pl-postgres"`; `db_name` = `DB_NAME` or `"payments_ledger"`; `db_user` = `DB_SUPERUSER` or `"postgres"`.
  - `PAYPAL_ENABLED` must be `"true"`. Otherwise raise `ValueError("PAYPAL_ENABLED must be true")`.
- `payment_body(run_id: str) -> dict`: `{"orderKey": f"f12-{run_id}", "productRef": "demo-product", "priceVersion": 1, "amountMinor": 10000, "currency": "USD", "successUrl": "https://example.com/f12/return", "cancelUrl": "https://example.com/f12/cancel"}`.
- `refund_body(payment_id: str, run_id: str) -> dict`: `{"paymentId": payment_id, "amountMinor": 2500, "currency": "USD", "reason": "REQUESTED_BY_CUSTOMER", "clientRefundKey": f"f12-refund-{run_id}"}`.
- `hosted_url(resource: dict) -> str`:
  - `nextAction.type` must be `REDIRECT_TO_HOSTED_CHECKOUT`, and `nextAction.hostedUrl` must start with `https://www.sandbox.paypal.com/`;
  - otherwise raise `ValueError` naming which check failed;
  - returns the URL.
- `payment_done(resource: dict) -> bool`:
  - `paymentStatus == "SUCCEEDED" and financialStatus == "POSTED"`;
  - raises `RuntimeError` if `paymentStatus` is `CANCELED` or `FAILED`.
- `refund_done(resource: dict) -> bool`:
  - `refundStatus == "SUCCEEDED" and financialStatus == "POSTED"`;
  - raises `RuntimeError` if `refundStatus == "FAILED"` or `controlState` is present and not `"NORMAL"`.
- `paypal_id(value: str) -> str`: returns the value if `PAYPAL_ID.fullmatch(value)`, else raises `ValueError`. Every id goes through it before it appears in SQL.
- `check_webhooks(rows: list[dict], capture_id: str, refund_id: str) -> list[str]` returns failure messages, empty when fine. `rows` have `event_id`, `event_type`, `object_id`, `status`, `reason`. The rules are decision 8's webhook rules. A non-`DONE` row's message includes its `status` and `reason`.
- `check_postings(bts: list[dict], psp_entries: int, capture_id: str, refund_id: str) -> list[str]`: `bts` have `bt_id`, `state`, `journal_id`, `amount_minor`, `fee_minor`, `net_minor`. The rules are decision 8's posting rules.
- `check_balances(items: list[dict], capture_bt: dict, refund_bt: dict) -> list[str]`:
  - `items` are `/ops/balances` items. Use only those whose `providerAccountId` is `PROVIDER_ACCOUNT` or whose `sourceDomain` is `INTERNAL`.
  - The rules are decision 8's balance rules.
  - A missing account purpose is a failure.
- `summary(order_id, capture_id, refund_id, event_ids: list[str], balances: dict[str, int], failures: list[str]) -> str`: plain-text lines, ready to paste into `docs/progress.md`.
  - The first line is `F12 live run: PASS` or `F12 live run: FAIL`.
  - Then `order id`, `capture id`, `refund id`, `webhook event ids`, one `balance <PURPOSE> = <minor>` line per purpose, and every failure.
- IO helpers, not unit-tested:
  - `request(method, url, auth_header, body=None, key=None) -> tuple[int, dict]` with `urllib.request`. A 4xx/5xx raises `RuntimeError` with the status and the response `code` field, never the request headers.
  - `query(config, sql) -> list[dict]`: runs `docker exec -e PGOPTIONS=-c default_transaction_read_only=on <container> psql -U <user> -d <db> -At -v ON_ERROR_STOP=1 -c <sql>`. The SQL is always `SELECT coalesce(json_agg(t),'[]') FROM (<inner>) t`, and the single output line is parsed with `json.loads`.
  - `wait_until(check, timeout_s, interval_s=3) -> Any`: polls until `check()` returns a truthy value. On timeout it raises `TimeoutError`.
- `main() -> int`, in this order:
  1. `load_config(os.environ)`.
  2. Preflight:
     - `GET <api>/actuator/health` and `GET <worker>/actuator/health` must return `UP`;
     - `GET /v1/identity` with the app token must return 200.
  3. `run_id = time.strftime("%Y%m%d%H%M%S")`. `POST /v1/payments` with `Idempotency-Key: f12-pay-<run_id>` must return 201. Print the payment id and `hosted_url(...)`.
  4. Prompt: `Open the URL, sign in with the sandbox PERSONAL account, approve, then press Enter`.
  5. `wait_until(GET /v1/payments/{id} → payment_done, 120)`. The `GET` itself triggers the capture (F06 decision 10). Record `checkoutSessionId` as the order id and `latestChargeId` as the capture id; both go through `paypal_id`.
  6. `POST /v1/refunds` with `Idempotency-Key: f12-refund-<run_id>` must return 201. Then `wait_until(GET /v1/refunds/{id} → refund_done, 180)`; the worker sends it. Record `providerRefundId` through `paypal_id`.
  7. `wait_until(webhooks ok, 600)`. Each poll queries `SELECT event_id,event_type,object_id,status,reason FROM platform.webhook_inbox WHERE object_id IN ('<capture>','<refund>')` and passes when `check_webhooks` is empty. PayPal can take minutes.
  8. Query the BTs (`SELECT bt_id,state,journal_id,amount_minor,fee_minor,net_minor FROM platform.balance_transaction WHERE bt_id IN (…)`). Query the PSP entry count: entries on the `PSP_FUNDS` account of `PROVIDER_ACCOUNT`. Then `GET /ops/balances?currency=USD` with the ops token. Run the three checks.
  9. Print `summary(...)`. Return 0 if there are no failures, else 1.

  `Ctrl-C` and `TimeoutError` print the ids known so far and return 2.

## Risks

- **Revenue share in the real wiring.** If accrual or reservation reconciliation needs more than the two partner accounts, test 11 fails at step 2 or 3. Stop and report the stack trace; do not disable revenue share.
- **Startup calls to PayPal.** If any bean calls PayPal during startup (token prefetch), test 11's first queued `token()` is consumed early and step 1 fails. Report the call list. Do not add a production seam to avoid it.
- **Hidden recovery work in the `api` profile.** No scheduler runs there (`PaymentWorker` and `WebhookWorker` are `worker`-only). If a call shows up that test 11 did not queue, report it instead of adding replies.
- **Real sandbox shapes** (the F05/F06/F08/F09/F10 risks): `custom_id` missing on create, missing breakdowns, verification `FAILURE` on genuine events, the refund event shape. The script fails with the inbox `reason` or payment state; the human records it (decision 9).
- **Webhook delivery delay or ngrok changes.** The script waits up to 10 minutes. A changed ngrok domain means re-registering and a new `PAYPAL_WEBHOOK_ID`; restart the API after that.
- **Local database state.** Fixtures refuse a `FAKE` database. Recreating it deletes local data; that is the operator's call, and the runbook says so.
- **Secrets.**
  - The root `.env` is gitignored (`.gitignore:2`).
  - The script never prints tokens (test 21, test 29).
  - `PAYPAL_CLIENT_SECRET` is only read by the ledger process.
  - Before every commit, check `git status` shows no `.env`.
- **Full suite time.** `./mvnw verify` takes about 30 minutes on the developer's Mac (F11). The new IT adds one Spring context.
