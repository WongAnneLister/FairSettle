## Goal

Behavior (copied from docs/features.json):

> The storefront (dispatch/frontend) is English only: every page, toast, status and date. The order page's demo controls appear only to the role that may use them, and a picked-up order can be marked as a failed delivery by its driver, with a driver-fault or platform-fault reason, and shows as Delivery failed.

The demo video (F31) and the README GIF are recorded in the storefront. Judges read English, and the old GIF showed Chinese labels.

### Decisions (user, 2026-11-04)

1. **Replace the Chinese text with English in place.** No i18n library, no language switch. `<html lang="en">`, and dates and times in `en-US`.
2. **The order page's quick-advance row ("快捷推进演示") shows only the actions the signed-in role may perform.** Today a customer sees every button and gets "操作受限" on click. That is what happened during the F30 GIF recording.
3. **Support `DeliveryFailed` in the storefront.**
   - The status shows everywhere a status shows.
   - The assigned driver can mark a picked-up order as failed, with reason `DRIVER_FAULT` or `PLATFORM_FAULT`.
   - The backend already supports it (F25): `editOrder` takes `failureReason`, and the state machine allows `PickedUp → DeliveryFailed` for the assigned driver.

## Changes

### `src/lib/order-actions.ts` (new)

```ts
import { DeliveryFailureReason, Order, OrderStatus, User, UserRole } from './types';

export type QuickAction = 'startCooking' | 'finishCooking' | 'takeOrder' | 'pickUp' | 'deliver' | 'markFailed';

/** English label for every order status (F36). */
export const ORDER_STATUS_LABELS: Record<OrderStatus, string>;

/** Delivered and DeliveryFailed end an order. */
export function isFinished(status: OrderStatus): boolean;

/** The order page's demo controls the signed-in user may use, in display order. */
export function quickActionsFor(
  order: Pick<Order, 'status' | 'driver'>,
  user: Pick<User, 'id' | 'role'> | null,
): QuickAction[];

export const DELIVERY_FAILURE_REASONS: ReadonlyArray<{ value: DeliveryFailureReason; label: string }>;

/** The editOrder input that marks a picked-up order as a failed delivery. */
export function markFailedInput(orderId: number, reason: DeliveryFailureReason):
  { id: number; status: OrderStatus.DeliveryFailed; failureReason: DeliveryFailureReason };
```

`ORDER_STATUS_LABELS`:

| Status | Label |
| --- | --- |
| `Pending` | `Waiting for the restaurant` |
| `Cooking` | `Cooking` |
| `Cooked` | `Ready for pickup` |
| `PickedUp` | `On the way` |
| `Delivered` | `Delivered` |
| `DeliveryFailed` | `Delivery failed` |

`quickActionsFor`:
- `user` is `null` or `Client` → `[]`.
- `Owner`: `Pending` → `['startCooking']`; `Cooking` → `['finishCooking']`; otherwise `[]`. The backend still checks that the owner owns the restaurant.
- `Delivery`:
  - `Cooked` with no `order.driver` → `['takeOrder']`;
  - `Cooked` with `order.driver?.id === user.id` → `['pickUp']`;
  - `PickedUp` with `order.driver?.id === user.id` → `['deliver', 'markFailed']`;
  - otherwise `[]`, including another driver's order.
- `Delivered` and `DeliveryFailed` → `[]` for everyone.

`DELIVERY_FAILURE_REASONS`, in this order:
1. `{ value: DRIVER_FAULT, label: 'Driver fault' }`;
2. `{ value: PLATFORM_FAULT, label: 'Platform fault' }`.

`markFailedInput(7, DRIVER_FAULT)` returns `{ id: 7, status: 'DeliveryFailed', failureReason: 'DRIVER_FAULT' }`.

## Risks

- **Missed text in rarely visited pages.** E1 scans every source file, so nothing Chinese can remain. A clumsy translation is a review matter.
- **Layout shifts**, because English strings are longer than Chinese ones. Check at 1324 px width and at phone width in review. Long button labels may wrap; that is acceptable.
- **`DeliveryFailed` in Apollo variables.** The value is the enum name string, like the existing statuses, and the GraphQL enum is `DeliveryFailed` in `dispatch/src/orders/entities/order.entity.ts`. A live check in review marks one order failed on the live stack.
- **The proactive case (F25) opens for a failed delivery.** That is intended: marking an order failed on the live stack makes the agent propose a refund. Review checks this once and leaves the case for the human to approve or reject.
